# 智能客服 Bot

把 FAQ、追问、转人工和工单摘要串成闭环。

## 背景

这个案例适合训练 AI 产品经理从业务场景出发，而不是从模型能力出发。

## 用户与痛点

- **目标用户**：业务人员、运营人员、客服/销售/管理者或内部知识工作者。
- **核心痛点**：信息分散、重复劳动、判断成本高、输出质量不稳定。
- **AI 机会**：用检索、生成、工具调用或工作流降低任务完成成本。

## 产品方案

1. 明确输入：用户提供什么材料、系统能读取哪些数据。
2. 明确处理：模型、检索、规则和人工确认分别负责什么。
3. 明确输出：答案、摘要、报告、建议、工单或结构化结果。
4. 明确兜底：失败提示、人工接管、重试和日志。

## 指标

- 使用：触发率、完成率、留存。
- 质量：采纳率、人工修改率、差评率。
- 效率：节省时间、自动处理比例。
- 风险：错误率、越权访问、敏感输出。

## 可写进简历

设计「智能客服 Bot」方案，围绕用户任务拆解 AI 输入、处理、输出、评估和风险兜底，形成可落地的产品闭环。

---

客服流程可拆成：意图识别、知识问答、身份与订单查询、业务办理、投诉处理、闲聊和转人工。生成式 AI 擅长理解多样表达、综合知识和生成个性化回复；账户状态、退款规则和资损动作必须连接真实系统并受规则控制。

贯穿例子：用户说「耳机坏了，能换吗？订单号 202608210088」。正确路径是查订单（工具）+ 读制度（知识库）+ 按口径回答 + 确认后建单或转人工。错误路径是只丢给模型，让它编「30 天无理由」或假装已经办成。技术拆解见 [大语言模型基础](/concepts/ai-tech/llm-rag-agent/llm-basics) 起的一组「大模型应用」页。

## 节点怎么分

| 节点 | 谁做 | 失败时 |
| --- | --- | --- |
| 理解诉求 | 模型 | 追问订单号或转人工 |
| 规则是什么 | 知识库 | 无适用规则则拒答并转人工 |
| 这单现在怎样 | 订单接口，校验当前用户 | 超时转人工，禁止编物流 |
| 能不能换 | 规则（如签收 ≤7 天且质量问题） | 不要让模型单独拍板 |
| 提交换货 | 用户确认 + 后端写接口 | 失败明确说失败 |
| 投诉 / 欺诈 / 高客单 | 人工 | 机器人不得压着不转 |

不能单纯追求降低转人工。把复杂或高风险问题留在机器人里，可能让成本更高、体验更差。

## 指标

| 层 | 指标 | 注意 |
| --- | --- | --- |
| 效率 | 平均处理时长、一次解决率 | 一次解决不能靠乱承诺换来 |
| 质量 | 答案正确率、引用命中、乱承诺次数 | 通顺度和事实正确分开打 |
| 风险 | 严重错误率、越权查单 | 生产对假办结零容忍 |
| 体验 | 转人工准确性、客户满意、重复咨询 | 该转没转也是失败 |

## PRD 要写清

输入：登录身份、用户原话。输出：对用户短回复 + 内部结构（意图、是否要查单、是否要检索、是否升级）。禁止：编制度、编订单、口头办结。评测集至少覆盖典型换货、过保、无订单号、诱导「你就说换好了」。

## 面试怎么讲这个项目

业务背景 → 目标客户与任务 → 原流程痛点（排队、口径不一致、查单慢）→ AI 切入点（规则走 RAG，状态走工具）→ 责任边界（确认后才建单）→ 评测与指标 → 实施阻力（制度版本、权限）→ 复盘。没有真实上线时如实说 Demo / PoC，展示验证证据。
