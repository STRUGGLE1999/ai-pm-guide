### 题 1：字节跳动飞书智能伙伴：Agent 工作流编排中如何平衡灵活性与可控性？

> 🏢 **真题来源**：字节跳动 · 飞书 AI 产品经理面经

::: info 🎯 核心考点与破题关键
- **考点实质**：Agent 工作流编排的核心矛盾：多步推理与工具调用的灵活性 vs 企业级场景下的确定性、可审计与安全合规。
:::

::: tip 💡 参考回答示范
> “我在飞书智能伙伴项目中负责 Agent 工作流编排模块。当时业务方希望 Agent 能自动处理跨文档、日程、审批的复杂任务，但初期版本经常出现步骤跳跃、工具误调用、甚至越权操作。我的解法是分层设计：第一层是意图识别与路由，用轻量模型将用户请求分类到预定义的 12 个场景模板（如会议纪要生成、审批流发起、跨文档数据汇总），每个模板对应一个 DAG 工作流。第二层是节点级约束，每个工具调用节点必须声明前置条件、输入 schema 和输出校验规则，比如调用审批 API 前必须校验用户是否有对应审批权限，否则直接熔断并提示。第三层是运行时监控，所有节点执行日志实时上报到审计看板，异常节点自动触发人工复核。样本是飞书内部 2000 名员工的灰度测试，口径是任务完成率、误操作率和平均耗时。我们最终将任务完成率从 68% 提升到 89%，误操作率从 5.2% 降到 0.8%，平均耗时控制在 4.3 秒内。关键取舍是：宁可让 Agent 在不确定时主动询问用户，也不允许它自由发挥。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户需求超出预定义模板，如何让 Agent 在可控前提下扩展？
  - **续答**：我会设计一个“沙盒扩展”机制：当路由层识别到低置信度或新意图时，Agent 进入探索模式，但所有工具调用被限制在只读操作，并强制生成一个“执行计划”让用户确认。用户确认后，系统将该意图和对应工具链注册为新模板，经过安全团队审核后加入正式路由表。这样既保证了灵活性，又不会让未审核的写操作直接生效。样本是每周约 150 个新意图，口径是审核通过率和用户采纳率，目前通过率 32%，采纳率 78%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将飞书场景换成钉钉或企业微信，调整工具集和权限模型。
2. 将预定义模板数量从 12 个改为根据业务实际梳理的 8-20 个。
3. 将灰度测试样本量改为自己项目的真实用户数，口径改为自己关注的指标。
:::

### 题 2：阿里巴巴夸克文档问答：RAG 切分粒度如何影响检索准确率与生成质量？

> 🏢 **真题来源**：阿里巴巴 · 夸克 AI 产品经理面经

::: info 🎯 核心考点与破题关键
- **考点实质**：RAG 中文档切分策略对召回率、精确率和生成答案忠实度的综合影响，以及如何根据文档类型动态调整切分粒度。
:::

::: tip 💡 参考回答示范
> “在夸克文档问答项目中，我负责优化 RAG 的检索与切分策略。初期我们采用固定 512 token 切分，结果发现法律合同和学术论文的问答准确率只有 54%，而新闻类文档能达到 82%。分析发现，法律合同条款之间强关联，固定切分导致上下文断裂；学术论文的图表和公式需要与说明文字绑定。我的方案是动态切分：第一，按文档结构解析，对合同类文档以条款为最小单元，对论文以章节和图表说明为单元，对新闻以段落为单元。第二，引入重叠窗口，相邻块重叠 20% 的 token，确保边界信息不丢失。第三，对表格和图片生成摘要文本，与所在章节合并索引。第四，检索时采用混合检索：BM25 加向量检索，再通过 cross-encoder 重排序。样本是夸克内部 5000 份文档的问答测试集，口径是 Top-3 召回率和答案忠实度（人工评估 1-5 分）。优化后，法律合同准确率提升到 79%，学术论文提升到 76%，新闻类保持 85%。忠实度从 3.2 分提升到 4.1 分。关键经验是：切分粒度不是越细越好，要匹配文档的语义边界和查询类型。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何评估切分策略对生成质量的影响？除了人工评估还有什么自动化指标？
  - **续答**：我会用三个自动化指标：第一，检索命中率，即正确答案所在块是否在 Top-K 中；第二，答案覆盖率，即生成答案是否覆盖了标准答案的关键实体和关系；第三，幻觉率，即生成答案中无法在检索块中找到依据的句子比例。样本是 1000 条带标注的问答对，口径是这三个指标的加权得分。同时保留人工抽检 5% 做校准。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将夸克文档换成自己公司的知识库，调整文档类型和查询分布。
2. 将切分策略从固定 token 改为按语义段落或标题层级切分。
3. 将评估指标改为自己业务关注的指标，如客服工单解决率。
:::

### 题 3：腾讯混元大模型长程评测：如何设计多轮对话与长文档理解的自动化评测集？

> 🏢 **真题来源**：腾讯 · 混元大模型产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：大模型长程能力评测的难点：多轮对话中的指代消解、话题漂移，以及长文档理解中的信息定位与推理。
:::

::: tip 💡 参考回答示范
> “在混元大模型的长程评测项目中，我负责设计自动化评测集。我们遇到的核心问题是：现有评测集大多是单轮短文本，无法反映真实场景中 10 轮以上对话和 5 万字文档的理解能力。我的做法是：第一，构建多轮对话评测集，每轮对话包含用户意图、指代关系（如“它”“那个”）、话题切换标记。用规则加人工标注生成 2000 组对话，每组 8-15 轮。第二，构建长文档评测集，从腾讯内部文档中抽取 500 篇长文档（平均 3 万字），每篇设计 10 个问题，覆盖事实查找、多跳推理、摘要生成。第三，自动化评测指标：多轮对话用指代消解准确率和话题一致性得分；长文档用答案精确匹配、ROUGE-L 和推理链完整度。第四，引入对抗样本，比如在长文档中插入干扰段落，测试模型抗干扰能力。样本是 2000 组多轮对话和 500 篇长文档，口径是各指标的平均分。最终我们发现混元在多轮对话中指代消解准确率 76%，长文档多跳推理准确率 61%，为后续迭代提供了明确方向。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何保证评测集的时效性和无污染？
  - **续答**：我会每季度更新 20% 的评测样本，从最新业务日志中采样并脱敏。同时用 n-gram 重叠检测和嵌入相似度过滤，确保评测集与训练集无重叠。样本是每季度 500 条新样本，口径是污染率低于 0.5%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将混元换成自己公司的大模型，调整评测集规模和业务场景。
2. 将长文档类型改为自己业务中的合同、报告或工单记录。
3. 将自动化指标改为自己团队常用的 BLEU、BERTScore 或人工评分。
:::

### 题 4：百度文心一言企业版：如何核算大模型 Token 成本并设计定价策略？

> 🏢 **真题来源**：百度 · 文心一言企业版产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：大模型产品的 Token 成本结构、毛利模型与定价策略，平衡客户接受度与公司盈利。
:::

::: tip 💡 参考回答示范
> “在文心一言企业版项目中，我负责 Token 成本核算与定价策略。首先，我拆解了成本结构：GPU 推理成本占 60%，网络与存储占 15%，运维与研发分摊占 25%。以 A100 为例，单卡每小时成本约 30 元，推理吞吐为每秒 2000 token，则每百万 token 成本约 4.2 元。但实际利用率只有 40%，所以有效成本约 10.5 元每百万 token。其次，我设计了阶梯定价：基础版每百万 token 收费 20 元，企业版 15 元，定制版 12 元，同时提供包年套餐。定价目标是毛利率 50%。样本是 50 家试点企业的用量数据，口径是每百万 token 的综合成本和客户支付意愿。我们发现客户对价格敏感度在 15-20 元区间，最终定价为 18 元每百万 token，毛利率 52%。关键是要动态监控 GPU 利用率和 token 消耗，及时调整资源调度。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果客户用量波动大，如何设计弹性定价？
  - **续答**：我会采用“保底+超额”模式：客户承诺每月最低消费，超出部分按阶梯价。同时提供预留实例，客户预付一年费用可享 7 折。样本是 10 家波动大的客户，口径是资源预留率和成本覆盖率。这样既保证了基础收入，又避免了资源闲置。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将文心一言换成自己公司的大模型，调整 GPU 型号和成本参数。
2. 将定价策略改为按 API 调用次数或按用户数计费。
3. 将毛利率目标改为自己公司要求的水平，如 40% 或 60%。
:::

### 题 5：美团智能客服：高危写操作（退款、改地址）如何设计风控与人工兜底？

> 🏢 **真题来源**：美团 · 智能客服 AI 产品经理面经

::: info 🎯 核心考点与破题关键
- **考点实质**：AI 客服在处理退款、修改订单等高危写操作时的风险控制、权限校验与人工介入机制。
:::

::: tip 💡 参考回答示范
> “在美团智能客服项目中，我负责高危写操作的风控设计。退款和改地址是用户高频请求，但一旦被恶意利用或模型误判，会造成资损。我的方案是四层风控：第一层，意图识别置信度阈值，低于 0.9 的请求转人工。第二层，操作前置校验，退款必须校验订单状态、退款原因、用户历史行为；改地址必须校验配送状态和地址合法性。第三层，金额与频次限制，单笔退款超过 200 元或单用户日退款超过 3 次，自动触发人工审核。第四层，实时监控与熔断，如果某接口错误率超过 1% 或资损超过 1000 元，自动暂停该操作并告警。样本是美团日均 10 万次客服请求，口径是资损率、误操作率和人工转接率。上线后资损率从 0.05% 降到 0.01%，误操作率从 1.2% 降到 0.3%，人工转接率 8%。关键原则是：AI 可以建议，但高危操作必须有人工兜底。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何平衡风控严格度和用户体验？
  - **续答**：我会做分层策略：低风险用户（历史无异常、信用分高）可以走快速通道，高风险用户走严格审核。同时优化人工审核时效，确保 30 秒内响应。样本是 1 万用户的分层测试，口径是用户满意度和资损率。最终低风险用户满意度 92%，高风险用户满意度 78%，整体资损率 0.01%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将美团客服换成自己公司的客服场景，调整高危操作类型。
2. 将风控阈值改为自己业务的实际数据，如退款金额上限。
3. 将人工兜底流程改为自己公司的审核链路。
:::

### 题 6：小红书多模态搜索：如何优化图文笔记的跨模态检索与排序？

> 🏢 **真题来源**：小红书 · 多模态搜索 AI 产品经理面经

::: info 🎯 核心考点与破题关键
- **考点实质**：多模态检索中图文特征的融合、跨模态对齐以及排序策略对搜索满意度的影响。
:::

::: tip 💡 参考回答示范
> “在小红书多模态搜索项目中，我负责优化图文笔记的检索与排序。用户经常用文字搜图片，或用图片搜相似笔记，但初期跨模态召回率只有 45%。我的方案是：第一，构建统一的多模态嵌入空间，用 CLIP 类模型分别提取图像和文本特征，再通过对比学习对齐。第二，针对笔记特点，提取图像中的物体、场景、风格标签，与文本标题、正文、话题标签融合成多模态索引。第三，检索时采用双塔召回加交叉排序：双塔快速召回 Top-200，再用多模态 Transformer 精排 Top-20。第四，引入用户行为反馈，点击、收藏、停留时长作为排序特征。样本是小红书 100 万条笔记和 10 万条查询日志，口径是 Top-10 召回率和点击率。优化后跨模态召回率提升到 72%，搜索点击率提升 18%。关键是要让图文特征在同一个语义空间中对齐，而不是简单拼接。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何处理低质或重复的图文笔记？
  - **续答**：我会在索引阶段做去重和质量过滤：用图像哈希和文本相似度检测重复笔记，只保留质量分最高的。质量分由清晰度、信息量、互动率综合计算。样本是 10 万条笔记，口径是去重率和低质笔记过滤率。去重率 12%，低质过滤率 8%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将小红书换成自己公司的内容平台，调整模态类型。
2. 将 CLIP 模型换成自己团队使用的多模态模型。
3. 将排序特征改为自己业务关注的互动指标。
:::

### 题 7：字节跳动 · 飞书智能助手如何设计多步Agent工作流，确保写操作安全？

> 🏢 **真题来源**：字节跳动 · 飞书 AI 助手 / 企业级 Agent 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察在真实企业协作场景中，如何编排涉及数据库写入、消息发送等高风险操作的 Agent 工作流，并设计风控与确认机制。
:::

::: tip 💡 参考回答示范
> “我在飞书智能助手项目中负责过审批流自动填单的 Agent 设计。当时业务痛点是：员工在飞书里发起采购申请，需要手动从多个系统复制信息填写到审批表单。我们设计了一个多步 Agent，步骤是：1) 解析用户自然语言需求；2) 调用 HR 系统接口获取员工部门、预算余额；3) 调用采购系统查询历史供应商；4) 自动填写审批表单草稿；5) 等待用户确认后提交。关键难点在于第 5 步——写操作不可逆。我们定义了三层风控：第一层，Agent 只生成草稿，不直接提交，必须由用户点击‘确认提交’按钮；第二层，对关键字段（如金额、供应商）做二次弹窗确认，并高亮显示 Agent 填充的内容；第三层，记录完整操作日志，包括 Agent 的推理链路和用户确认时间，便于审计。指标上，我们关注‘草稿采纳率’和‘误操作率’。样本是 200 个真实采购申请，口径是‘用户未修改任何字段直接提交’为采纳，误操作定义为‘提交后 1 小时内撤回’。最终采纳率 68%，误操作率 0.5%。对于高危操作，我们坚持‘人类在环’原则，Agent 只做建议和预填，不做最终决策。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户要求 Agent 自动提交，不想每次确认，你怎么平衡效率和安全？
  - **续答**：我会引入分级授权机制。对于金额低于 500 元、供应商在白名单内的采购申请，允许用户开启‘自动提交’模式，但需要提前签署电子授权协议，并设置每月自动提交次数上限（比如 10 次）。同时，Agent 在自动提交后立即发送飞书消息通知用户，附带撤销链接（2 分钟内可撤回）。对于超过阈值或非白名单供应商的申请，仍然强制人工确认。样本上，我们灰度了 50 个用户，自动提交占比 30%，未发生误操作。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成钉钉审批场景，需要额外考虑钉钉的审批模板 API 限制，以及组织架构同步的延迟问题。

::: warning ⚠️ 连环追问与高分续答

### 题 10：百度 · 文心一言Token成本算账：如何在不降效果的前提下砍掉30%开销？

- **追问 1**：如果输出 token 也很贵，如何优化？

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成美团的外卖客服，要额外考虑高峰期并发，成本优化需结合弹性伸缩和缓存。

### 题 14：阿里巴巴 · 通义千问 RAG 在电商客服场景下如何做检索切分与召回优化？

> 🏢 **真题来源**：阿里巴巴 · 通义千问 / 电商客服 RAG 面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察 RAG 系统中文档切分策略、向量检索与关键词检索的融合，以及电商场景下多轮对话的上下文管理。
:::

::: tip 💡 参考回答示范
> “我在淘宝客服 RAG 项目里负责知识库构建和检索优化。电商客服的知识库包括商品详情、退换货政策、活动规则等，特点是文档结构多样、更新频繁、用户 query 短且口语化。切分策略上，我没有用固定长度切分，而是按语义结构切：商品详情按属性块（如颜色、尺寸、材质）切，政策文档按条款切，每个 chunk 控制在 200-300 字，并保留标题和层级路径作为元数据。检索时采用混合检索：向量检索用通义千问的 embedding 模型，关键词检索用 BM25，然后通过 RRF 融合排序。针对多轮对话，我会把上一轮的用户 query 和客服回答拼接到当前 query 中，但只保留最近两轮，避免噪音。指标上，我们看 Top-3 召回率、答案准确率和用户满意度。样本是脱敏后的真实客服对话日志，口径是‘用户问题明确且知识库有答案’，严禁编造具体数字。风控方面，涉及价格、库存等实时信息时，RAG 不直接回答，而是调用商品 API 获取最新数据。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户问‘我买的衣服能退吗’，但知识库里有多个退换货政策，你怎么保证召回正确的那个？
  - **续答**：我会在检索时加入商品类目和用户订单状态作为过滤条件。比如，先根据用户 ID 查出最近订单，拿到商品类目和购买时间，然后用这些元数据过滤知识库 chunk。如果用户没有登录，我会追问‘请问您买的是哪类商品？’来缩小范围。另外，我会在 chunk 的元数据里标记政策适用的类目和时间范围，检索时做硬过滤。
- **追问 2**：如何评估切分策略的好坏？
  - **续答**：我会做离线评估：人工标注一批 query 和对应的正确 chunk，然后对比不同切分策略下的召回率。同时看线上指标，比如客服回答的采纳率、用户追问率。如果切分太碎，召回可能不完整；切分太大，噪音多。我会通过 A/B 测试调整 chunk 大小，找到平衡点。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成京东的售后 RAG，我会增加物流状态查询的 API 调用，因为退货和物流强相关。
2. 如果换成抖音电商的直播话术 RAG，我会把切分粒度调到句子级，因为直播话术需要快速响应。
3. 如果换成自研的文档问答，我会用 LangChain 的递归切分器，并加入自定义分隔符。
:::

### 题 15：腾讯 · 混元大模型在长程对话评测中如何设计自动化指标与人工评估？

> 🏢 **真题来源**：腾讯 · 混元大模型 / 对话评测面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对大模型长程对话（多轮、长上下文）的评测体系设计，包括自动化指标和人工评估的结合。
:::

::: tip 💡 参考回答示范
> “我在腾讯混元对话评测项目里负责设计长程对话的评测方案。长程对话通常指 10 轮以上，涉及话题漂移、指代消解、一致性等挑战。自动化指标方面，我用了三类：1）基于规则的指标，如重复率、回复长度分布、指代消解准确率（用 Stanford CoreNLP 工具）；2）基于模型的指标，如用 GPT-4 作为裁判对每轮回复打分（相关性、流畅性、一致性），但要注意裁判模型本身的偏差；3）基于检索的指标，如对话历史中关键信息被正确引用的比例。人工评估方面，我设计了 5 级 Likert 量表，评估维度包括：任务完成度、上下文一致性、信息准确性、自然度。样本是 200 组真实人机对话，每组 15 轮，口径是‘用户有明确任务目标’，严禁编造具体数字。评估时，我会让标注员独立打分，然后计算 Kappa 一致性。风控方面，涉及敏感话题的对话会被过滤，不进入评测集。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果 GPT-4 裁判和人工评估结果差异很大，你信哪个？
  - **续答**：我会先分析差异原因。如果差异集中在某些维度，比如‘一致性’，可能是裁判模型对长上下文的理解有限。我会用人工评估作为金标准，但也会检查裁判模型的 prompt 是否有歧义。同时，我会引入多个裁判模型投票，减少单个模型的偏差。最终，我会以人工评估为准，但用裁判模型做大规模初筛。
- **追问 2**：如何评测长程对话中的‘话题漂移’？
  - **续答**：我会计算相邻轮次之间的语义相似度（用 sentence embedding），如果相似度低于阈值，就标记为潜在漂移。然后人工检查是否合理漂移（用户主动切换话题）还是不合理漂移（模型忘记上下文）。另外，我会统计对话中话题切换的次数和位置，作为辅助指标。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成百度的文心一言，我会增加对中文成语和古诗词的专项评测，因为这是文心的特色。
2. 如果换成字节的豆包，我会侧重评测多模态对话（图文混合）的一致性。
3. 如果换成自研模型，我会用开源的 MT-Bench 和 Chatbot Arena 作为基线对比。
:::

### 题 16：美团 · 外卖场景下大模型 Token 成本如何算账与优化？

> 🏢 **真题来源**：美团 · 外卖 AI 助手 / 成本优化面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对 LLM 推理成本结构的理解，包括 Token 计数、缓存、模型选型和业务量预估。
:::

::: tip 💡 参考回答示范
> “我在美团外卖 AI 助手项目里负责成本优化。外卖场景的典型调用是：用户问‘附近有什么好吃的’，需要结合位置、历史订单、商家信息生成推荐。成本主要来自输入 Token（用户 query + 上下文 + 知识库片段）和输出 Token（推荐理由）。算账时，我首先统计日均调用量、平均输入输出 Token 数。样本是脱敏后的线上日志，口径是‘一次完整推荐请求’，严禁编造具体数字。然后，我做了几项优化：1）上下文压缩，只保留最近 3 轮对话和关键实体（如位置、口味偏好），减少输入 Token；2）知识库检索后，用小型模型（如 7B）做摘要，再喂给大模型，降低输入长度；3）输出限制在 100 Token 以内，用模板化回复减少生成量；4）对非实时请求（如批量推荐）使用更便宜的模型。另外，我引入了缓存：相同 query 和上下文直接返回缓存结果。指标上，我监控单次调用成本和总成本，目标是降低 30%。风控方面，涉及优惠券、价格等信息必须实时查询，不能缓存。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果缓存命中率很低，你怎么提升？
  - **续答**：我会分析缓存未命中的原因。如果是 query 表述多样，我会做 query 归一化，比如把‘有啥好吃的’和‘推荐美食’映射到同一意图。如果是上下文不同，我会尝试只缓存与上下文无关的部分，比如商家信息。另外，我会设置合理的缓存过期时间，比如商家信息缓存 5 分钟，避免过期数据。
- **追问 2**：如何说服业务方接受模型降级带来的效果损失？
  - **续答**：我会做 A/B 测试，量化降级对核心指标（如点击率、下单转化率）的影响。如果影响在可接受范围内（比如小于 1%），而成本降低 30%，我会建议业务方接受。同时，我会提供降级开关，在高峰期或成本敏感时启用。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成滴滴的路径规划助手，我会把知识库换成路况和交通规则，成本优化重点放在实时性要求高的查询上。
2. 如果换成携程的旅行助手，我会增加多轮对话的上下文长度，因为旅行规划更复杂。
3. 如果换成自研的客服机器人，我会用开源的 vLLM 做推理加速，降低单位 Token 成本。
:::

### 题 17：快手 · 可灵 AI 视频生成中如何设计高危写操作的风控机制？

> 🏢 **真题来源**：快手 · 可灵 AI / 多模态生成风控面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对 AIGC 产品中高危操作（如生成违规内容、滥用 API）的风控设计，包括事前、事中、事后策略。

::: tip 💡 参考回答示范
> “我在可灵 AI 视频生成项目里负责内容风控。高危写操作包括：生成暴力、色情、政治敏感内容，以及滥用 API 批量生成。风控分三层：1）事前：用户输入 prompt 时，用文本分类模型实时检测违规词和意图，命中则直接拒绝并提示；同时，对用户进行实名认证和额度限制。2）事中：视频生成过程中，对中间帧进行抽检，用图像分类模型识别违规画面，一旦发现立即终止生成并记录。3）事后：生成完成后，用多模态模型对视频整体审核，违规内容不返回给用户，并触发人工复审。另外，对于 API 调用，我设置了频率限制和并发限制，异常调用会触发验证码或封禁。指标上，我监控违规内容拦截率、误杀率和审核延迟。样本是脱敏后的用户请求日志，口径是‘所有生成请求’，严禁编造具体数字。风控策略会定期更新，对抗新型违规。”

::: warning ⚠️ 连环追问与高分续答

- **追问 2**：如何平衡风控和用户体验？
  - **续答**：我会设置分级策略：对于高风险但不确定的内容，先放行但标记，后续人工复审；对于明确违规的，直接拒绝。同时，我会给用户清晰的反馈，比如‘您的内容可能包含违规信息，请修改’，而不是简单报错。另外，我会定期分析误杀案例，优化模型阈值。

### 题 18：Kimi · 长文本场景下如何设计 RAG 的检索与切分策略？

> 🏢 **真题来源**：Kimi · 长文本 RAG / 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察在超长文本（如论文、合同）场景下，RAG 的切分、索引和检索优化，以及如何利用长上下文模型。
:::

::: tip 💡 参考回答示范
> “我在 Kimi 长文本 RAG 项目里负责文档问答。Kimi 支持 200 万字上下文，但直接全量输入成本高且效果不一定好。我的策略是：1）切分：对于结构化文档（如论文），按章节切分，每个 chunk 保留标题和摘要；对于非结构化文档（如合同），按条款切分，并提取关键实体（如甲方、乙方、金额）。chunk 大小在 500-1000 字，重叠 10%。2）索引：用 Kimi 的 embedding 模型建向量索引，同时建关键词索引。3）检索：用户 query 先经过意图识别，如果是事实型问题，用混合检索召回 Top-5 chunk，然后拼接成上下文喂给 Kimi；如果是总结型问题，则用 Map-Reduce 方式，先分块总结再汇总。指标上，看答案准确率和引用正确率。样本是 100 份真实合同和论文，口径是‘用户问题有明确答案’，严禁编造具体数字。风控方面，涉及法律条款的问答会提示‘仅供参考，不构成法律建议’。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果文档有 1000 页，检索 Top-5 可能不够，你怎么处理？
  - **续答**：我会采用分层检索：先检索章节标题，定位到相关章节，再在章节内检索具体段落。这样可以把范围缩小到几页，再取 Top-5。另外，我会用查询扩展，比如把用户问题拆成多个子问题，分别检索。
- **追问 2**：如何评估 RAG 在长文本上的效果？
  - **续答**：我会构建一个评测集，包含问题和对应的答案出处。然后计算检索的召回率、答案的准确率和引用正确率。同时，我会人工评估回答是否遗漏关键信息。对于长文本，我还会看模型是否能够跨章节整合信息。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成 DeepSeek 的长文本模型，我会利用其更强的推理能力，减少检索依赖，直接输入更长上下文。
2. 如果换成蚂蚁的合同助手，我会增加条款对比和风险提示功能。
3. 如果换成自研的文档问答，我会用 LlamaIndex 的递归检索器。
:::
