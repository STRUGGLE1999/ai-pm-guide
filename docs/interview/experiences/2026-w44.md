### 题 1：字节跳动飞书智能助手：如何设计多轮 Agent 工作流编排以降低任务失败率？

> 🏢 **真题来源**：字节跳动 · 飞书 AI 助手 / Agent 工作流产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对 Agent 工作流编排中状态管理、异常恢复与用户干预机制的设计能力，本质是平衡自动化效率与任务可靠性。
:::

::: tip 💡 参考回答示范
> “我在飞书智能助手项目中负责过会议纪要自动生成与待办分发的 Agent 工作流。当时多轮任务失败率约 18%，主要原因是工具调用超时和上下文丢失。我的做法是：第一，将工作流拆分为原子步骤（如“获取会议录音→转写→摘要→提取待办→分配负责人”），每个步骤定义明确的输入输出 schema 和超时阈值（样本是 200 场会议，口径是端到端成功生成待办且负责人非空）。第二，引入检查点机制，每完成一个步骤持久化中间状态到飞书多维表格，失败时从最近检查点恢复而非重跑全流程。第三，设计用户干预节点：当置信度低于 0.7 时（口径是模型对摘要关键实体抽取的置信分），推送飞书卡片让用户确认或修改，而不是静默失败。第四，对工具调用增加重试与降级策略，例如日历 API 超时则降级为生成待办文本由用户手动添加。上线后失败率降至 6%，用户干预率 12%，但任务完成满意度提升 23 个百分点。指标上我关注端到端成功率、平均恢复时长和用户干预接受率，严禁编造数据，所有口径均与数据团队对齐。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户中途关闭飞书页面，检查点机制如何保证任务继续执行？
  - **续答**：我会把工作流执行引擎放在服务端异步任务队列，与前端会话解耦。用户关闭页面不影响服务端继续执行，完成后通过飞书机器人消息推送结果。检查点存储在服务端数据库，前端仅做状态展示。同时设置任务超时上限（如 30 分钟），超时后标记失败并通知用户。样本是 50 个中途关闭页面的案例，口径是任务最终完成率，实测从 40% 提升到 92%。
- **追问 2**：如何评估 Agent 工作流中每个步骤的贡献度以决定优化优先级？
  - **续答**：我会做步骤级漏斗分析，统计每个步骤的通过率、平均耗时和失败原因分布。样本是 500 条工作流日志，口径是步骤通过率=该步骤成功输出且被下游接受的次数/进入该步骤的总次数。优先优化通过率低于 80% 或耗时占比超过 30% 的步骤。例如转写步骤耗时占 60%，我们就推动切换更快的 ASR 模型，将端到端时延降低 35%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 若换到钉钉场景，可将检查点存储从飞书多维表格改为钉钉宜搭，并利用钉钉工作通知做用户干预。
2. 若任务类型是审批流，需增加权限校验节点，确保 Agent 不越权操作。
3. 若模型能力较弱，可降低自动化阈值，增加人工确认环节，以成功率优先。
:::

### 题 2：阿里巴巴通义千问 RAG 产品：如何设计文档切分策略以平衡召回率与生成质量？

> 🏢 **真题来源**：阿里巴巴 · 通义千问企业知识库 RAG 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对 RAG 中切分粒度、语义完整性与检索效率的权衡能力，本质是让检索片段既包含完整答案又不过度冗余。
:::

::: tip 💡 参考回答示范
> “我在通义千问企业知识库项目中负责文档解析与切分模块。最初用固定 512 token 切分，召回率仅 65%，生成答案常缺上下文。我设计了分层切分策略：第一，按文档结构切分，优先使用标题层级（H1/H2/H3）作为自然边界，样本是 2000 份企业制度文档，口径是切分后片段与人工标注答案的重合度。第二，对超长段落用语义分割模型判断句子边界，避免在句子中间切断，保证每个片段是完整语义单元。第三，设置重叠窗口 10%-15%，防止答案跨片段丢失。第四，为每个片段生成摘要元数据，检索时先用摘要粗筛再用原文精排。上线后召回率提升至 88%，生成答案的忠实度（人工评估）从 72% 提升到 91%。指标上我关注片段召回率、答案忠实度和平均片段长度，所有评估集由标注团队独立构建，严禁编造。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：表格和图片类文档如何切分？
  - **续答**：表格我会整表保留为一个片段，并附加表头描述作为元数据，避免行列被切断。图片则用多模态模型生成文字描述后作为独立片段。样本是 300 份含表格的文档，口径是表格问答准确率，整表保留比按行切分提升 40 个百分点。
- **追问 2**：如何确定重叠窗口的大小？
  - **续答**：我会做 A/B 实验，对比 0%、10%、20% 重叠下的召回率和存储成本。样本是 1000 条问答对，口径是答案完整召回率。实测 10%-15% 重叠在召回率上比 0% 高 12 个百分点，再增大则收益递减且存储成本线性上升，因此定为 12%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 若文档是代码库，切分应以函数或类为边界，而非段落。
2. 若检索延迟敏感，可减少重叠窗口并增加元数据索引以加速粗筛。
3. 若企业文档更新频繁，需设计增量切分与索引更新机制。
:::

### 题 3：腾讯混元大模型长程评测：如何设计多轮对话的自动化评测体系？

> 🏢 **真题来源**：腾讯 · 混元大模型对话产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对长程对话中上下文一致性、任务完成度和安全性的量化评估能力，本质是构建可复现、可解释的评测流水线。
:::

::: tip 💡 参考回答示范
> “我在腾讯混元对话产品中负责长程评测体系设计。传统单轮评测无法反映多轮退化，我设计了三级评测：第一，规则评测，针对事实一致性、格式合规等硬性指标，用正则和结构化解析自动打分，样本是 500 组多轮对话，口径是规则通过率。第二，模型评测，用强模型作为裁判对每轮回复的连贯性、有用性、安全性打分（1-5 分），并计算轮间分数衰减斜率，斜率大于 0.5 视为上下文丢失。第三，人工抽检，每周抽 50 组对话由标注员复核，校准模型裁判的偏差。评测集覆盖任务型（订票、客服）和闲聊型，每组至少 8 轮。上线后我们发现第 5 轮后连贯性平均下降 0.8 分，推动优化了上下文压缩策略，衰减斜率降至 0.2。指标上我关注任务完成率、轮间一致性分数和安全违规率，所有评测集版本化管理，严禁编造。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：模型裁判本身有偏差，如何保证评测可信？
  - **续答**：我会做裁判校准：每月用人工标注的 200 组对话计算模型裁判与人工评分的一致性（Cohen's kappa），低于 0.7 则调整裁判提示词或换模型。同时保留规则评测作为硬约束，模型裁判仅用于软性质量评估。样本是 6 个月数据，口径是 kappa 值，稳定在 0.75 以上。
- **追问 2**：如何评测长程对话中的记忆能力？
  - **续答**：我会在对话第 1 轮植入关键信息（如用户偏好），在第 8 轮提问相关问题时检查是否引用。样本是 300 组对话，口径是记忆召回准确率。实测基线模型仅 55%，优化记忆摘要机制后提升到 82%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 若产品是语音对话，需增加 ASR 错误对评测的影响分析。
2. 若评测成本受限，可减少模型裁判调用，增加规则和抽样人工。
3. 若面向企业客服，评测集需加入业务知识准确性维度。
:::

### 题 4：百度文心一言 Token 成本算账：如何设计分级缓存与路由策略降低推理成本？

> 🏢 **真题来源**：百度 · 文心一言 API 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对 Token 消耗结构、缓存命中率和模型路由的成本优化能力，本质是在保证体验的前提下做单位经济模型优化。
:::

::: tip 💡 参考回答示范
> “我在文心一言 API 产品中负责成本优化。当时月度 Token 成本超预算 30%，我拆解成本结构发现：系统提示词占比 25%，重复问答占比 18%，高成本模型调用占比 40%。我的策略：第一，对系统提示词做前缀缓存，相同前缀只计费一次，样本是 10 万次请求，口径是缓存命中率，上线后命中率 35%，节省 8% 成本。第二，对高频重复问题建立语义缓存，相似度大于 0.95 直接返回缓存答案，样本是 5 万条 query，口径是缓存准确率（人工抽检 200 条），准确率 98%，节省 6% 成本。第三，设计模型路由：简单分类、抽取任务路由到小模型，复杂推理才用大模型，样本是 8 万次请求，口径是路由后质量损失（人工评估），质量损失小于 2%，成本降低 22%。综合后总成本下降 28%，达到预算内。指标上我关注每千 Token 成本、缓存命中率和路由质量损失率，所有数据来自计费日志，严禁编造。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：语义缓存如何避免返回过时答案？
  - **续答**：我会给缓存条目设置 TTL（如 24 小时），并对时效敏感类目（如价格、库存）禁用缓存。同时监控缓存答案的负反馈率，超过 5% 则自动失效。样本是 1 万条缓存命中，口径是负反馈率，实测 2.3%。
- **追问 2**：模型路由的质量损失如何持续监控？
  - **续答**：我会对路由到小模型的请求按 5% 比例抽样，用大模型重新生成并对比，计算一致性分数。样本是每周 500 条，口径是分数低于 4 分的比例，超过 3% 则调整路由规则。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 若产品是 C 端免费产品，需更激进地使用缓存和小模型路由。
2. 若企业客户对质量敏感，可提供“高质量模式”关闭路由。
3. 若模型供应商降价，需重新计算路由收益阈值。
:::

### 题 5：蚂蚁集团智能理赔 Agent：如何设计高危写操作的风控与人工兜底机制？

> 🏢 **真题来源**：蚂蚁集团 · 智能理赔 Agent 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对 Agent 执行资金类、权限类写操作时的风险识别、拦截与人工接管设计，本质是安全与效率的平衡。
:::

::: tip 💡 参考回答示范
> “我在蚂蚁智能理赔 Agent 中负责写操作风控。理赔涉及打款、修改保单等高风险操作，一旦出错损失大。我的设计：第一，操作分级，将写操作分为低危（如生成理赔报告）、中危（如修改联系方式）、高危（如发起打款），高危操作必须人工复核。第二，前置校验规则，对高危操作检查金额阈值（如超过 5000 元强制人工）、收款账户白名单、重复理赔检测，样本是 1 万笔理赔，口径是规则拦截准确率，拦截了 120 笔可疑操作，准确率 95%。第三，人工兜底工作流，Agent 生成操作建议后推送到人工审核队列，审核员可一键通过或驳回，并反馈原因用于模型迭代。第四，全链路审计日志，记录每次写操作的输入、输出和决策依据。上线后高危操作零事故，人工复核率 15%，平均处理时长增加 8 分钟但风险可控。指标上我关注高危操作拦截率、人工复核通过率和事故数，严禁编造。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何避免人工复核成为瓶颈？
  - **续答**：我会对复核任务做优先级排序，金额大、时效紧的优先，并给审核员提供 Agent 生成的决策摘要和证据链，缩短单笔复核时间。样本是 2000 笔复核，口径是平均复核时长，从 12 分钟降至 6 分钟。
- **追问 2**：如果 Agent 误判导致漏拦，如何追溯和改进？
  - **续答**：我会建立误判案例库，每周复盘漏拦案例，分析是规则缺失还是模型误判，并补充规则或调整阈值。样本是 3 个月数据，口径是漏拦率，从 0.5% 降至 0.1%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 若场景是内部报销，金额阈值可降低，复核可改为抽样。
2. 若写操作可逆（如修改草稿），可减少人工复核比例。
3. 若监管要求更严，需增加双人复核机制。
:::

### 题 6：小红书多模态搜索：如何设计图文笔记的召回与排序以提升点击率？

> 🏢 **真题来源**：小红书 · 多模态搜索产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对图文混合内容的理解、多模态特征融合与排序目标的设计能力，本质是让搜索既懂图又懂文。
:::

::: tip 💡 参考回答示范
> “我在小红书多模态搜索项目中负责召回排序策略。用户搜“夏日穿搭”时，纯文本召回会漏掉大量优质图文笔记。我的方案：第一，多模态召回，用图文联合嵌入模型将笔记的封面图、标题、正文映射到同一向量空间，查询也做多模态编码（支持用户上传图片搜索），样本是 100 万篇笔记，口径是召回 Top100 的相关性人工评分。第二，特征融合排序，在排序模型中融合文本相关性、图像质量分（清晰度、构图）、互动率（点赞收藏比）和时效性，样本是 50 万次搜索请求，口径是点击率。第三，针对“图片搜索”场景，增加以图搜图的视觉相似度特征，并做类目过滤防止跨类目误召回。上线后图文搜索点击率提升 18%，长尾 query 的召回覆盖率提升 25%。指标上我关注点击率、召回覆盖率和人工相关性评分，所有 A/B 实验分流均匀，严禁编造。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何评估图像质量分对排序的贡献？
  - **续答**：我会做消融实验，对比去掉图像质量分前后的点击率变化。样本是 10 万次请求，口径是点击率差值，实测去掉后点击率下降 3.2 个百分点，说明有正向贡献。
- **追问 2**：用户上传图片搜索时，如何防止低质或违规图片？
  - **续答**：我会在查询侧接入图像安全审核，拦截违规图片并提示用户。同时用图像质量模型过滤模糊图片，引导用户重新上传。样本是 1 万次图片搜索，口径是违规拦截率，达到 99%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 若平台以视频为主，需增加视频帧采样和时序特征。
2. 若搜索场景是电商，需加入商品属性匹配特征。
3. 若算力受限，可减少多模态召回通道，仅对头部 query 启用。
:::
