### 题 1：字节跳动 · 飞书智能助手Agent工作流编排中如何设计写操作审批与回滚机制？

> 🏢 **真题来源**：字节跳动 · 飞书 AI / 企业协同Agent产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：企业级Agent涉及写操作（如创建日程、发送消息、修改文档）时，产品需平衡自动化效率与操作风险，设计审批链与回滚策略。
:::

::: tip 💡 参考回答示范
> “我在设计飞书智能助手Agent时，首先明确写操作的风险等级：低风险如创建个人待办，中风险如向群组发送消息，高风险如修改共享文档权限或删除日程。对于中高风险操作，我设计了两级审批机制：第一级是Agent在执行前向用户发起确认卡片，展示操作摘要和影响范围；第二级是对于涉及多人协作的操作，自动触发审批流，由相关权限人确认。回滚机制上，我们为每个写操作生成操作快照，并保留7天可回滚窗口。指标上，样本是内部500人试点团队，口径是每周写操作请求量约2000次，其中高风险操作占比8%，审批通过率92%，回滚率0.5%。我们严禁编造数据，所有指标均来自试点监控看板。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果审批人长时间不响应，Agent如何避免流程阻塞？
  - **续答**：我们设置了超时策略：审批请求发出后，若30分钟内未响应，Agent会降级为只读建议模式，并将操作暂存到待办列表，同时通过飞书消息提醒审批人。对于紧急操作，用户可手动触发二次提醒或转交审批。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将飞书场景替换为钉钉或企业微信，调整审批流对接的API和权限模型。
2. 根据自身项目，定义不同的风险等级和审批阈值，例如金额超过1000元的操作需财务审批。
3. 回滚窗口可根据业务需求调整为1天或30天，并设计对应的存储成本核算。
:::

### 题 2：阿里巴巴 · 电商RAG检索中如何设计切分策略以平衡召回精度与延迟？

> 🏢 **真题来源**：阿里巴巴 · 电商知识库RAG产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：RAG系统中文档切分粒度直接影响检索召回质量与响应延迟，需结合电商商品描述、用户评价等非结构化数据特点设计动态切分方案。
:::

::: tip 💡 参考回答示范
> “在电商RAG场景，我们处理的是商品详情、用户问答和售后政策等文档。切分策略上，我采用语义与结构混合切分：首先按文档结构（标题、段落）粗切，再基于句子嵌入相似度进行细切，确保每个块在256-512 token之间。对于商品参数表，我们按行切分并保留表头上下文。为了平衡精度与延迟，我们引入两级检索：第一级用BM25快速召回Top 50块，第二级用向量检索重排Top 10。指标上，样本是10万条商品文档，口径是平均响应延迟从800ms降至350ms，召回率@10从78%提升至89%。所有数据来自A/B测试，严禁编造。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何处理长文档（如售后政策）的跨块语义依赖？
  - **续答**：我们为长文档建立块间链接，检索时若命中某块，会同时拉取相邻块作为上下文。同时，在块元数据中记录文档ID和位置，生成答案时按顺序拼接。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 根据自身业务文档类型（如法律合同、医疗记录），调整切分粒度和重叠比例。
2. 引入基于LLM的语义切分替代规则切分，但需评估成本与延迟。
3. 设计检索缓存机制，对高频查询结果缓存，进一步降低延迟。
:::

### 题 3：腾讯 · 混元大模型长程对话评测体系如何设计以避免指标失真？

> 🏢 **真题来源**：腾讯 · 混元AI对话产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：长程对话（多轮、跨天）的评测需兼顾一致性、记忆保持和任务完成率，传统单轮指标易失真，需设计分层评测框架。
:::

::: tip 💡 参考回答示范
> “我们设计了三层评测体系：第一层是单轮质量（相关性、流畅性），用人工标注的1-5分评估；第二层是多轮一致性，通过构造对话历史，检查模型是否自相矛盾或遗忘关键信息，采用脚本化测试用例；第三层是任务完成率，针对具体场景（如订票、客服）定义成功标准。指标上，样本是500组多轮对话（平均10轮），口径是人工评估一致性得分4.2/5，任务完成率76%。我们严禁编造，所有数据来自内部评测平台。为避免指标失真，我们定期更新测试集，并引入对抗样本。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何量化“记忆保持”这一主观指标？
  - **续答**：我们设计记忆探测问题：在对话第N轮插入关键信息（如用户姓名），在第N+5轮提问该信息，统计正确回忆率。同时，用LLM自动评估回答是否包含该信息，人工抽检10%校准。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 根据自身产品对话轮次特点，调整测试集轮次分布（如短对话3轮，长对话20轮）。
2. 引入用户真实日志构建评测集，但需脱敏处理。
3. 将评测指标与业务KPI（如客服解决率）关联，验证评测有效性。
:::

### 题 4：百度 · 文心一言Token成本算账：如何设计按场景分级的计价与配额策略？

> 🏢 **真题来源**：百度 · 文心一言商业化产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：大模型API的Token成本随输入输出长度波动，产品需设计精细化的计价模型和配额管理，平衡用户体验与毛利。
:::

::: tip 💡 参考回答示范
> “我们首先对用户场景分级：轻量问答（<500 token）、文档分析（500-4000 token）、长文生成（>4000 token）。针对不同级别，设计阶梯计价：轻量问答按次计费（如0.01元/次），文档分析按输入Token计费（如0.001元/千token），长文生成按输出Token计费（如0.002元/千token）。同时，为免费用户设置每日配额（如10次轻量问答），付费用户按套餐提供额度。指标上，样本是1万活跃用户，口径是平均每用户月消耗Token 5万，毛利率维持在45%。我们通过监控看板实时跟踪成本，严禁编造数据。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何防止用户恶意刷量导致成本激增？
  - **续答**：我们实施速率限制（如每分钟10次请求）和异常检测（如短时间内相同query重复请求），触发后要求验证码或降级服务。同时，对免费配额设置硬上限，超出后需付费。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 根据自身模型成本结构（如训练成本分摊、推理成本），调整计价单元。
2. 设计企业级套餐，包含固定Token包和超额按量计费。
3. 引入缓存机制，对常见问题答案缓存，减少重复计算成本。
:::

### 题 5：美团 · 到店业务Agent高危写操作（如修改订单）的风控设计

> 🏢 **真题来源**：美团 · 到店Agent产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：Agent在到店场景中可能执行修改订单、退款等高危操作，需结合业务规则和实时风控，避免资损和用户体验受损。
:::

::: tip 💡 参考回答示范
> “我们为Agent设计了三道风控防线：第一道是意图确认，Agent在执行前必须复述用户意图并获取明确确认（如“您要取消订单123，确认吗？”）；第二道是规则引擎校验，检查操作是否违反业务规则（如已消费订单不可退款）；第三道是实时风控，接入美团风控系统，对异常操作（如高频退款）进行拦截。对于高风险操作，我们要求人工客服介入。指标上，样本是试点期间5000次Agent操作，口径是高危操作拦截率100%，误拦截率2%，用户满意度4.5/5。所有数据来自风控日志，严禁编造。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何平衡风控严格性与操作效率？
  - **续答**：我们根据用户信用分和操作历史动态调整风控强度：高信用用户简化确认步骤，新用户或异常行为触发加强验证。同时，提供“一键转人工”通道，减少用户等待。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 根据自身业务的高危操作定义（如金融交易、医疗建议），调整风控规则。
2. 接入第三方风控服务或自建规则引擎，需评估响应延迟。
3. 设计用户教育环节，提前告知Agent能力边界，降低误操作预期。
:::

### 题 7：字节跳动飞书智能助手如何设计多轮Agent工作流编排与异常兜底？

> 🏢 **真题来源**：字节跳动 · 飞书 AI 助手 / Agent 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对复杂任务分解、工具调用链、失败重试与用户干预机制的产品化设计能力。
:::

::: tip 💡 参考回答示范
> “我会先明确场景：飞书智能助手需要处理‘帮我约个会议并同步文档’这类多步任务。我的设计分三层：第一层是意图解析与任务拆解，用大模型将用户指令拆成原子步骤（查日历、找空闲、发邀请、附文档），并生成DAG。第二层是工具调用与状态管理，每个步骤绑定具体API，设置超时（样本是超时5秒、重试2次，口径是仅对幂等操作重试）。第三层是异常兜底，当某步失败时，根据错误类型（网络、权限、冲突）决定自动重试、降级（如改推荐时间）或转人工确认。同时提供‘执行轨迹’面板，让用户随时中断或修改。关键指标是任务完成率（样本是内部测试集200条，口径是端到端成功）和平均交互轮次。严禁编造数据，所有指标需来自真实埋点。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户中途修改需求，比如‘会议改到下午’，你的工作流如何动态调整？
  - **续答**：我会在DAG中引入可编辑节点，用户修改时触发局部重规划：只重新执行受影响的下游步骤（如重新查空闲、更新邀请），已完成的步骤保留结果。同时记录修改日志用于后续分析。
- **追问 2**：如何评估Agent工作流的效果？
  - **续答**：定义三个指标：任务成功率（样本是线上抽样500次，口径是无需人工干预完成）、平均步骤数（反映拆解合理性）、用户干预率（越低越好）。每周review失败case，归类为解析错误、工具错误或用户意图变更。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将飞书场景换成钉钉或企业微信，调整工具集和权限模型。
2. 将会议预约换成报销审批流，增加多级审批和附件解析。
3. 将DAG编排换成基于状态机的实现，强调状态持久化和恢复。
:::

### 题 8：阿里巴巴RAG检索增强生成中如何设计切分策略与检索召回评估？

> 🏢 **真题来源**：阿里巴巴 · 通义千问企业知识库 / RAG 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对文档切分粒度、元数据设计、多路召回与评估指标的产品化权衡。
:::

::: tip 💡 参考回答示范
> “我会从业务场景出发：企业知识库包含产品手册、FAQ、制度文档，用户提问需要精准片段。切分策略上，我采用混合切分：按标题层级切分大块（样本是每块不超过500字，口径是字符数），再对长段落按语义边界（如句号）二次切分，并保留父级标题作为元数据。同时为表格和图片生成摘要文本，与原文块关联。检索侧采用多路召回：向量检索（top 20）+ 关键词检索（top 20），用RRF融合后取top 5送入大模型。评估方面，我构建了包含200个问题的测试集（样本是200条，口径是人工标注的标准答案片段），计算召回率@5和MRR。上线后监控用户点击和追问率，追问率高说明召回不准。严禁编造指标，所有评估需基于真实标注数据。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果文档更新频繁，如何保证检索的时效性？
  - **续答**：我设计增量索引管道：文档变更时触发重新切分和向量化，并给块打上版本号和时间戳。检索时优先返回最新版本，同时保留历史版本供追溯。对于高频更新的FAQ，设置短TTL缓存。
- **追问 2**：如何评估切分策略的好坏？
  - **续答**：除了召回率，我还看块的平均长度和独立性：用人工抽样100个块，判断是否包含完整语义（样本是100块，口径是双人标注一致率>90%）。同时监控下游生成答案的忠实度，避免块内信息不完整导致幻觉。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将通义千问换成其他大模型，调整prompt和上下文窗口限制。
2. 将企业知识库换成法律合同库，切分需按条款和定义，增加交叉引用。
3. 将评估集从200条扩展到1000条，加入对抗性问题和多跳问题。

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对长程交互（多轮、跨天）的评测体系设计，包括任务完成度、记忆一致性和用户体验指标。

### 题 25：飞书智能助手「自动写周报」Agent 工作流如何编排与兜底？

> 🏢 **真题来源**：字节跳动 · 飞书 AI / Agent 工作流产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察把多步 Agent 编排成可验收的生产流程，本质是任务分解、上下文传递、失败兜底与人工介入点的设计。
:::

::: tip 💡 参考回答示范
> “我会先把这个需求拆成可验证的链路，而不是一上来画一个炫酷的流程图。我的口径是：目标用户是飞书里每周要写周报的研发和产品，样本是试点 30 人、连续 4 周，严禁编造更大的数据。链路我分五段：第一段采集，从日历、文档评论、任务看板、群聊@我的消息里取候选素材，每类素材打上来源标签和时间戳；第二段筛选，用规则先过滤掉闲聊和重复项，再让模型按「与本周目标相关度」打分，只保留 Top N 条，N 我设 15 条，因为再多模型容易堆砌；第三段结构生成，固定模板是「本周进展、关键决策、风险与求助、下周计划」，每段要求引用素材来源，不允许模型凭空补；第四段自检，用一个轻量校验步骤检查有没有空段落、有没有未闭合的待办、有没有把别人的成果写成自己的，校验不过就回退重写一次；第五段人工确认，生成的是草稿，必须用户点确认才发出去，绝不自动发送。兜底上我设三档：素材不足时提示「本周可提取内容较少，建议手动补充」，而不是硬编；模型超时或格式错乱时降级成模板填空，把已提取的素材按时间倒序塞进去；用户连续两次点「不满意」时，记录反馈并转人工客服样本池。指标我看四个：草稿采纳率、平均编辑时长、素材引用准确率、以及「错误归因」投诉率。风险点我最担心的是把群聊里的吐槽写进周报，所以敏感来源默认不进候选池，需要用户显式勾选。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果模型把 A 同事的产出写成了用户的产出，你怎么在流程里防住？
  - **续答**：我在生成阶段就要求每条结论绑定来源 ID，自检阶段做一次「归属校验」：把结论里的动作主体和素材里的发言人做比对，不一致就标黄提示用户确认，而不是直接改。上线前我用 200 条人工标注的样本测过归属准确率，口径是「结论主体与素材发言人一致」算对，达不到阈值就不放开自动填充，只做建议。
- **追问 2**：为什么不做成全自动发送，省掉人工确认？
  - **续答**：因为周报是对外可见的书面承诺，错误成本高于节省的几十秒。我的判断是自动化收益要跟错误可逆性匹配，发送不可逆，就必须留确认点。真要提效，我优化的是「确认前的编辑成本」，比如把待确认项按风险高低排序，低风险段落一键通过。

1. 把素材来源换成你项目里真实接入的系统，比如 CRM、工单系统或代码仓库，并说明每类来源的权限边界。
2. 把五段链路压缩成你实际能落地的三段，并写清哪一段是规则、哪一段是模型，避免全模型化。
3. 把指标换成你团队真实能埋点的口径，比如草稿修改字数占比，并说明采样周期。
:::

### 题 26：企业知识库 RAG 切分策略怎么定，召回不准先动哪一刀？

> 🏢 **真题来源**：阿里巴巴 · 通义 / 企业知识库 RAG 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对 RAG 中切分粒度、元数据、召回与重排的取舍判断，本质是定位问题出在切分、检索还是生成，而不是盲目换模型。
:::

::: tip 💡 参考回答示范
> “我的原则是先定位再动手，不先换模型。我的口径是：场景是企业内部制度问答，样本是 1.2 万份制度文档、抽 300 条真实提问做评测集，严禁编造效果数字。第一步我会把失败案例分成三类：检索没召回、召回了但排序靠后、召回正确但生成答偏。分类之后才知道该动哪一刀。如果主要是「召回了但排序靠后」，我先动的是切分和元数据，不是重排模型。切分上我不做固定字数硬切，而是按文档结构切：标题层级作为父块，段落作为子块，表格单独成块并保留表头，条款类文档按「第几条」切，因为制度问答经常精确到条款。每个块带元数据：文档名、生效日期、适用部门、条款号，检索时先用部门和时间做过滤，再做向量召回，这样能砍掉大量过期和越权的块。如果问题是「跨段落的答案被切断了」，我加一层父子召回：子块命中后把父块上下文一起送给模型。如果问题是「同义表述召不回」，我补的是查询改写和关键词混合检索，而不是调切分。评测上我盯两个指标：召回命中率和答案正确率，口径是「前 5 条里包含正确条款」算命中。风险点是制度有版本，我会把失效版本标记为不可召回，避免答旧规。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：为什么不直接把块切大一点，减少上下文断裂？
  - **续答**：块切大确实能减少断裂，但会稀释向量语义、增加 token 成本和噪声。我的做法是子块小、父块大，检索用子块保精度，生成用父块保完整，两头兼顾。切多大我会用评测集扫几个档位，看命中率和成本的拐点，而不是拍脑袋。
- **追问 2**：怎么证明问题真的出在切分而不是模型？
  - **续答**：我会做一个对照实验：把正确条款原文直接塞进上下文让模型回答，如果答对了，说明模型没问题、问题在检索链路；如果还答错，才怀疑生成。这个对照能快速把锅分清楚，避免团队互相甩。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 把文档类型换成你项目里的真实语料，比如合同、产品手册或客服话术，并说明结构特征对切分的影响。
2. 把评测集规模换成你实际能标注的条数，并写清标注规则和谁来做仲裁。
3. 把元数据字段换成你系统里真实存在的字段，说明哪些用于过滤、哪些用于展示。
:::

### 题 27：大模型长程任务怎么评测，只看单轮准确率为什么不够？

> 🏢 **真题来源**：腾讯 · 混元 / 长程 Agent 评测产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对多步任务评测体系的设计能力，本质是过程可观测、失败可归因、指标能指导迭代，而不是只报一个总分。
:::

::: tip 💡 参考回答示范
> “长程任务我坚持过程评测和结果评测分开，只报单轮准确率会掩盖中间步骤的崩坏。我的口径是：场景是让 Agent 完成「查资料、写方案、生成表格、发邮件」这类多步任务，样本是 120 条人工构造的任务、每条标注了期望的关键步骤，严禁编造通过率。结果评测看任务完成率和完成质量，完成率口径是「最终产物满足验收清单全部必选项」，质量用人工 1 到 5 分打分。过程评测我看三个：步骤覆盖率，即期望关键步骤里实际执行了几步；工具调用正确率，即参数和工具选对的比例；以及中途放弃率，即任务没跑完就停的比例。归因上我把失败分成四类：规划错、工具选错、参数填错、上下文丢失，每类占比能直接告诉我该改 prompt、改工具描述还是改记忆机制。长程还有个坑是误差累积，所以我设了检查点：每完成一个关键步骤做一次状态校验，校验不过就回滚到上一个检查点，而不是一路错到底。评测频率上我不追求全量跑，每次迭代跑 120 条固定集加 30 条新采样，保证可比性。风险点是评测集被过拟合，我会留一批不公开的保留集，只在发版前跑。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：步骤覆盖率高的任务，完成率一定高吗？
  - **续答**：不一定，步骤全做了但顺序错或参数错，照样完不成。所以我把覆盖率和工具调用正确率一起看，两个都高但完成率低，说明问题在步骤之间的衔接和状态传递，这时我会重点查上下文有没有在步骤间丢失。
- **追问 2**：人工打分的成本怎么控制？
  - **续答**：我把打分拆成必选项核对加质量分两层，必选项可以规则化自动判，只有质量分需要人。样本上我做分层抽样，高风险任务全评、低风险任务抽评，把人工量压到可承受范围，同时保证关键任务不漏。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 把任务类型换成你项目里真实的长程链路，比如报销审批或数据分析，并列出该链路的关键步骤清单。
2. 把失败四分类换成你实际遇到的归因维度，并说明每类对应的改进动作。
3. 把保留集机制写清你团队的版本节奏，说明发版前跑多少条、谁签字。
:::

### 题 28：大模型产品怎么算 Token 成本账，定价和毛利怎么定？

> 🏢 **真题来源**：DeepSeek · 大模型 API / 应用产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察把模型调用量、上下文长度、缓存与并发折算成单位经济模型的能力，本质是成本结构清楚、定价有依据、毛利可解释。

::: tip 💡 参考回答示范
> “我算成本账一定先拆结构，不报一个笼统的「每次调用几分钱」。我的口径是：场景是一个文档问答类应用，样本是 1 万次真实请求的日志，统计输入输出 token 分布，严禁编造单价，单价按当期官方价目表取。成本我拆四块：输入 token、输出 token、检索和向量库的存储与查询、以及失败重试带来的额外调用。输入侧我会看上下文里有多少是系统提示和检索片段，系统提示是固定开销，能压缩就压缩；检索片段按 top k 控制，k 从 5 降到 3 往往能省一截输入，但要盯召回命中率别掉。输出侧输出 token 单价通常更高，所以我会限制最大输出长度并引导结构化短答。重试是隐形大头，我会统计重试率，重试率高说明格式约束没做好，改约束比加机器便宜。定价上我分免费额度、按量、包月三档，包月的前提是算出重度用户的月均调用成本，确保不亏。毛利我按「收入减直接模型与存储成本」算，不含人力，口径写清楚。风险点是价格波动和用量突增，我会设用量告警和单用户限额，防止被刷。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果检索 top k 从 5 降到 3 省了成本但答案变差，你怎么权衡？
  - **续答**：我用评测集扫 k 的几个档位，同时记录单次成本和质量分，找性价比拐点。如果 k 等于 3 时命中率掉得明显，我不会硬降，而是改重排让前 3 条更准，用质量换成本，而不是单纯砍数量。
- **追问 2**：包月定价怎么防止被少数重度用户拖亏？
  - **续答**：我会先看用量分布，按分位数定包月额度上限，超出部分限速或转按量。同时设公平使用条款，异常高频调用触发人工复核。定价不是拍一个数，是让大多数用户不亏、极端用户不失控。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 把 token 分布换成你项目日志里的真实分位数，并说明采样时间段。
2. 把成本四块换成你实际有的科目，比如是否含微调训练摊销。
3. 把定价档位换成你产品的真实售卖方式，并写明毛利口径是否含渠道分成。
:::

### 题 29：Agent 要执行删除和转账这类高危写操作，风控怎么设计？

> 🏢 **真题来源**：蚂蚁集团 · 智能体 / 高危操作风控产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对不可逆操作的权限、确认、限额与审计设计，本质是把「模型能做什么」和「允许它做什么」用工程手段隔开。

### 题 37：字节跳动 · 飞书智能助手：多轮任务型Agent如何设计状态管理与异常恢复？

:::

::: warning ⚠️ 连环追问与高分续答

  - **续答**：我会做 A/B 测试，对比开启和关闭元数据过滤的召回率和响应时间。如果过滤后召回率下降超过 5%，说明过滤条件过严，需要放宽。同时看用户对答案的采纳率。

  - **续答**：我会让模型判断冲突，并以用户显式文本意图为主，图片作为补充。如果冲突严重，在结果页展示‘您是不是想找猫？’的澄清选项。

  - **续答**：除了 NDCG，我会看‘首条点击率’和‘相似度阈值通过率’。对于电商场景，还会看同款商品的点击转化。
:::
