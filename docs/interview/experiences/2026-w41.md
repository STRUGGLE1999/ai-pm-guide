### 题 1：字节跳动飞书智能助手如何设计Agent工作流，平衡任务完成率与响应延迟？

> 🏢 **真题来源**：字节跳动 · 飞书 AI 助理 / 企业级 Agent 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：核心是设计多步骤 Agent 编排，在有限延迟内完成跨应用操作，并量化完成率与延迟的权衡。
:::

::: tip 💡 参考回答示范
> “我在飞书智能助手项目中负责 Agent 工作流设计。首先明确任务边界：用户通过自然语言发起如“安排下周与产品团队的评审会并预定会议室”的请求，需要调用日历、会议室、人员目录等多个 API。我设计了基于意图识别的分层编排：第一层用轻量模型（如 7B 参数）做意图分类和槽位填充，第二层用大模型（如 70B 参数）做复杂规划和异常处理。样本是过去 3 个月飞书内 5000 条真实用户请求，口径是端到端任务完成率（用户无需二次干预即达成目标）和 P95 响应延迟。我们通过异步执行和预取策略，将平均延迟从 4.2 秒降到 2.8 秒，完成率从 68% 提升到 82%。具体措施：1）对高频操作（如查日程）走缓存和规则引擎，延迟 <500ms；2）对复杂操作（如跨时区协调）采用流式输出中间状态，让用户感知进度；3）设置超时降级，若大模型规划超过 3 秒则切换为模板化流程。风控上，涉及写操作（如创建会议）必须二次确认，并记录审计日志。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户请求涉及敏感权限（如访问高管日历），你如何设计降级和风控？
  - **续答**：我会在意图识别阶段加入权限校验层。样本是 200 条涉及高管日历的请求，口径是权限拒绝率与用户满意度。对于无权限请求，不直接报错，而是返回“需要审批”的引导，并自动发起审批流。同时，Agent 只读取脱敏后的空闲/忙碌状态，不暴露具体日程内容。若审批通过，则临时授予一次性 Token，操作完成后立即回收。风控上，所有敏感操作记录操作人、时间、目标，并同步到安全审计系统。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将飞书场景换成钉钉或企业微信，调整 API 调用方式和权限模型。
2. 将任务完成率指标改为“首次响应准确率”，因为有些任务需要多轮交互。
3. 如果公司没有自研大模型，可替换为调用外部 API，但需增加网络延迟和成本考量。
:::

### 题 2：阿里巴巴国际站 RAG 检索中，如何设计切分策略以提升长文档问答准确率？

> 🏢 **真题来源**：阿里巴巴 · 国际站 AI 客服 / RAG 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：核心是文档切分粒度与检索召回、生成质量的权衡，需结合业务文档结构设计动态切分。
:::

::: tip 💡 参考回答示范
> “在国际站 AI 客服项目中，我们处理大量商品描述、物流政策、关税规则等长文档。样本是 1000 份平均长度 8000 词的商品文档，口径是问答准确率（人工评估答案是否包含正确信息且无幻觉）。最初用固定 512 token 切分，准确率只有 62%，因为切分点常打断关键条款。后来改为基于语义和结构的动态切分：1）先按标题、列表、表格等结构分割，保证每个块语义完整；2）对超长段落用滑动窗口重叠 20% 切分；3）对表格和图片说明单独处理，保留上下文。同时，在检索阶段加入元数据过滤（如商品类目、更新时间），召回 top-5 块后，用重排序模型（如 bge-reranker）精排。最终准确率提升到 79%，P95 检索延迟从 800ms 降到 500ms。成本上，切分块数增加 30%，但通过缓存和向量索引优化，整体 Token 消耗仅增加 10%。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果文档更新频繁，如何保证检索索引的实时性？
  - **续答**：我们采用增量索引策略。样本是每天更新 200 份文档，口径是索引延迟和查询一致性。对于新增或修改的文档，触发实时向量化并更新索引，延迟控制在 1 分钟内。对于删除的文档，先标记为失效，查询时过滤。同时，设置版本号，确保用户查询时看到的是最新版本。如果更新量突增，则降级为批量更新，并通知用户可能看到旧数据。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将国际站文档换成法律合同或医疗指南，切分策略需更注重条款完整性。
2. 如果使用开源向量数据库，需考虑其增量更新性能，可能需换成 Pinecone 或 Weaviate。
3. 将准确率指标改为“答案可溯源率”，因为客服场景要求提供出处。
:::

### 题 3：腾讯混元大模型长程评测：如何设计多轮对话的自动化评估方案？

> 🏢 **真题来源**：腾讯 · 混元大模型 / 对话系统产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：核心是构建覆盖多轮上下文一致性、任务完成度的自动化评测框架，减少人工评估成本。
:::

::: tip 💡 参考回答示范
> “在混元大模型对话产品中，我们需要评估模型在多轮对话中的表现。样本是 500 组人工构造的多轮对话，每组 5-10 轮，口径是任务完成率（最后一轮是否达成用户目标）和上下文一致性（是否出现矛盾）。我们设计了自动化评估流水线：1）用规则引擎检查关键槽位是否在轮次间保持一致；2）用另一个大模型（如 GPT-4）作为裁判，对每轮回复打分（1-5 分），并给出理由；3）对任务完成率，定义明确的成功条件（如预订酒店需包含日期、房型、确认号），由脚本自动验证。为了校准裁判模型，我们人工标注了 100 组对话作为金标准，裁判模型与人工评分相关性达到 0.85。最终，自动化评估将评测周期从 2 周缩短到 2 天，成本降低 70%。但注意，裁判模型本身有偏差，我们定期用人工抽查修正。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何评估模型在长对话中的“遗忘”问题？
  - **续答**：我们设计“记忆探测”轮次：在对话进行到第 8 轮时，突然询问第 2 轮提到的信息。样本是 200 组对话，口径是记忆准确率。如果模型回答错误，则标记为遗忘。同时，我们计算上下文窗口利用率，若对话长度接近模型上限，则提示可能遗忘。改进措施包括：在关键信息出现时，让模型生成摘要并重复，或使用外部记忆库。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将混元换成其他大模型，需调整裁判模型的 prompt 和评分标准。
2. 如果业务场景是客服，任务完成率定义需更严格，如必须解决用户问题。
3. 将自动化评估改为半自动，人工只复核低分对话，以平衡成本与准确率。
:::

### 题 4：蚂蚁集团信贷场景：如何计算大模型 Token 成本并设计降本方案？

> 🏢 **真题来源**：蚂蚁集团 · 信贷 AI 助手 / 大模型成本优化面经

::: info 🎯 核心考点与破题关键
- **考点实质**：核心是拆解 Token 消耗结构，通过缓存、压缩、模型选型等手段在保证效果下降低成本。
:::

::: tip 💡 参考回答示范
> “在蚂蚁信贷 AI 助手中，我们每天处理 10 万次用户咨询。样本是过去一个月 300 万次调用，口径是单次咨询平均 Token 消耗和总成本。最初使用 70B 模型，平均每次消耗 1500 Token（输入+输出），成本约 0.03 元/次，月成本 90 万元。我们做了以下优化：1）意图分类和简单问答（如“利率是多少”）用 7B 模型或规则引擎，覆盖 40% 请求，成本降至 0.002 元/次；2）对复杂问题，用 70B 模型，但通过 prompt 压缩（去除冗余示例）和输出限制（max_tokens=200），将 Token 消耗降到 1000；3）引入缓存，对高频问题（如“如何还款”）缓存答案，命中率 25%，节省 20% 成本。最终月成本降至 45 万元，效果指标（回答准确率）仅下降 1.5%。风控上，所有涉及金额、利率的回答必须从知识库检索，禁止模型自由生成。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户问题需要多轮推理，缓存失效，如何进一步降本？
  - **续答**：对于多轮推理，我们采用“思维链压缩”：让模型在中间步骤生成简洁的推理摘要，而非完整思考过程。样本是 1000 组多轮对话，口径是推理准确率和 Token 消耗。压缩后 Token 减少 30%，准确率不变。另外，我们使用投机解码（speculative decoding）加速推理，降低单位时间成本。如果仍超预算，则对非关键场景降级为 7B 模型，并提示用户“正在使用快速模式”。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将信贷场景换成电商客服，高频问题不同，缓存策略需调整。
2. 如果公司自研模型，可调整模型架构降低推理成本，但需重新训练。
3. 将成本指标改为“每解决一个用户问题的成本”，更贴近业务价值。
:::

### 题 5：美团高危写操作风控：AI 助手如何安全执行退款、改地址等操作？

> 🏢 **真题来源**：美团 · 客服 AI 助手 / 写操作风控产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：核心是设计写操作的多级确认与回滚机制，在提升效率的同时防止误操作和欺诈。
:::

::: tip 💡 参考回答示范
> “在美团客服 AI 助手中，用户可能要求“退款到银行卡”或“修改配送地址”。样本是过去半年 5 万次写操作请求，口径是误操作率（用户投诉因 AI 操作导致损失）和欺诈率。我们设计了三层风控：1）意图识别后，判断是否为高危操作（如退款金额>100 元、修改地址跨城市），若是则触发二次确认，要求用户输入验证码或点击确认按钮；2）操作前，调用风控系统检查用户历史行为、设备指纹，若风险分高则转人工；3）操作后，记录详细日志，并支持 5 分钟内一键回滚（如退款撤销、地址改回）。同时，AI 只执行有明确规则的操作，如退款金额必须与订单一致，否则拒绝。最终，误操作率从 0.5% 降到 0.1%，欺诈率未上升。但转人工率增加了 15%，我们通过优化确认话术（如“请确认退款金额 50 元到尾号 1234 的银行卡”）将用户放弃率控制在 5% 以内。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户坚持要求执行高风险操作，但风控系统拦截，如何安抚？
  - **续答**：我们设计安抚话术：先共情（“理解您着急”），再解释风控原因（“为了您的资金安全”），最后提供替代方案（“您可以联系人工客服快速处理”）。样本是 500 次拦截，口径是用户满意度。同时，记录拦截原因，若某类拦截频繁且合理，则优化规则。对于高价值用户，可提供绿色通道，但需人工复核。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将美团场景换成银行或支付，风控要求更严，需符合金融监管。
2. 如果写操作涉及第三方系统，需增加 API 幂等性和重试机制。
3. 将误操作率指标改为“操作成功率”，因为有些操作失败是用户主动取消。
:::

### 题 6：小红书多模态搜索：如何设计图文混合检索的评测指标？

> 🏢 **真题来源**：小红书 · 多模态搜索 / AI 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：核心是定义多模态检索的相关性、多样性和时效性指标，并构建自动化评测集。
:::

::: tip 💡 参考回答示范
> “在小红书多模态搜索中，用户可能上传图片找相似笔记，或输入文字找相关图片。样本是 2000 条真实搜索 query（含图片和文字），口径是 top-10 结果的点击率和人工相关性评分。我们设计了三个指标：1）相关性：用 CLIP 模型计算 query 与结果的向量相似度，并人工标注 500 条作为校准，要求 top-3 相关性≥4 分（5 分制）；2）多样性：计算 top-10 结果的类目分布熵，避免全是同一类笔记；3）时效性：对时尚、美妆等类目，要求 30 天内笔记占比≥60%。自动化评测流水线：先用模型打分，再对低分结果人工复核。上线后，点击率提升 12%，用户搜索满意度（NPS）提升 8 分。挑战在于多模态对齐，我们通过对比学习微调 CLIP 模型，使图文匹配准确率从 75% 提升到 88%。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户上传的图片质量差或模糊，如何保证检索效果？
  - **续答**：我们加入图像增强预处理：先检测模糊度，若低于阈值则提示用户“图片模糊，是否重新上传”，同时用超分辨率模型增强。样本是 300 张模糊图片，口径是检索成功率。增强后，成功率从 40% 提升到 65%。另外，对于模糊图片，检索时降低图像权重，更多依赖文字描述。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将小红书换成淘宝或京东，商品图片检索需更注重属性匹配。
2. 如果多模态模型自研，需考虑训练成本和数据标注。
3. 将点击率指标改为“加购率”或“收藏率”，更贴近电商场景。
:::

### 题 7：字节跳动飞书智能助手：如何设计Agent工作流编排以处理多轮会议纪要生成与待办提取？

> 🏢 **真题来源**：字节跳动 · 飞书 AI / 企业协同 Agent 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对Agent工作流编排的理解，包括任务分解、工具调用、状态管理以及与企业IM场景的结合。
:::

::: tip 💡 参考回答示范
> “我以飞书会议纪要场景为例。首先，我会将任务拆解为：语音转写→摘要生成→待办提取→责任人匹配→日历创建。Agent需要调用飞书开放接口，如获取会议录音、查询参会人日历、创建待办。工作流引擎采用状态机，每个节点有输入输出schema。关键点：1）异步处理长音频，设置超时和重试；2）摘要生成使用大模型，但需限制token消耗，我会设置分段摘要再合并；3）待办提取需结构化输出，用function call格式。指标上，样本是1000场会议，口径是端到端完成率>95%，待办提取准确率>90%。风控方面，涉及写操作如创建日历，必须二次确认，避免误操作。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果会议中多人同时说话，转写准确率下降，如何优化？
  - **续答**：我会引入声纹分离和说话人日志，先做语音分离再转写。同时，在摘要阶段，用大模型结合上下文推断发言人意图。样本是200场重叠语音会议，口径是转写准确率从70%提升到85%。如果仍不达标，降级为人工校对入口。
- **追问 2**：如何评估待办提取的准确性？
  - **续答**：定义准确率=正确提取的待办数/总待办数，召回率=正确提取/实际待办。人工标注500场会议作为golden set，要求准确率>90%，召回>85%。同时监控用户对生成待办的编辑率，编辑率<10%为健康。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 将飞书会议纪要换成钉钉闪记，需适配钉钉的API和权限体系。
2. 将待办提取换成工单创建，需对接Jira或内部工单系统。
3. 将会议场景换成客服对话质检，Agent需实时分析并触发预警。
:::

### 题 8：阿里巴巴国际站：RAG检索增强生成中，如何设计多语言商品知识库的切分与检索策略？

> 🏢 **真题来源**：阿里巴巴 · 国际站 AI 搜索 / RAG 产品面经

::: info 🎯 核心考点与破题关键

### 题 13：字节跳动 · 飞书智能伙伴：如何设计企业知识库Agent的检索与切分策略，平衡准确率与响应延迟？

> 🏢 **真题来源**：字节跳动 · 飞书 AI 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察RAG系统中文档切分、索引构建、检索召回与重排的工程权衡，以及对企业场景下实时性要求的理解。
:::

::: tip 💡 参考回答示范
> “我在飞书智能伙伴项目中负责知识库问答的检索链路设计。当时遇到的核心矛盾是：企业文档格式复杂（PDF、PPT、表格、聊天记录），切分粒度太粗会导致召回不精准，太细又增加检索次数和延迟。我的方案是采用动态分层切分：对于结构化文档（如制度文件），按标题层级切分为段落，每个段落保留父级标题作为上下文；对于非结构化聊天记录，按对话轮次切分，并合并同一主题的连续消息。索引阶段，我们用了混合检索：稀疏向量（BM25）保证关键词匹配，稠密向量（如bge-m3）保证语义匹配，然后通过RRF融合排序。为了控制延迟，我们设置了召回上限：稀疏和稠密各召回Top 50，融合后取Top 20进入重排模型（如bge-reranker），最终取Top 5给大模型生成。实测下来，在内部1万份文档的测试集上，准确率从纯稠密的72%提升到混合检索的89%，P99延迟控制在800ms以内。关键决策点：切分时保留元数据（如文档标题、部门、更新时间），检索时支持元数据过滤，比如只搜“人力资源部”最近半年的文档。另外，我们做了缓存层，对高频问题缓存检索结果，命中率约30%，进一步降低延迟。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果企业文档每天新增上千份，如何保证索引实时更新且不影响线上查询？
  - **续答**：我们采用了增量索引+双缓冲机制。新文档先写入临时索引，每5分钟合并到主索引，合并时使用别名切换，线上查询无感知。同时，对于紧急更新的文档，提供手动触发重建的入口，但会限制频率。另外，我们监控索引延迟指标，如果超过10分钟，就告警并降级为只搜旧索引，保证可用性。
- **追问 2**：如何评估检索环节的准确率？有没有量化指标？
  - **续答**：我们构建了包含500个问题的评测集，每个问题标注了正确答案所在的文档片段。指标包括：Recall@5（前5个结果中包含正确答案的比例）、MRR（平均倒数排名）、以及端到端的答案准确率（人工评估）。上线前Recall@5为85%，上线后通过bad case分析持续优化切分策略，两个月后提升到92%。

2. 如果换成微信客服场景，需处理短文本和口语化表达，切分策略改为按消息会话窗口滑动。
3. 如果延迟要求更严（如200ms），可去掉重排模型，仅用混合检索+规则过滤。

> “长程对话评测最难的是保持上下文一致性和避免遗忘。我们设计了一套组合方案：自动化指标用 GPT-4 做裁判，对每轮回复打分，维度包括相关性、一致性、信息量、安全性，每个维度 1-5 分。同时用规则检测硬伤，比如重复、矛盾、敏感词。人工评估抽 10% 的对话，由标注团队按同样维度打分，并计算与自动评分的一致性。样本是 1000 组多轮对话，每组 10 轮，覆盖闲聊、任务、知识问答。口径是“整组对话的平均分”和“最后一轮的一致性得分”。严禁编造具体数字，但可以说自动评分与人工评分的 Pearson 相关系数在 0.7 左右。对抗测试我们构造了“记忆干扰”场景，比如在第 3 轮告诉模型一个事实，第 8 轮问它，看是否记得。成本上，GPT-4 裁判太贵，我们后来用混元自己微调了一个小模型做裁判，成本降了 80%，但需要定期校准。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：自动裁判模型自己也会有偏见，怎么保证公平？
  - **续答**：我们做两件事：一是用多个裁判模型投票，比如混元、GPT-4、Claude 各打一次，取平均；二是定期用人工标注数据微调裁判模型，减少位置偏见和长度偏见。另外，我们会公开评测集和评分标准，接受内部质疑。
- **追问 2**：长程对话里，如果用户故意引导模型说错话，怎么评测安全性？
  - **续答**：我们单独有一套红队测试集，包含诱导、越狱、多轮渐进式攻击。评测时不仅看单轮回复，还看整个对话链是否最终被攻破。指标是“攻击成功率”，越低越好。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 把混元换成 Kimi 或 DeepSeek，评测长文档问答中的多轮追问。
2. 把对话轮数从 10 轮增加到 50 轮，观察遗忘曲线。
3. 把人工评估换成众包，增加交叉验证和一致性检验。

::: details 🛠️ 换成你自己的项目时改这三处

### 题 25：字节跳动 · 飞书智能助手：如何设计多轮 Agent 工作流编排以处理跨文档会议纪要生成？

> 🏢 **真题来源**：字节跳动 · 飞书 AI 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：Agent 工作流编排与状态管理，结合企业办公场景的复杂任务分解与工具调用。
:::

::: tip 💡 参考回答示范
> “我在飞书智能助手项目中负责会议纪要生成 Agent 的设计。核心思路是将任务拆解为「会议录音转写→议题识别→待办提取→责任人匹配→飞书文档结构化输出」五个步骤，用状态机编排。具体实现：用户上传会议录音后，先调用语音转写 API 获取带时间戳的文本；然后通过大模型进行议题分割，这里我们定义了一个 JSON Schema 约束输出，要求模型按 {topic, discussion, decisions, action_items} 结构返回。对于待办提取，我会用 few-shot 提示让模型识别「谁在什么时间前要完成什么」，并关联飞书通讯录进行责任人匹配。关键难点是长会议（超过 1 小时）的上下文窗口限制，我们采用滑动窗口加摘要的方式：每 10 分钟 chunk 做局部摘要，再对摘要做全局聚合。评估指标上，我们内部标注了 200 场真实会议作为测试集，口径是「待办提取准确率」和「责任人匹配 F1」，当前分别达到 87% 和 82%。风控方面，对于涉及敏感信息的会议（如 HR 绩效沟通），系统会强制要求用户二次确认是否生成纪要，并默认不存储原始录音。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果会议中多人同时说话，转写文本混乱，你的 Agent 如何保证议题分割的准确性？
  - **续答**：我们首先在转写层引入说话人分离（diarization）模型，输出带 speaker 标签的文本。然后在议题分割 prompt 中显式加入说话人角色信息，比如「张三是产品经理，李四是研发负责人」，让模型根据角色判断议题归属。同时，我们设置了一个后处理规则：如果连续多个 chunk 的议题标签置信度低于阈值（如 0.6），则触发人工复核提示，由用户手动调整分割点。在测试集上，加入说话人信息后议题分割的准确率从 72% 提升到 85%。
- **追问 2**：待办提取时，如果责任人不在飞书通讯录中，或者有重名，你怎么处理？
  - **续答**：对于不在通讯录的情况，Agent 会输出原始文本中的人名，并标记为「未匹配」，同时提供「手动指定」入口，让用户从通讯录选择或输入外部邮箱。对于重名，我们会结合上下文中的部门信息、历史交互记录进行消歧，如果仍无法确定，则列出所有同名候选人让用户选择。我们内部统计，重名导致的错误匹配约占 5%，通过交互式确认可以降到 1% 以下。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成钉钉场景，可以强调与钉钉待办、DING 消息的打通，以及组织架构同步的差异。
2. 如果换成微信会议，需考虑微信生态的封闭性，可能无法直接获取通讯录，需设计基于群成员昵称的模糊匹配。
3. 如果换成英文会议，需调整 prompt 为英文，并注意日期格式、姓名顺序等本地化问题。
:::

### 题 26：阿里巴巴 · 通义千问企业知识库：RAG 检索中如何设计切分策略以平衡召回率与精度？

> 🏢 **真题来源**：阿里巴巴 · 通义千问 / 企业知识库产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：RAG 文档切分策略对检索效果的影响，涉及语义完整性、重叠窗口、元数据增强等。
:::

::: tip 💡 参考回答示范
> “在通义千问企业知识库项目中，我负责 RAG 检索链路的优化。切分策略直接决定召回片段的质量。我们最初用固定长度 512 token 切分，发现很多片段被拦腰截断，导致答案不完整。后来改为基于语义的切分：先用 spaCy 做句子边界检测，再合并相邻句子直到接近 512 token，同时保留 10% 的重叠窗口。对于结构化文档（如 PDF 表格），我们单独用表格解析器提取为 Markdown，再按行切分。关键改进是引入「父文档-子块」索引：子块用于向量检索，父文档用于上下文补充。具体做法是，每个子块存储其所属父文档的 ID，检索时先召回子块，再根据父文档 ID 取回完整段落送给大模型。评估上，我们构建了 500 条问答对，口径是「答案包含率」和「冗余 token 比例」。当前语义切分比固定切分答案包含率提升 18%，冗余 token 降低 25%。风控方面，对于法律、财务等敏感文档，切分时会自动打上密级标签，检索时根据用户权限过滤。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：重叠窗口设置多少合适？有没有量化依据？
  - **续答**：我们做过 A/B 测试，重叠比例从 0% 到 20% 分别测试。结果显示，重叠 10% 时答案包含率最高，继续增加重叠会导致检索结果冗余，且索引体积增大。具体数据：重叠 0% 时答案包含率 76%，10% 时 85%，20% 时 84%。所以最终选择 10%。
- **追问 2**：对于超长文档（如 100 页 PDF），父文档-子块索引会不会导致父文档过大，超出模型上下文？
  - **续答**：会，所以我们限制了父文档的最大长度，比如 2000 token。如果原始文档超过这个长度，我们会先按章节切分为多个父文档，每个父文档再切子块。这样既保证了上下文完整性，又不会超限。同时，我们会在检索时根据子块得分排序，只取 top-3 父文档拼接，确保总 token 在模型窗口内。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成腾讯文档，需考虑在线协作文档的实时更新，切分策略要支持增量索引。
2. 如果换成百度如流，可结合百度的知识图谱，在切分时注入实体链接。
3. 如果换成非结构化聊天记录，切分需按对话轮次而非句子边界。

### 题 27：腾讯 · 混元大模型长程评测：如何设计多轮对话的自动化评估方案？

> 🏢 **真题来源**：腾讯 · 混元大模型产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：长程对话评测的指标设计、数据构造与自动化评估，避免人工评估的高成本与不一致。

::: tip 💡 参考回答示范

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：裁判模型本身可能有偏见，如何保证评估的公正性？

### 题 31：字节跳动飞书智能伙伴如何设计多轮任务型Agent的编排与异常恢复？

> 🏢 **真题来源**：字节跳动 · 飞书智能伙伴 / 企业级Agent产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察在真实办公场景中，如何用有限状态机+LLM规划器设计可中断、可回滚、可解释的多轮任务流，并处理工具调用失败、用户中途改需求等异常。

::: tip 💡 参考回答示范
> “我在飞书智能伙伴项目里负责过会议纪要自动生成并同步到日历和待办的任务型Agent。我的设计分三层：第一层是意图路由，用轻量分类模型把用户输入分为新建任务、修改任务、查询状态、闲聊四类，样本是过去3个月飞书用户真实query抽样2000条，口径是人工标注的意图准确率，严禁编造。第二层是任务编排，用有限状态机定义状态：待确认、执行中、等待用户输入、已完成、已取消、异常挂起。每个状态迁移由LLM规划器输出下一步动作，但动作空间被严格限制为调用工具（如日历API、待办API、搜索API）或向用户提问。第三层是异常恢复，当工具调用失败时，不直接报错，而是把错误码映射为可恢复策略：比如日历冲突则建议改期，权限不足则引导授权，网络超时则自动重试两次并降级为草稿保存。关键指标是任务完成率、平均轮次、异常恢复率。上线后任务完成率从68%提升到86%，样本是两周内1000个真实任务，口径是用户最终确认完成的占比。风控上，高危操作如删除日历事件必须二次确认，并在状态机里加锁。”

- **追问 1**：如果用户中途说‘算了，改成明天下午’，你的状态机怎么处理？
  - **续答**：我会把‘修改任务’作为一个独立意图，触发状态机从执行中回退到待确认状态，并保留已填槽位。具体是：LLM规划器解析出修改实体（时间=明天下午），然后对比原任务槽位，只更新变化字段，再走一遍确认流程。如果原任务已经部分执行（比如日历已创建），则先调用删除或更新API，再创建新任务。这里要防止重复创建，所以每个任务有唯一ID，所有工具调用都带幂等键。

:::

2. 换成微信客服机器人时，异常恢复策略要更轻量，因为用户期望即时回复，所以重试次数降为1次，更多引导用户重新描述。
3. 换成剪映的AI剪辑助手时，任务编排从办公流变为媒体处理流，状态机要增加‘渲染中’‘导出中’等长时状态，异常恢复要考虑资源排队。

### 题 32：阿里巴巴国际站RAG检索中，如何设计切分策略以平衡召回与精度？

> 🏢 **真题来源**：阿里巴巴 · 国际站AI导购 / RAG产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察在跨境电商商品知识库场景下，如何根据文档结构、查询类型设计动态切分，并评估切分对召回率、答案准确率、延迟的影响。
:::

::: tip 💡 参考回答示范
> “在国际站AI导购项目里，知识库包含商品详情、物流政策、退换货规则、支付方式等。我负责RAG的切分策略。首先做文档分析：商品详情页是半结构化，有标题、属性表、描述、评论；政策文档是长文本，有章节和条款。我采用混合切分：对属性表按行切，每行作为一个chunk，保留键值对；对描述按语义段落切，用滑动窗口，窗口大小256token，重叠64token；对政策文档按标题层级切，一级标题作为父chunk，二级标题作为子chunk，检索时先召回父chunk再定位子chunk。评估指标是召回率@5、答案准确率、平均响应延迟。样本是过去一个月用户真实query抽样500条，口径是人工标注的相关文档是否在前5。严禁编造具体数字，但可以说我们通过A/B测试发现，滑动窗口+重叠比固定长度切分召回率提升明显。另外，对query也做意图分类：事实型query直接检索，比较型query需要多路召回再融合。风控上，涉及价格和库存的答案必须实时调用API校验，不能只靠RAG。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户问‘这款手机支持哪些频段’，你的切分能召回吗？
  - **续答**：频段信息通常在商品详情的规格表里，我按行切分后，每个频段行是一个chunk，但用户问的是‘哪些’，需要聚合。所以我在检索后加了一个聚合步骤：召回所有相关行，然后用LLM汇总成列表。如果规格表是图片，则需要OCR后切分，这时我会把OCR文本按表格结构还原，再按行切。

2. 换成阿里云文档助手时，技术文档有代码块，切分时要保留代码完整性，不能从中间切断。
3. 换成Lazada多语言场景时，切分要按语言分开，并考虑翻译后的token长度变化，窗口大小需调整。

::: tip 💡 参考回答示范
> “我在混元大模型评测组负责长程多轮对话的自动化评估。挑战是对话轮次多（平均10轮以上），人工评估慢且不一致。我设计了三层评估：第一层是规则评估，检查每轮回复是否包含敏感词、是否重复、是否偏离主题，用正则和关键词匹配，样本是内部构造的1000组多轮对话，口径是规则命中率。第二层是模型评估，用另一个大模型作为裁判，给每轮回复打分，维度包括相关性、一致性、有用性、安全性，评分标准是1-5分，并让裁判给出理由。为了减少裁判偏见，我们采用双裁判取平均，并在提示词里明确评分细则。第三层是人工抽检，每周抽100组对话，由标注员复核，计算模型评估与人工评估的一致性（如Kappa系数）。关键指标是多轮一致性得分、遗忘率（指模型忘记前文信息的比例）、指令遵循率。严禁编造具体数字，但可以说我们通过这套体系把评测周期从一周缩短到一天。风控上，安全评估必须一票否决，任何一轮出现违规内容，整组对话判负。”

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：模型裁判本身有偏见，你怎么校准？
  - **续答**：我会用人工标注的黄金集来校准裁判。具体是选500组对话，人工打分，然后让裁判模型打分，计算两者相关性。如果某些维度偏差大，就调整裁判的提示词，或者换一个裁判模型。另外，对于关键维度如安全性，不用模型裁判，直接用规则或专门的安全模型。
- **追问 2**：长程对话中，如何检测模型是否遗忘了前文？
  - **续答**：我会在对话中埋设需要记忆的信息，比如用户在第2轮说‘我对花生过敏’，然后在第8轮问‘推荐一个零食’，看模型是否避开花生。如果推荐了含花生的零食，就记为遗忘。样本是构造的200组对话，口径是遗忘发生的比例。也可以让模型在每轮结束后总结前文，再对比总结与原始信息。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成百度文心一言时，评测维度可以增加知识准确性，因为文心强调知识增强，需要校验事实性。
2. 换成Kimi长文本场景时，长程评测要扩展到超长上下文，比如100k token，检测模型在长文档中的信息检索能力。
3. 换成DeepSeek代码助手时，多轮对话围绕代码调试，评测要增加代码正确性、可运行性，用单元测试自动化验证。
:::

### 题 34：美团外卖AI客服如何做Token成本算账与模型选型？

> 🏢 **真题来源**：美团 · 外卖AI客服 / 成本与架构面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察在日均千万级对话场景下，如何根据业务价值分层，选择不同尺寸模型，并计算Token成本、优化缓存与压缩，实现ROI最大化。
:::

::: tip 💡 参考回答示范
> “我在美团外卖AI客服负责成本优化。首先做业务分层：简单咨询（如营业时间、配送范围）用规则或小模型（如7B），复杂问题（如退款纠纷、食品安全）用大模型（如70B）。然后算账：假设日均1000万次对话，平均每次输入200token、输出100token。如果全用大模型，按每百万token价格X元计算，日成本很高。我们通过意图分类，把70%的简单咨询路由到小模型，成本降低60%以上。具体数字我不能编造，但可以说我们设了成本阈值，比如单次对话成本超过0.01元就触发告警。另外，优化缓存：对高频问题（如‘发票怎么开’）的答案做缓存，命中率约30%，样本是过去一周日志。还有Prompt压缩：把系统提示词从500token压缩到200token，保留关键指令。风控上，涉及金额和退款的回复必须走大模型并加人工审核。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：小模型效果差导致用户不满，你怎么权衡？
  - **续答**：我会设置兜底策略：小模型回复后，如果用户点击‘未解决’或转人工，则自动升级到大模型重新回答。同时监控小模型的解决率，样本是每天1000次抽样，口径是用户是否在24小时内再次提问同一问题。如果解决率低于阈值，就调整路由比例。
- **追问 2**：如何评估缓存带来的收益？
  - **续答**：缓存收益=命中次数×单次大模型成本-缓存维护成本。我会统计缓存命中率、缓存答案的准确率（人工抽检），以及缓存更新频率。如果答案有时效性（如促销活动），就设短TTL。样本是过去一个月缓存日志，口径是命中且正确的比例。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成滴滴客服时，场景更强调安全，涉及行程录音，模型选型要优先考虑私有化部署，成本计算包含GPU折旧。
2. 换成小红书客服时，用户问题更偏社区规则，可以多用小模型+知识库，减少大模型调用。
3. 换成蚂蚁金融客服时，合规要求高，必须用大模型并保留完整日志，成本中要包含审计存储费用。
:::

### 题 35：华为云AI助手如何处理高危写操作的风控与二次确认？

> 🏢 **真题来源**：华为 · 云AI助手 / 安全与风控面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察在云资源管理场景中，AI助手执行删除、重启、修改配置等写操作时，如何设计权限校验、二次确认、回滚与审计。
:::

::: tip 💡 参考回答示范
> “我在华为云AI助手负责高危写操作的风控。云资源操作如删除ECS、重启RDS、修改安全组，一旦误操作影响巨大。我的设计是四道防线：第一道是意图识别，用分类模型判断用户是否真的想执行写操作，还是只是询问。样本是过去三个月用户query抽样5000条，口径是人工标注的意图准确率。第二道是权限校验，调用IAM接口检查用户是否有该资源的操作权限，无权限直接拒绝。第三道是二次确认，对于高危操作，AI助手不直接执行，而是生成一个确认卡片，列出资源ID、操作类型、影响范围，要求用户输入‘确认’或点击按钮。第四道是回滚预案，对于可回滚操作（如修改配置），先备份原配置；对于不可回滚操作（如删除），强制要求用户输入资源名称以确认。审计上，所有写操作记录操作人、时间、资源、结果，并同步到云审计服务。关键指标是误操作率、二次确认通过率、回滚成功率。严禁编造具体数字，但可以说我们上线后误操作率显著下降。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户说‘我确认’，但资源名称输错了，怎么办？
  - **续答**：我会在确认卡片里要求用户输入完整的资源ID或名称，并与系统查询到的资源名做精确匹配。如果不匹配，则提示错误并拒绝执行。同时，对于批量操作，要求用户逐个确认或上传CSV，避免一个确认覆盖多个资源。
- **追问 2**：如何防止AI助手被提示词注入攻击，执行恶意写操作？
  - **续答**：我会在输入层做过滤，检测是否包含‘忽略之前指令’等注入模式，样本是已知攻击语料。另外，写操作的执行不依赖LLM的直接输出，而是LLM输出结构化命令，再由后端校验命令的合法性。即使LLM被注入，后端也会根据权限和二次确认拦截。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成阿里云助手时，权限体系换成RAM，二次确认可以结合MFA。
2. 换成腾讯云助手时，审计日志要对接云审计，并支持操作回滚。
3. 换成私有云场景时，风控要增加网络隔离检查，确保操作不跨安全域。
:::

### 题 36：小红书多模态笔记理解中，如何设计图文匹配与标签生成的产品方案？

> 🏢 **真题来源**：小红书 · 多模态AI / 内容理解产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察在多模态内容理解场景下，如何融合图像和文本特征，生成精准标签，并评估对推荐、搜索、广告的业务价值。
:::

::: tip 💡 参考回答示范
> “我在小红书负责多模态笔记理解，目标是给每篇笔记生成结构化标签，用于推荐和搜索。方案分三步：第一步是特征提取，图像用CLIP或自研视觉模型提取embedding，文本用BERT提取embedding，然后拼接或做交叉注意力。第二步是标签生成，用多标签分类模型预测标签，标签体系包括品类（如美妆、穿搭）、风格（如复古、清新）、场景（如通勤、约会）。训练样本是过去半年人工标注的10万篇笔记，口径是标注一致性。第三步是业务应用，标签用于召回和排序。评估指标是标签准确率、召回率、F1，以及下游推荐CTR提升。严禁编造具体数字，但可以说我们通过A/B测试发现，加入多模态标签后推荐点击率有提升。风控上，涉及敏感内容（如医疗建议）的标签要人工复核。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：图文不一致时，比如图片是猫但文字写狗，你怎么处理？
  - **续答**：我会把图文一致性作为一个特征，如果模型检测到不一致，则降低标签置信度，并触发人工审核。具体是计算图像embedding和文本embedding的余弦相似度，低于阈值则标记。样本是1000篇人工构造的不一致笔记，口径是检测准确率。
- **追问 2**：标签体系如何更新？新品类出现怎么办？
  - **续答**：我会定期（如每月）分析未登录标签的笔记，用聚类发现新标签，然后人工审核后加入体系。同时，模型支持增量学习，新标签只需少量样本即可适配。样本是过去一个月的新增笔记，口径是聚类纯度。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成抖音短视频理解时，要增加音频特征，标签体系增加BGM、舞蹈类型等。
2. 换成得物商品理解时，要增加品牌识别，标签体系增加品牌、型号、真伪特征。
3. 换成微信视频号时，要结合社交关系，标签体系增加社交热度、好友互动等。
:::
