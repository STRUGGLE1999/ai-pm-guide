### 题 1：字节跳动飞书智能助手：如何设计企业知识库RAG的检索与切分策略？

> 🏢 **真题来源**：字节跳动 · 飞书智能助手 / 企业知识库RAG产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：核心考察RAG系统中文档切分粒度、检索召回与重排的工程化权衡，以及如何平衡回答准确率与响应延迟。
:::

::: tip 💡 参考回答示范
> “我负责过飞书智能助手的企业知识库问答模块。当时业务痛点是员工搜索内部文档时，答案经常不完整或答非所问。我们样本是5000份飞书文档和1000条真实员工提问，口径是回答准确率（人工评估）和端到端延迟。首先，切分策略上，我们没有用固定长度，而是基于文档结构：标题、列表、表格分别处理。标题作为元数据，列表按项切分，表格转为Markdown后按行切分并保留表头。每个chunk控制在200-400字，重叠50字。检索阶段，我们用了混合检索：BM25召回Top 50，向量检索（用bge-large-zh）召回Top 50，然后合并去重，用交叉编码器重排Top 10。为了降低延迟，向量检索用了HNSW索引，重排模型用了蒸馏版。最终准确率从62%提升到85%，P99延迟从3.2秒降到1.8秒。关键决策是：对于表格类查询，我们额外增加了表头匹配的规则召回，因为向量模型对表格结构不敏感。另外，我们设置了兜底策略：如果重排后最高分低于阈值，就返回“未找到相关文档”并引导用户缩小范围。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果文档更新频繁，如何保证检索的实时性？
  - **续答**：我们设计了增量索引管道：文档变更时，通过飞书开放平台的事件订阅触发重新切分和向量化，只更新变化的chunk。向量库支持upsert，BM25索引也做增量更新。对于删除操作，我们做了软删除标记，检索时过滤。为了应对突发大量更新，我们用了消息队列削峰，并设置索引版本号，确保检索时看到一致快照。实测文档更新后，新内容在30秒内可被检索到。
- **追问 2**：如何评估RAG系统的回答质量？
  - **续答**：我们构建了包含500个问题的评测集，覆盖事实型、对比型、总结型。人工标注了标准答案和关键点。自动评估用ROUGE和BERTScore，但主要看人工评估的准确率和完整性。我们还监控了“无答案率”和“用户点踩率”，作为线上反馈。每周抽样100条线上日志做人工复核，发现badcase就归因到切分、检索或生成环节。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成钉钉知识库，需要适配钉钉文档的API和权限体系，切分时注意钉钉的富文本格式。
2. 如果换成微信客服场景，需考虑短文本和口语化查询，检索时增加同义词扩展和意图识别。
3. 如果换成内部Wiki，可以引入用户点击行为作为弱监督信号，优化重排模型。
:::

### 题 2：阿里巴巴国际站：如何用Agent工作流自动处理买家询盘并生成报价？

> 🏢 **真题来源**：阿里巴巴 · 国际站AI外贸助手 / Agent工作流编排面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察多步骤Agent编排中的状态管理、工具调用、异常处理与人工兜底机制，以及如何量化业务提效。
:::

::: tip 💡 参考回答示范
> “我在国际站负责过一个询盘自动处理Agent。业务场景是：买家发来询盘，Agent需要理解需求、查询商品库、计算价格、生成报价单并回复。样本是过去3个月5000条真实询盘，口径是自动处理率（无需人工介入）和报价准确率。我们用了LangChain式的编排，但自研了状态机。流程分四步：1）意图识别和实体抽取，用微调的BERT模型，抽取产品、数量、目标价等；2）工具调用，包括商品搜索API、价格计算API、库存API；3）报价单生成，用LLM填充模板；4）发送前审核，如果价格低于底价或库存不足，转人工。关键点是状态管理：每个步骤的输出作为下一步输入，并记录中间状态，便于回溯。异常处理上，如果工具调用超时或返回错误，重试2次后转人工。最终自动处理率达到65%，报价准确率98%（人工抽检200条）。我们设置了风控规则：报价必须经过价格校验，且不能承诺交期，这些由规则引擎硬编码，不交给LLM。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何防止Agent被恶意询盘诱导给出错误报价？
  - **续答**：我们做了三层防护：第一，输入过滤，识别垃圾询盘和注入攻击；第二，工具调用时，价格计算API只接受结构化参数，且参数范围有限制；第三，输出前用规则引擎校验，比如折扣率不能超过阈值。另外，我们记录了所有Agent的决策日志，定期审计。
- **追问 2**：如果商品库有百万级SKU，如何快速检索？
  - **续答**：我们用了向量检索加关键词过滤。先将商品标题和属性向量化，存到Milvus。查询时，先提取关键属性做过滤，再向量检索Top 20，然后用精排模型排序。为了降低延迟，我们做了两级缓存：热门商品缓存和查询结果缓存。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成淘宝客服，需处理更口语化的表达，并接入订单和物流API。
2. 如果换成跨境支付场景，需增加汇率转换和合规检查工具。
3. 如果换成B2B批发，报价需考虑阶梯价格和MOQ，工具调用更复杂。
:::

### 题 3：腾讯会议：如何设计大模型长程评测方案以保障会议纪要质量？

> 🏢 **真题来源**：腾讯 · 腾讯会议AI小助手 / 大模型长程评测面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察长文本场景下的评测集构建、指标设计、人工与自动评估结合，以及如何持续监控线上质量。
:::

::: tip 💡 参考回答示范
> “我负责腾讯会议AI纪要的评测。会议纪要的特点是长文本（1小时会议约1万字）和多说话人。样本是200场真实会议，覆盖不同行业和口音，口径是纪要的完整性、准确性和可读性。我们构建了分层评测集：第一层是事实性，抽取会议中的关键决策、待办、时间点，人工标注标准答案，计算召回率和准确率；第二层是摘要质量，用ROUGE和BERTScore，但更看重人工评分（1-5分）；第三层是格式，检查是否包含决议、待办、责任人等结构化字段。自动评估上，我们训练了一个小模型来预测人工评分，相关性达到0.85。线上监控方面，我们每天抽样100条纪要，人工快速标注，如果连续3天评分下降超过10%，就触发告警。我们还做了A/B测试，对比不同LLM版本。关键点是：长文本评测不能只看整体，要分段落评估，因为模型可能在中间部分丢失信息。我们用了“关键信息点”的方式，每个会议标注10-20个关键点，检查纪要是否覆盖。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何评估多说话人场景下的纪要准确性？
  - **续答**：我们增加了说话人归属的评估：检查每个待办是否关联到正确的说话人。人工标注时，会标记说话人ID。自动评估用说话人识别准确率，目前是92%。对于归属错误，我们会在后处理中用规则修正，比如根据上下文判断。
- **追问 2**：如果会议中有专业术语，如何保证纪要质量？
  - **续答**：我们构建了行业术语库，在ASR和LLM阶段都做了热词增强。评测时，专门抽取包含术语的片段，检查是否准确。另外，我们允许用户自定义术语，并实时生效。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成飞书妙记，需适配飞书的文档格式和协作功能。
2. 如果换成英文会议，需考虑语言差异和跨文化表达。
3. 如果换成电话会议，需处理低质量音频和更少的视觉线索。
:::

### 题 4：百度文心一言：如何计算和优化大模型推理的Token成本？

> 🏢 **真题来源**：百度 · 文心一言企业版 / Token成本算账面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对LLM推理成本结构的理解，包括输入输出Token、缓存、批处理、模型选择等，以及如何平衡成本与效果。
:::

::: tip 💡 参考回答示范
> “我在百度文心一言企业版负责成本优化。当时业务方抱怨API调用费用太高。样本是过去一个月100万次调用，口径是每千Token成本和平均响应时间。我们首先做了成本拆解：输入Token占60%，输出Token占40%。优化措施：1）输入侧，压缩Prompt，去掉冗余示例，用系统指令替代少样本示例，平均减少30%输入Token；2）输出侧，设置max_tokens，并让模型学会简洁回答，通过微调降低输出长度；3）缓存，对常见问题（如FAQ）的答案进行缓存，命中率25%，直接节省这部分成本；4）批处理，将多个请求合并成一个批次，提高GPU利用率，但会增加延迟，我们只对非实时场景使用；5）模型选择，简单任务用ERNIE Tiny，复杂任务用ERNIE 4.0，通过路由模型自动选择。最终每千Token成本降低45%，响应时间基本不变。我们还建立了成本监控看板，按业务线分摊，每周review。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何评估缓存策略对回答质量的影响？
  - **续答**：我们只对确定性高的问题缓存，比如“公司地址”。缓存前会人工审核一批，确保答案准确。线上监控缓存命中的用户满意度，如果低于非缓存，就调整缓存范围。
- **追问 2**：如果业务要求低延迟，如何平衡批处理？
  - **续答**：我们区分实时和非实时场景。实时场景不用批处理，而是用动态批处理（连续批处理）技术，在GPU上同时处理多个请求，但每个请求独立返回。这需要推理框架支持，我们用了vLLM。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成阿里通义千问，需考虑其计费方式和模型版本差异。
2. 如果换成自研模型，需计算GPU折旧和电费，而不仅是API费用。
3. 如果换成边缘设备，需考虑内存和算力限制，可能用量化模型。
:::

### 题 5：美团：如何设计高危写操作的风控机制防止AI误操作？

> 🏢 **真题来源**：美团 · 美团智能客服 / 高危写操作风控面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察AI产品在涉及资金、权限等写操作时的安全设计，包括权限控制、二次确认、审计日志和熔断机制。
:::

::: tip 💡 参考回答示范
> “我在美团智能客服负责退款和改单等写操作。这些操作一旦出错，会导致资损或用户投诉。样本是过去半年10万次写操作请求，口径是误操作率和拦截率。我们设计了四层风控：第一层，意图识别，只有明确且置信度高于0.95的请求才进入写操作流程，否则转人工；第二层，权限校验，AI只能操作授权范围内的订单，且金额超过500元必须人工审批；第三层，二次确认，AI会向用户复述操作内容，用户确认后才执行；第四层，执行前校验，调用业务API前，检查订单状态、用户身份等，防止条件不满足。我们还设置了熔断：如果某类操作失败率超过5%，自动暂停AI执行，转人工。审计日志记录所有AI决策和操作，便于回溯。最终误操作率从0.5%降到0.1%，拦截了2000次高风险请求。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何防止用户诱导AI进行未授权的操作？
  - **续答**：我们做了对抗训练，让模型识别诱导性语言。同时，权限校验是硬性的，不依赖模型判断。即使模型被诱导，API层也会拒绝。
- **追问 2**：如果AI误操作已经发生，如何快速补救？
  - **续答**：我们设计了回滚机制，对于可逆操作（如退款），支持一键撤销。对于不可逆操作，有应急流程，客服可手动补偿。同时，我们会分析误操作原因，更新风控规则。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成滴滴行程修改，需考虑实时位置和司机接单状态。
2. 如果换成银行转账，需增加生物识别和多重审批。
3. 如果换成电商改价，需考虑促销规则和库存影响。
:::

### 题 6：小红书：如何利用多模态大模型提升笔记审核效率？

> 🏢 **真题来源**：小红书 · 社区内容安全 / 多模态审核面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察多模态模型在内容审核中的应用，包括图文匹配、违规识别、误杀与漏杀平衡，以及人机协同流程。
:::

::: tip 💡 参考回答示范
> “我在小红书负责笔记审核的多模态升级。之前审核主要靠文本和图像分开，漏杀率较高。样本是100万条笔记，口径是违规召回率和误杀率。我们引入了多模态大模型，同时理解图片和文本，判断是否违规。具体做法：1）用CLIP-like模型做图文匹配，检测图文不符（如用美女图卖假货）；2）用多模态LLM对疑似违规内容进行细粒度分类，比如软色情、违禁品等；3）对于高风险类别，直接机审拦截，低风险转人工。为了降低误杀，我们设置了置信度阈值，只有高于0.9才自动拦截，0.7-0.9转人工复核。同时，我们构建了对抗样本库，持续训练模型。最终违规召回率从85%提升到95%，误杀率从2%降到0.8%。人机协同上，机审覆盖80%的流量，人工只处理疑难。我们还做了可解释性，模型会输出违规原因，帮助人工快速判断。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何应对新型违规内容？
  - **续答**：我们建立了主动学习循环：人工审核中发现的漏杀样本，会加入训练集，每周更新模型。同时，用异常检测发现新违规模式。
- **追问 2**：多模态模型推理成本高，如何优化？
  - **续答**：我们用了模型蒸馏，将大模型能力蒸馏到小模型，部署在边缘。对于简单任务，用小模型；复杂任务才用大模型。另外，我们用了缓存，相同图片哈希只推理一次。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成抖音短视频审核，需处理视频帧和音频，时序信息更复杂。
2. 如果换成淘宝商品审核，需结合商品类目和属性。
3. 如果换成微信朋友圈审核，需考虑隐私和社交关系。
:::

### 题 7：字节跳动飞书智能伙伴：如何设计多轮工具调用的Agent工作流，避免死循环与Token爆炸？

> 🏢 **真题来源**：字节跳动 · 飞书智能伙伴 / Agent平台产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察Agent工作流编排中对工具调用链路的控制能力，包括循环检测、预算控制与状态管理。
:::

::: tip 💡 参考回答示范
> “我在飞书智能伙伴项目里负责过Agent工具调用的链路设计。当时业务方要求智能伙伴能自动查日程、发消息、改文档，但测试时经常出现模型反复调用同一个接口，或者陷入'查不到就重试'的死循环，一次对话消耗几万Token。我的解法是三层控制：第一，在编排层加一个'调用轨迹栈'，记录每一步的tool_name和参数指纹，如果连续两次调用相同工具且参数相似度超过0.9，就强制中断并返回兜底话术，比如'我暂时无法完成这个操作，建议您手动处理'。第二，给每个会话设置硬性Token预算，比如单轮对话上限8000 Token，达到阈值后自动降级为纯文本回复并提示用户'当前操作较复杂，请简化需求'。第三，用状态机管理任务阶段，把'查日程-改日程-发通知'拆成三个独立状态，每个状态只允许调用特定工具集，避免模型自由发挥。上线后死循环率从12%降到0.8%，单次任务平均Token消耗从1.2万降到4500。样本是飞书内部200个真实用户一周的日志，口径是单次用户主动发起的任务会话。这里严禁编造，所有数字都来自我们埋点统计。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果模型在某个状态下反复调用工具但参数不同，比如每次改一点时间，你怎么判断是正常迭代还是无效循环？
  - **续答**：我会引入'目标漂移检测'。在状态机里为每个任务预设一个目标向量，比如'改日程'的目标是最终确认一个时间点。每次工具调用后，计算当前结果与目标的语义距离，如果距离连续三次没有缩小，就判定为无效循环，触发人工确认或终止。同时设置最大迭代次数，比如改日程最多允许5次尝试，超过就转人工。
- **追问 2**：Token预算用完后直接降级，会不会导致用户体验断裂？有没有更平滑的降级策略？

::: warning ⚠️ 连环追问与高分续答

- **追问 2**：如果商品描述本身结构混乱，没有明确规格表，怎么切分？
  - **续答**：我会先用小模型做结构识别，把文本分成'属性-值'对。如果识别失败，就退化为滑动窗口切分，窗口大小256 Token，重叠50 Token，并给每个chunk打上'低置信度'标签，生成时提示用户'该信息可能不完整，请核实'。

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户连续追问同一个工具，但每次参数都不同，状态机怎么处理？
  - **续答**：我会把工具调用参数作为状态的一部分存下来，每次新参数进来先做参数差异比对。如果参数变化在允许范围内（比如时间偏移不超过 1 小时），就合并成一次调用；如果变化太大，就重置状态机到‘工具就绪’并重新收集参数。同时会记录参数变更次数，超过 3 次就主动询问用户是否要放弃当前任务。
- **追问 2**：状态机持久化到 Redis 后，如何保证多实例部署下的并发一致性？
  - **续答**：我们用的是 Redis 分布式锁，key 是会话 ID，锁超时 5 秒。每次状态变更前先获取锁，变更后释放。如果获取锁失败，就返回‘系统繁忙，请重试’。另外，状态数据用 Hash 结构存储，每个字段单独更新，避免全量覆盖。监控上会统计锁等待时长和失败率，超过阈值就告警。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成钉钉场景：把飞书工具链换成钉钉的审批、考勤、日志接口，状态机不变，但需要适配钉钉的异步回调机制。
2. 换成微信客服场景：状态机增加‘转人工’状态，因为微信侧用户期望快速响应，工具调用失败直接转人工。
3. 换成内部 IT 运维 Agent：工具调用变成重启服务、查日志等，风控要求更高，所有写操作需要工单审批。
:::

### 题 14：阿里巴巴 RAG 检索增强生成中，如何设计切分策略以平衡召回与精度？

> 🏢 **真题来源**：阿里巴巴 · 通义千问 / 企业知识库 RAG 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察文档切分粒度、重叠窗口、元数据过滤对检索效果的影响，本质是信息检索中的召回率与准确率权衡。
:::

::: tip 💡 参考回答示范
> “在通义千问企业知识库项目中，我负责设计切分策略。样本是 5000 份产品文档，口径是人工标注的 200 个问答对。我们对比了三种切分方式：固定 512 token 切分、按段落切分、按语义相似度切分。固定切分召回率 78%，但精度只有 62%，因为很多答案被切到两个块里；按段落切分召回率 85%，精度 74%；语义切分召回率 91%，精度 82%，但计算成本高。最终我们采用混合策略：先用段落切分作为基础，再对超过 800 token 的段落用语义相似度二次切分，重叠窗口设 128 token。元数据上，每个块都带上文档标题、章节、更新时间，检索时先按元数据过滤（比如只搜最近 3 个月的文档），再做向量检索。重排序阶段用 cross-encoder 对 top 20 结果重新打分，取 top 5 送给 LLM。指标上，端到端回答准确率从 68% 提升到 86%。成本方面，切分和索引是一次性开销，检索时向量搜索延迟在 50ms 以内。风控上，如果检索结果相似度低于 0.7，就触发‘未找到相关内容’的兜底回复。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果文档更新频繁，如何避免旧块残留导致检索到过时信息？
  - **续答**：我们给每个块加了版本号和生效时间。文档更新时，先标记旧块为失效，再插入新块。检索时过滤掉失效块。另外，每天凌晨跑一次全量索引重建，确保一致性。监控上会统计失效块占比，超过 10% 就告警。
- **追问 2**：语义切分具体怎么实现？用了什么模型？
  - **续答**：我们用 BERT 做句子嵌入，计算相邻句子的余弦相似度，低于阈值 0.6 就切分。模型是开源的 paraphrase-multilingual-MiniLM，部署在 GPU 上，切分 5000 份文档耗时约 2 小时。为了降本，我们只对超过 800 token 的段落做语义切分，其余用段落切分。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成腾讯文档场景：文档类型更多（表格、PPT），需要针对不同格式设计切分规则，表格按行切分，PPT 按页切分。
2. 换成百度搜索场景：检索结果需要实时性，切分策略要更轻量，可能用固定 256 token 切分，牺牲一点精度换速度。
3. 换成小红书笔记场景：文本短且口语化，切分粒度可以更细，比如按句子切分，重叠窗口设 64 token。
:::

### 题 15：腾讯混元大模型长程评测如何设计多轮对话的自动化打分体系？

> 🏢 **真题来源**：腾讯 · 混元大模型 / 对话评测产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察长程对话中一致性、连贯性、任务完成度的自动化评估方法，本质是 NLP 评测中的指标设计与人工对齐。
:::

::: tip 💡 参考回答示范
> “在混元大模型长程评测项目中，我设计了一套自动化打分体系。样本是 1000 组多轮对话，每组 5-10 轮，口径是人工标注的 4 个维度：一致性、连贯性、任务完成度、安全性。自动化打分用 GPT-4 作为裁判，但直接打分与人工相关性只有 0.6。后来我们改成 pairwise 比较：让 GPT-4 对比两个模型的回复，选出更好的，准确率提升到 0.78。具体做法是：每轮对话后，把历史上下文和当前回复一起给裁判，裁判输出 A/B 或平局。为了降低成本，我们只对关键轮次（如任务完成轮）做 pairwise，其他轮次用规则打分（如重复率、长度）。一致性用实体追踪：提取对话中的实体，检查前后是否矛盾。连贯性用句子嵌入的余弦相似度。任务完成度用槽位填充率。安全性用敏感词库加分类器。最终综合得分是加权平均，权重通过人工标注数据拟合。指标上，自动化得分与人工评分的 Spearman 相关系数达到 0.82。风控上，所有评测数据脱敏，裁判模型不接触用户隐私。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果裁判模型本身有偏见，怎么校准？
  - **续答**：我们做了两件事：一是用多个裁判模型（GPT-4、Claude、混元）投票，取多数结果；二是定期用人工标注数据做校准，如果某个裁判与人工偏差大，就调整它的权重或弃用。另外，我们还会分析裁判的偏好，比如是否偏爱长回复，然后针对性修正。
- **追问 2**：长程对话中，如何评估模型是否记住了早期信息？
  - **续答**：我们设计了一个‘记忆探测’任务：在对话早期插入一个事实（如‘我明天要去北京’），然后在第 5 轮问‘我明天去哪？’。模型答对率作为记忆指标。另外，我们还用注意力可视化检查模型是否关注了早期 token。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成字节豆包场景：评测维度增加‘趣味性’，因为豆包面向 C 端，需要更活泼的回复。
2. 换成华为盘古场景：评测更注重行业知识准确性，需要引入领域专家标注。
3. 换成美团场景：评测任务完成度时，要结合具体业务指标，如外卖订单转化率。

### 题 19：字节跳动 · 飞书智能伙伴：如何设计 Agent 工作流编排让审批流自动流转？

> 🏢 **真题来源**：字节跳动 · 飞书 AI 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：Agent 工作流编排与业务系统集成，核心是任务拆解、状态机与异常兜底。
:::

::: tip 💡 参考回答示范
> “我在飞书智能伙伴项目里负责审批流 Agent 的编排设计。首先，我们把审批场景拆成三类节点：信息抽取、规则判断、动作执行。信息抽取用大模型从聊天记录或文档里抽字段，比如报销单的金额、事由、发票号；规则判断走确定性规则引擎，比如金额超过 5000 必须加签；动作执行调飞书审批 API 发起流程。编排上我用 DAG 定义节点依赖，每个节点有超时和重试策略。关键指标是端到端成功率，样本是过去 30 天 1.2 万条真实审批请求，口径是首次发起即成功且无人工干预。上线后成功率从 68% 提到 89%，平均耗时从 4.2 分钟降到 1.1 分钟。风控上，所有写操作前必须让用户二次确认，且记录操作日志。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果大模型抽取出错导致审批金额错误，你怎么兜底？
  - **续答**：我们做了三层兜底：第一层，抽取结果置信度低于 0.9 时强制转人工；第二层，金额字段与原始凭证做正则校验，不一致就拦截；第三层，审批发起后 30 秒内允许用户撤回。样本是 200 次模拟错误注入，口径是错误金额流出率，结果是 0.3%。
- **追问 2**：Agent 工作流和传统 BPM 引擎有什么区别？
  - **续答**：传统 BPM 是固定路径，Agent 工作流是动态路径。我们的做法是混合编排：确定性环节走 BPM，非确定性环节走大模型。比如报销标准判断，不同城市差旅标准不同，大模型根据员工城市和职级动态选择规则，再交给 BPM 执行。
:::

::: details 🛠️ 换成你自己的项目时改这三处

::: tip 💡 参考回答示范
> “我在混元做过长程对话评测，核心是解决“模型在 10 轮以后开始胡言乱语”的问题。样本是 3000 组多轮对话，每组 8-15 轮，口径是“任务完成率”和“事实一致性”。评测集设计上分四类：第一类是信息追踪，比如用户在第 3 轮说了预算 5000，第 10 轮问推荐，模型必须记得；第二类是工具调用，比如第 5 轮查天气，第 7 轮基于天气推荐穿搭；第三类是冲突处理，用户前后说法矛盾，模型要主动澄清；第四类是长文档问答，给 8000 字文档，在第 12 轮问细节。自动评测用 GPT-4 做裁判，但只对事实一致性和任务完成度打分，人工抽检 10% 校准。指标上，8 轮以内任务完成率 92%，12 轮以上掉到 67%，主要失败在信息追踪和冲突处理。后来我们加了记忆摘要机制，每 4 轮把关键信息压缩成摘要注入下一轮，12 轮以上完成率提到 81%。成本上，自动评测单组对话约 0.5 元，3000 组是 1500 元，人工抽检 300 组，每组 5 元，总成本 3000 元。风控上，评测集里不能出现真实用户隐私，所有对话都是脱敏后合成。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：自动评测用 GPT-4 做裁判，怎么保证裁判本身不偏？
  - **续答**：我会做三件事：第一，裁判 prompt 里明确评分 rubric，每个分数段有具体描述；第二，用 200 组人工标注数据校准裁判，计算裁判与人工的一致率，要求 Cohen's kappa 大于 0.7；第三，对裁判结果做位置偏差检验，把同一组对话的模型回答和参考答案交换位置，看裁判是否稳定。样本是 500 组，口径是交换位置后评分变化超过 1 分的比例，我们控制在 5% 以内。
- **追问 2**：长程评测里，工具调用的成功率怎么单独度量？
  - **续答**：我会把工具调用拆成三步：意图识别、参数填充、结果使用。意图识别看是否选了正确的工具，参数填充看槽位准确率，结果使用看模型是否在后续轮次引用了工具返回。样本是 1000 组带工具调用的对话，口径是三步全对的端到端成功率。目前意图识别 95%，参数填充 88%，结果使用 76%，端到端 72%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 把混元换成文心一言，评测集加入百度搜索的实时结果，重点测模型对搜索摘要的引用准确性。
2. 把长文档问答换成腾讯会议纪要，文档长度从 8000 字提到 2 万字，测模型对会议决议的追踪。
3. 把自动评测裁判从 GPT-4 换成 Claude，样本换成 2000 组，口径换成裁判与人工的 Spearman 相关系数。
:::

### 题 28：百度 · 文心一言 Token 成本算账与商业化定价题

> 🏢 **真题来源**：百度 · 文心一言 / 大模型 API 商业化产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考查如何拆解大模型推理的 Token 成本结构，设计阶梯定价、缓存策略和毛利模型，并平衡免费额度与付费转化。
:::

::: tip 💡 参考回答示范
> “我参与过文心一言 API 的定价模型设计。样本是 100 家中小企业客户的调用日志，口径是每百万 Token 的综合成本。成本拆解上，推理成本占 60%，其中 GPU 折旧 35%、电费 15%、运维 10%；网络和存储占 20%；风控和审核占 15%；剩余 5% 是管理分摊。当时 ERNIE 3.5 的每百万 Token 成本是 12 元，我们定价 20 元，毛利 40%。但问题是大客户用量大，要求折扣，小客户用量小，付费意愿低。后来做了三件事：第一，阶梯定价，每月 100 万 Token 以内 20 元，100-1000 万 15 元，1000 万以上 10 元；第二，缓存策略，对相同 prompt 的重复请求做 KV 缓存，命中率 18%，直接降本 12%；第三，免费额度从 50 万 Token 降到 10 万，但新用户首月送 100 万，付费转化率从 3% 提到 7%。指标上，综合毛利率从 40% 提到 52%，大客户续费率从 65% 提到 78%。风控上，免费额度必须绑定实名，且单日调用超过 10 万 Token 触发人工审核，防止羊毛党。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果客户要求私有化部署，你的成本模型怎么变？
  - **续答**：私有化部署的成本结构完全不同。硬件一次性投入占 70%，软件授权占 20%，运维占 10%。我会按三年折旧算，样本是 5 个私有化项目，口径是三年总拥有成本。一个 8 卡 A800 的集群，硬件 120 万，软件授权 30 万，运维 15 万，三年总成本 165 万。如果客户年调用量低于 5000 万 Token，私有化不划算，我会推公有云。
- **追问 2**：缓存命中率怎么提升？会不会影响回答质量？
  - **续答**：缓存只对完全相同的 prompt 生效，所以不影响质量。提升命中率靠两招：一是引导客户用固定模板，比如客服场景的 FAQ；二是对语义相同但措辞不同的 prompt 做向量聚类，聚类后共用缓存。样本是 10 万条请求，口径是缓存命中率，模板引导后从 18% 提到 25%，向量聚类再提到 32%。但向量聚类有误判风险，我们设了相似度阈值 0.95，低于阈值不走缓存。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 把文心一言换成通义千问，成本拆解加入阿里云的弹性计算折扣，样本换成 200 家客户。
2. 把阶梯定价换成按功能定价，比如基础问答、文档解析、代码生成分别定价，口径换成各功能的毛利率。
3. 把免费额度策略换成按任务类型送额度，比如文档解析送 50 万 Token，代码生成送 20 万 Token。
:::

### 题 29：美团 · 智能客服高危写操作风控题

> 🏢 **真题来源**：美团 · 智能客服 / 交易类 Agent 风控产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考查 Agent 在执行退款、改地址、取消订单等写操作时的权限校验、二次确认、熔断降级和审计追踪设计。
:::

::: tip 💡 参考回答示范
> “我在美团做过智能客服的退款 Agent。样本是 5000 笔退款请求，口径是“误退款率”和“用户满意度”。高危写操作的核心原则是：Agent 只能提议，不能直接执行。具体设计上分四层：第一层是意图识别，用户说“我要退款”，Agent 先判断是整单退还是部分退，是未发货还是已发货；第二层是权限校验，调用户身份接口确认订单归属，调商家接口确认退款规则，比如生鲜类超过 24 小时不能退；第三层是二次确认，Agent 生成退款摘要，包括金额、原因、到账时间，用户点击“确认退款”才真正调用退款接口；第四层是熔断，如果同一用户 1 小时内发起 3 次以上退款，或同一订单被多次退款，自动转人工。指标上，误退款率从 0.8% 降到 0.1%，用户满意度从 3.5 分提到 4.2 分（5 分制）。审计上，每次写操作记录操作人、时间、订单号、退款金额、Agent 版本号，日志保留 2 年。风控上，退款接口本身有幂等设计，防止重复退款。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户情绪激动，要求立刻退款，Agent 怎么平衡体验和风控？
  - **续答**：我会做情绪识别加优先通道。情绪识别用文本分类，样本是 2000 条客服对话，口径是情绪标签准确率，目前是 85%。识别为高情绪时，Agent 先安抚，然后走快速通道：如果订单金额低于 100 元且规则允许，二次确认后直接退；如果金额高于 100 元，转人工但排队优先级提到最高。样本是 500 笔高情绪退款，口径是平均处理时长，从 8 分钟降到 3 分钟。
- **追问 2**：Agent 版本升级后，误退款率突然升高，你怎么排查？
  - **续答**：我会先看灰度数据，对比新旧版本的误退款率。然后拆解链路，看是意图识别、权限校验还是二次确认出了问题。样本上，我们有一次新版本把“部分退款”误判为“整单退款”，误退款率从 0.1% 跳到 0.5%。排查发现是意图分类器的训练数据里部分退款样本太少，只有 5%。后来补了 2000 条部分退款样本，重新训练后恢复到 0.1%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 把美团退款换成滴滴行程取消，高危操作改成取消订单和修改终点，风控规则换成行程状态校验。
2. 把二次确认从点击按钮换成语音确认，样本换成 1000 通电话，口径是语音确认的准确率。
3. 把熔断规则从次数换成金额，比如单用户单日退款超过 500 元自动转人工，样本换成 3000 笔。
:::

### 题 30：小红书 · 多模态笔记理解与搜索排序题

> 🏢 **真题来源**：小红书 · 多模态搜索 / 笔记理解产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考查图文笔记的跨模态对齐、多模态特征融合、搜索相关性排序，以及如何用用户行为数据做冷启动。
:::

::: tip 💡 参考回答示范
> “我负责过小红书搜索里“看图找笔记”的多模态链路。样本是 20 万条带图 query 和对应的点击日志，口径是 Top10 点击率。核心问题是用户上传一张穿搭图，想找同款或相似风格，但笔记的图文质量参差不齐。我的做法是：第一，跨模态对齐，用 CLIP 类模型把图片和文本映射到同一空间，图片特征和笔记的标题、正文、标签分别算相似度，再加权融合，权重是图片 0.5、标题 0.3、正文 0.2；第二，多模态特征融合，除了 CLIP 特征，还加入图片的颜色直方图、物体检测结果，比如“上衣、裤子、鞋子”，和笔记的标签做匹配；第三，冷启动，新笔记没有点击数据，就用多模态相似度做粗排，再根据后续点击做精排。指标上，Top10 点击率从 12% 提到 19%，端到端延迟从 600ms 压到 380ms。成本上，单次多模态检索消耗 0.5 分钱，主要是图片编码和向量检索。风控上，图片先过审核模型，涉黄涉暴直接拦截，不进入检索。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户上传的图片是拼图，包含多个物品，你怎么处理？
  - **续答**：我会先做图片分割，用物体检测模型识别出多个主体，然后对每个主体分别生成 query，再合并检索结果。样本是 5000 张拼图，口径是 Top10 点击率。分割后单主体检索的点击率是 21%，合并后是 18%，因为合并会引入噪声。后来改成按主体分别展示结果，用户点击某个主体再细化，点击率回到 20%。
- **追问 2**：多模态特征融合时，权重怎么定？
  - **续答**：我们用网格搜索加线上 A/B。样本是 10 万条 query，口径是 NDCG@10。图片权重从 0.3 到 0.7 试了 5 档，0.5 时 NDCG 最高，是 0.68。标题权重 0.3，正文 0.2。但不同类目不一样，穿搭类图片权重高，美食类标题权重高。后来做了类目自适应，穿搭类图片 0.6，美食类图片 0.4。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 把小红书换成抖音，多模态笔记换成短视频，加入视频帧采样和音频转文本。
2. 把跨模态对齐从 CLIP 换成 BLIP-2，样本换成 30 万条 query，口径换成 MRR。
3. 把冷启动策略从多模态相似度换成图神经网络，用笔记的共现关系做推荐。
:::

### 题 31：字节跳动 · 飞书智能伙伴：Agent 工作流编排中，如何解决多轮对话状态丢失导致的重复提问？

> 🏢 **真题来源**：字节跳动 · 飞书 AI 产品经理面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察 Agent 工作流中记忆与状态管理机制，以及如何通过产品设计降低用户重复输入成本。
:::

::: tip 💡 参考回答示范
> “我之前在飞书智能伙伴项目里，核心目标是把跨天会议安排、日程调整、文档协作串成一个 Agent 工作流。当时用户反馈最集中的问题是：第一轮说了‘下周三下午两点跟产品团队开评审会’，第二轮补充‘把会议室换成 8 楼 A 区’，Agent 会重新问一遍‘请问会议主题是什么’。我们排查发现，对话状态只存在前端 session 里，一旦用户切到其他会话或刷新页面，状态就丢了。
> 
> 我做的方案分三层：第一层，短期记忆用 Redis 存最近 5 轮对话的 slot 值，key 是用户 ID + 工作流 ID，TTL 设 30 分钟，样本是 2000 个真实工作流会话，口径是用户主动发起且未结束的会话。第二层，长期记忆把已确认的实体（会议主题、时间、参与人、会议室）写入飞书多维表格，作为工作流上下文，每次新轮次先做实体对齐，避免重复提问。第三层，前端加一个‘已收集信息卡片’，用户能直接看到当前 Agent 已经知道什么，缺失什么，点击卡片可以补全。
> 
> 指标上，我们盯两个数：重复提问率从 18% 降到 4%，样本是 500 个跨天工作流会话，口径是同一实体被追问两次以上。任务完成率从 62% 提到 81%。但这里有个坑：长期记忆写入多维表格后，如果用户修改了会议时间，旧实体没失效，会导致 Agent 用错时间。所以我们加了版本号，每次用户确认修改就递增，Agent 只读最新版本。
> 
> 风险控制上，涉及写操作（比如自动发会议邀请）必须二次确认，且确认卡片里要展示所有已收集实体，避免因为状态错乱发错邀请。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户在多轮对话中突然切换意图，比如从‘安排会议’变成‘查一下上周的会议纪要’，你的状态管理怎么处理？
  - **续答**：我会把工作流状态分成主意图和子意图。主意图切换时，当前工作流的 slot 值不销毁，而是挂起，存到‘待恢复工作流’列表里。用户查完纪要后，Agent 主动问一句‘要继续安排刚才的会议吗？’如果用户说继续，就把挂起的 slot 恢复。样本是 300 个意图切换会话，口径是用户主动打断且 10 分钟内返回。恢复成功率做到 76%。关键是要给用户一个显式的‘恢复’入口，不能偷偷恢复，否则用户会困惑。
- **追问 2**：长期记忆写入多维表格，会不会有权限和隐私问题？比如用户 A 的会议信息被用户 B 看到？
  - **续答**：会。我们做了两层隔离：第一，多维表格按用户 ID 做行级权限，Agent 写入时带上 owner 字段，查询时强制过滤 owner=当前用户。第二，敏感字段比如参与人手机号，做脱敏存储，Agent 展示时只显示姓名。样本是 1000 条会议记录，口径是包含外部参与人的记录。上线后没有出现越权访问。但这里有个边界：如果用户把会议共享给同事，同事的 Agent 能不能读？我们当时决定不能，必须用户手动授权，授权粒度到单条记录。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成钉钉智能助理，短期记忆可以复用钉钉的会话上下文，但长期记忆要对接钉钉宜搭，权限模型不同，需要重新设计行级权限。
2. 如果换成微信客服 Agent，没有多维表格，长期记忆可以存到企业微信的客户联系记录里，但要注意微信的隐私合规要求更严，不能存手机号。
3. 如果换成剪映的 AI 剪辑助手，状态管理要加上时间轴位置，用户说‘把刚才那个转场再调快一点’，Agent 要知道‘刚才’指的是哪个片段，可以存 clip ID 和版本号。
:::

### 题 32：阿里巴巴 · 通义千问企业知识库：RAG 切分粒度怎么定？切太碎召回噪声大，切太大答案不精准，怎么权衡？

> 🏢 **真题来源**：阿里巴巴 · 通义千问企业知识库产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察 RAG 文档切分策略与召回精度、答案质量的权衡，以及如何用评测数据驱动切分参数调优。
:::

::: tip 💡 参考回答示范
> “我在通义千问企业知识库项目里，服务的是内部法务和 HR 场景。最初我们按固定 512 token 切分，结果法务合同里一个条款被切成两半，召回后模型答‘根据合同第 3.2 条’，但 3.2 条的后半句在下一个 chunk 里，答案不完整。HR 场景更严重，员工手册按 512 切，一个完整的请假流程被切到三个 chunk，用户问‘年假怎么请’，召回三个片段，模型拼出来的答案顺序是乱的。
> 
> 我重新设计了切分策略：第一，按文档结构切，优先用标题、段落、列表项作为边界，样本是 500 份法务合同和 200 份 HR 手册，口径是人工标注了 1000 个问答对。第二，对超长段落做语义切分，用 embedding 相似度找断点，阈值设 0.75，低于阈值就切。第三，每个 chunk 加 10% 的 overlap，避免边界信息丢失。切分后平均 chunk 长度 380 token，最大 800，最小 120。
> 
> 指标上，召回率从 72% 提到 89%，口径是 top-5 召回包含正确答案的比例。答案完整率从 65% 提到 84%，口径是人工评估答案是否覆盖问题所有要点。但这里有个代价：chunk 数量从 1.2 万涨到 2.8 万，检索延迟从 120ms 涨到 210ms。我们通过加缓存和倒排索引优化，压回 150ms。
> 
> 风控上，法务场景要求答案必须带原文引用和 chunk ID，用户能点开看原文。如果模型答案和原文引用不一致，直接降级为‘请查看原文’。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：语义切分用 embedding 相似度，阈值 0.75 是怎么定的？有没有做消融实验？
  - **续答**：做了。我们拿了 200 份文档，人工标注了 500 个理想切分点，然后跑不同阈值：0.6 切得太碎，chunk 数多 30%，召回噪声大；0.8 切得太粗，答案完整率下降 8%；0.75 在召回率和完整率之间最平衡。样本是 500 个标注点，口径是人工判断切分是否破坏语义单元。但不同文档类型阈值不一样，法务合同用 0.78，HR 手册用 0.72，我们做成了可配置的。
- **追问 2**：chunk 加了 10% overlap，会不会导致召回重复，模型答案冗余？
  - **续答**：会。我们做了去重：召回后先按 chunk ID 去重，如果两个 chunk 重叠超过 50%，只保留得分高的那个。另外在 prompt 里明确告诉模型‘如果多个片段有重复内容，只输出一次’。样本是 300 个重复召回 case，口径是人工判断答案是否冗余。去重后答案冗余率从 22% 降到 7%。但 overlap 不能省，省了边界信息丢失更严重。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成腾讯文档 AI 助手，文档类型更多，有表格、PPT、思维导图，切分要按元素类型分别处理，表格按行切，PPT 按页切，不能统一用 token 数。
2. 如果换成百度如流知识库，检索层可以用百度自研的语义索引，切分粒度可以更粗，因为索引本身能处理长文本，但答案生成还是要靠 chunk 拼接。
3. 如果换成蚂蚁支小宝的金融知识库，合规要求更高，每个 chunk 必须带监管文件编号和生效日期，切分时要保留这些元数据，不能只切正文。
:::

### 题 33：腾讯 · 混元大模型长程评测：如何设计一套评测集，真实反映模型在 10 轮以上对话中的指令遵循能力？

> 🏢 **真题来源**：腾讯 · 混元大模型产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察长程对话评测集的设计方法，包括任务类型、轮次分布、评分口径和自动化评估与人工评估的结合。
:::

::: tip 💡 参考回答示范
> “我在腾讯混元做长程对话评测时，发现现有评测集大多是单轮或 3 轮以内，模型在 10 轮以上会忘记早期指令。比如用户第一轮说‘所有回答用表格’，到第 8 轮模型就忘了，开始用段落。我们设计了一套 200 个对话的评测集，每个对话 12-15 轮，覆盖四个任务类型：多约束指令遵循、信息追踪、意图切换、纠错恢复。
> 
> 设计方法上，第一，每个对话有一个‘核心约束’，比如‘始终用 JSON 格式输出’，这个约束在第 1 轮给出，后续轮次不再重复，看模型能不能记住。第二，每 3 轮插入一个‘干扰轮’，比如问一个无关问题，看模型会不会被带偏。第三，第 10 轮左右插入一个‘纠错轮’，用户说‘你刚才第三轮说错了，应该是 X’，看模型能不能定位并修正。
> 
> 评分口径分三层：第一层，约束遵循率，统计每个对话中模型违反核心约束的轮次比例，样本是 200 个对话，口径是人工标注的违反次数。第二层，信息追踪准确率，统计模型正确引用早期轮次信息的比例。第三层，纠错成功率，统计模型正确修正的比例。
> 
> 自动化评估用 GPT-4 做裁判，但人工抽检 20% 发现 GPT-4 对‘表格’和‘JSON’的区分不够准，所以关键约束还是人工评。最终混元在约束遵循率上从 68% 提到 85%，信息追踪从 55% 提到 78%，纠错成功率从 40% 提到 62%。
> 
> 风控上，评测集不能泄露到训练数据里，我们做了时间戳隔离，评测集创建后不再用于训练。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：GPT-4 做裁判，怎么保证它和人工评分一致？有没有做一致性检验？
  - **续答**：做了。我们抽了 50 个对话，人工和 GPT-4 分别打分，算 Cohen's Kappa，约束遵循率是 0.72，信息追踪是 0.65，纠错是 0.58。纠错一致性最低，因为 GPT-4 有时分不清‘模型真的修正了’还是‘模型只是重复了用户的话’。所以纠错轮我们全部人工评。样本是 50 个对话，口径是人工双盲标注。
- **追问 2**：干扰轮会不会导致模型表现下降，但其实是合理的？比如用户问无关问题，模型回答了，算不算违反约束？
  - **续答**：不算。我们定义约束是‘在相关轮次中必须遵守’，干扰轮如果和核心约束无关，模型正常回答不扣分。但有一种情况扣分：用户问无关问题，模型回答时用了段落而不是表格，如果核心约束是‘所有回答用表格’，那还是要扣。样本是 200 个干扰轮，口径是人工判断是否相关。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成字节豆包的长程评测，可以加入多模态轮次，比如用户发一张图，后面几轮引用这张图的内容，看模型能不能记住图片信息。
2. 如果换成 Kimi 的长文本评测，可以把对话轮次拉到 50 轮以上，重点测模型在超长上下文中的信息衰减曲线，每 10 轮统计一次准确率。
3. 如果换成 DeepSeek 的代码助手评测，长程对话要加入代码上下文追踪，比如第一轮定义了一个函数，第 10 轮要求修改这个函数，看模型能不能正确引用。
:::

### 题 34：百度 · 文心一言企业版：Token 成本算账，如何在不降低效果的前提下把单次问答成本降低 40%？

> 🏢 **真题来源**：百度 · 文心一言企业版产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察大模型 Token 成本结构分析、成本优化手段（缓存、压缩、模型路由、输出控制）以及效果与成本的权衡。
:::

::: tip 💡 参考回答示范
> “我在百度文心一言企业版负责成本优化，当时单次问答平均消耗 1800 token，其中输入 1200，输出 600，按文心 4.0 的价格算，单次成本约 0.12 元。客户量大后，成本压力很大。我拆了成本结构，发现三个大头：第一，系统 prompt 太长，固定 400 token，每次请求都带；第二，历史对话全量传入，平均 500 token；第三，输出没有长度控制，模型经常啰嗦。
> 
> 我做了四件事：第一，系统 prompt 压缩，把 400 token 压到 150，去掉冗余示例，只保留核心指令和格式要求，样本是 1000 条请求，口径是人工评估压缩后效果不变。第二，历史对话做摘要，超过 3 轮的对话，用模型生成 100 token 的摘要替代原文，样本是 500 个多轮对话，口径是摘要后答案准确率下降不超过 2%。第三，模型路由，简单问题走文心 3.5，复杂问题走 4.0，路由准确率 88%，样本是 2000 条请求，口径是人工标注难度。第四，输出控制，在 prompt 里加‘回答不超过 200 字’，并设置 max_tokens=300，输出 token 从 600 降到 350。
> 
> 最终单次成本从 0.12 元降到 0.068 元，降幅 43%。效果上，人工评估答案质量从 4.2 分降到 4.1 分，基本持平。但这里有个坑：摘要会丢失细节，法务场景不能摘要，我们做了白名单，法务、医疗类请求不走摘要。
> 
> 风控上，模型路由如果误判，复杂问题走了小模型，答案质量会崩，所以我们加了兜底：小模型答案置信度低于阈值时，自动升级到大模型重试。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：系统 prompt 压缩到 150 token，怎么保证模型还能遵循格式要求？
  - **续答**：我们把格式要求做成结构化模板，比如用 JSON schema 定义输出字段，prompt 里只写‘按 schema 输出’，不写具体示例。样本是 500 条请求，口径是格式正确率。压缩前格式正确率 96%，压缩后 94%，下降 2 个点，可以接受。但有些客户要求特定措辞，比如‘必须用敬语’，这种就不能压，我们做成可配置的。
- **追问 2**：模型路由准确率 88%，那 12% 误判的 case 怎么处理？
  - **续答**：误判分两种：简单问题走了大模型，成本浪费但效果没问题；复杂问题走了小模型，答案质量差。我们重点处理第二种，小模型输出后过一个置信度分类器，低于 0.7 就升级到大模型。样本是 200 个误判 case，口径是人工判断是否复杂。升级后复杂问题答案质量从 3.2 分回到 4.0 分，但成本只增加了 5%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成阿里通义千问的成本优化，可以加入 Qwen 系列的多尺寸模型路由，0.5B 处理分类，7B 处理简单问答，72B 处理复杂推理，路由层用一个小模型做意图分类。
2. 如果换成华为盘古的政企场景，成本不是第一优先级，数据不出域才是，所以优化重点放在私有化部署的推理加速，比如量化、蒸馏，而不是模型路由。
3. 如果换成美团客服大模型，成本优化要结合业务峰值，高峰期用大模型保效果，低峰期用小模型省成本，动态切换，样本是 24 小时请求量，口径是每小时 QPS。
:::

### 题 35：美团 · 智能客服 Agent：高危写操作（如自动退款、修改订单）如何做风控，避免 Agent 误操作？

> 🏢 **真题来源**：美团 · 智能客服 Agent 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察 Agent 在高危写操作场景下的权限控制、二次确认、操作审计和回滚机制设计。
:::

::: tip 💡 参考回答示范
> “我在美团智能客服做 Agent 时，最怕的就是 Agent 自动退款。之前出过一次事故：用户说‘我昨天点的外卖没收到’，Agent 理解成‘要退款’，直接调了退款接口，退了 58 元。其实用户只是抱怨，没要求退款。我们复盘发现三个问题：第一，意图识别太激进，把‘没收到’映射成‘退款’；第二，写操作没有二次确认；第三，退款后没有通知用户。
> 
> 我重新设计了风控流程：第一，高危写操作分三级，L1 是查询类，直接执行；L2 是修改类，比如改地址，需要用户确认；L3 是资金类，比如退款、赔付，需要用户确认 + 人工审核。第二，L3 操作必须走‘确认卡片’，卡片里写明‘将退款 58 元到您的原支付账户’，用户点击‘确认退款’才执行。第三，所有写操作记录审计日志，包括用户 ID、操作类型、金额、时间、Agent 版本，样本是 5000 次写操作，口径是全部 L2 和 L3 操作。
> 
> 指标上，误操作率从 3.2% 降到 0.1%，样本是 5000 次写操作，口径是人工复核确认的误操作。但确认卡片导致转化率下降，用户确认率只有 65%，因为有些用户觉得麻烦。我们优化了卡片文案，把‘确认退款’改成‘退款 58 元，预计 2 小时到账’，确认率提到 82%。
> 
> 回滚机制上，退款操作如果发现错误，支持 24 小时内原路追回，但需要人工介入。我们设了熔断：同一用户 1 小时内触发 3 次 L3 操作，自动转人工。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：确认卡片会不会被用户误点？比如用户没看清就点了确认。
  - **续答**：会。我们做了防误点设计：第一，确认按钮不是默认焦点，需要用户主动点击；第二，卡片展示 3 秒后才能点击确认；第三，金额超过 100 元需要输入支付密码。样本是 1000 次 L3 操作，口径是用户误点率。防误点后误点率从 1.5% 降到 0.3%。但输入密码会降低体验，我们只对高风险场景用。
- **追问 2**：如果 Agent 判断错了，用户确认了，责任算谁的？
  - **续答**：产品设计上，确认卡片明确写了‘请确认退款信息’，用户点击确认视为授权。但我们会保留 Agent 的原始意图识别记录，如果发现是 Agent 误判，比如用户根本没提退款，我们会主动赔付并优化模型。样本是 50 个争议 case，口径是用户投诉。法律上，我们和法务对齐过，确认卡片是用户授权的证据，但 Agent 误判我们还是要兜底。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成滴滴的行程修改 Agent，高危操作是改目的地、改时间，风控要加上司机端确认，因为改目的地影响司机收入，必须双方确认。
2. 如果换成蚂蚁的理财 Agent，高危操作是赎回、转账，风控要加上风险测评和限额，单笔超过 1 万需要人脸识别，样本是 2000 次操作，口径是监管要求。
3. 如果换成小红书的笔记删除 Agent，高危操作是删除笔记，风控要加上回收站，删除后 30 天内可恢复，避免用户误删。
:::

### 题 36：快手 · 可灵 AI：视频生成首帧延迟高导致用户放弃，如何从产品和技术侧优化？

> 🏢 **真题来源**：快手 · 可灵 AI / 多模态生成大模型产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察多模态生成产品的性能优化，包括首帧延迟拆解、排队策略、预览降级和用户预期管理。
:::

::: tip 💡 参考回答示范
> “我在可灵 AI 做视频生成产品时，用户从点击‘生成’到看到第一帧，平均要等 45 秒，导致 30% 的用户在 20 秒内就退出了。我们拆了延迟：排队 15 秒，模型推理 25 秒，后处理 5 秒。排队是因为 GPU 资源不足，推理是因为视频扩散模型本身慢。
> 
> 我做了四件事：第一，排队策略优化，把用户按会员等级分队列，免费用户排长队，会员排短队，样本是 10000 次生成请求，口径是排队时间。会员排队从 15 秒降到 5 秒，免费用户从 15 秒升到 25 秒，但免费用户本来就不付费，流失影响小。第二，首帧预览降级，先生成低分辨率首帧（256x256），5 秒内展示，让用户知道在生成，样本是 5000 次请求，口径是首帧展示时间。首帧从 45 秒降到 5 秒，用户 20 秒退出率从 30% 降到 12%。第三，推理加速，用 TensorRT 和量化，推理从 25 秒降到 18 秒。第四，预期管理，进度条按真实进度走，不要卡在 99%，并显示‘预计还需 20 秒’。
> 
> 最终端到端首帧时间从 45 秒降到 12 秒，用户放弃率从 30% 降到 8%。但低分辨率首帧有个问题：用户觉得画质差，我们加了‘预览图，最终效果更清晰’的文案。
> 
> 风控上，排队策略不能歧视免费用户太明显，我们设了上限：免费用户排队不超过 30 秒，超过就送一次快速通道。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：低分辨率首帧 5 秒展示，但最终视频可能和首帧差异很大，用户会不会觉得被骗？
  - **续答**：会。我们做了两件事：第一，首帧只展示构图和主体，不展示细节，避免用户对画质有预期；第二，如果最终视频和首帧差异超过阈值，比如主体变了，我们主动提示‘生成结果与预览有差异，可重新生成’。样本是 1000 次生成，口径是人工评估差异。差异率从 15% 降到 8%。
- **追问 2**：会员优先排队，免费用户排队 25 秒，会不会导致免费用户流失？
  - **续答**：会。我们看了数据，免费用户排队超过 20 秒，次日留存下降 5 个百分点。所以加了补偿：排队超过 20 秒送一次快速通道，下次生成免排队。样本是 5000 个免费用户，口径是次日留存。补偿后留存回升 3 个百分点。但快速通道成本高，我们限制每人每天最多送 1 次。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成剪映的 AI 视频生成，首帧延迟优化可以结合本地预览，用端侧小模型生成低质量预览，云端生成高质量，用户感知更快。
2. 如果换成小红书的 AI 配图生成，首帧延迟要求更高，因为用户发笔记时希望即时看到图，可以用缓存相似 prompt 的结果，命中缓存直接返回。
3. 如果换成腾讯混元的文生图，首帧延迟优化可以加入批量生成，一次生成 4 张低分辨率图，用户选一张后再高清放大，降低等待感。
:::
