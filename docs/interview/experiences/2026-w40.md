### 题 1：字节跳动飞书智能助手：如何设计企业知识库RAG的检索与切分策略？

> 🏢 **真题来源**：字节跳动 · 飞书智能助手 / 企业知识库RAG产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：核心考察RAG系统中文档切分粒度、检索召回与重排的工程化权衡，以及如何平衡回答准确率与响应延迟。
:::

::: tip 💡 参考回答示范
> “我负责过飞书智能助手的企业知识库问答模块。当时业务痛点是员工搜索内部文档时，答案经常不完整或答非所问。我们样本是5000份飞书文档和1000条真实员工提问，口径是回答准确率（人工评估）和端到端延迟。首先，切分策略上，我们没有用固定长度，而是基于文档结构：标题、列表、表格分别处理。标题作为元数据，列表按项切分，表格转为Markdown后按行切分并保留表头。每个chunk控制在200-400字，重叠50字。检索阶段，我们用了混合检索：BM25召回Top 50，向量检索（用bge-large-zh）召回Top 50，然后合并去重，用交叉编码器重排Top 10。为了降低延迟，向量检索用了HNSW索引，重排模型用了蒸馏版。最终准确率从62%提升到85%，P99延迟从3.2秒降到1.8秒。关键决策是：对于表格类查询，我们额外增加了表头匹配的规则召回，因为向量模型对表格结构不敏感。另外，我们设置了兜底策略：如果重排后最高分低于阈值，就返回“未找到相关文档”并引导用户缩小范围。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果文档更新频繁，如何保证检索的实时性？
  - **续答**：我们设计了增量索引管道：文档变更时，通过飞书开放平台的事件订阅触发重新切分和向量化，只更新变化的chunk。向量库支持upsert，BM25索引也做增量更新。对于删除操作，我们做了软删除标记，检索时过滤。为了应对突发大量更新，我们用了消息队列削峰，并设置索引版本号，确保检索时看到一致快照。实测文档更新后，新内容在30秒内可被检索到。
- **追问 2**：如何评估RAG系统的回答质量？
  - **续答**：我们构建了包含500个问题的评测集，覆盖事实型、对比型、总结型。人工标注了标准答案和关键点。自动评估用ROUGE和BERTScore，但主要看人工评估的准确率和完整性。我们还监控了“无答案率”和“用户点踩率”，作为线上反馈。每周抽样100条线上日志做人工复核，发现badcase就归因到切分、检索或生成环节。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成钉钉知识库，需要适配钉钉文档的API和权限体系，切分时注意钉钉的富文本格式。
2. 如果换成微信客服场景，需考虑短文本和口语化查询，检索时增加同义词扩展和意图识别。
3. 如果换成内部Wiki，可以引入用户点击行为作为弱监督信号，优化重排模型。
:::

### 题 2：阿里巴巴国际站：如何用Agent工作流自动处理买家询盘并生成报价？

> 🏢 **真题来源**：阿里巴巴 · 国际站AI外贸助手 / Agent工作流编排面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察多步骤Agent编排中的状态管理、工具调用、异常处理与人工兜底机制，以及如何量化业务提效。
:::

::: tip 💡 参考回答示范
> “我在国际站负责过一个询盘自动处理Agent。业务场景是：买家发来询盘，Agent需要理解需求、查询商品库、计算价格、生成报价单并回复。样本是过去3个月5000条真实询盘，口径是自动处理率（无需人工介入）和报价准确率。我们用了LangChain式的编排，但自研了状态机。流程分四步：1）意图识别和实体抽取，用微调的BERT模型，抽取产品、数量、目标价等；2）工具调用，包括商品搜索API、价格计算API、库存API；3）报价单生成，用LLM填充模板；4）发送前审核，如果价格低于底价或库存不足，转人工。关键点是状态管理：每个步骤的输出作为下一步输入，并记录中间状态，便于回溯。异常处理上，如果工具调用超时或返回错误，重试2次后转人工。最终自动处理率达到65%，报价准确率98%（人工抽检200条）。我们设置了风控规则：报价必须经过价格校验，且不能承诺交期，这些由规则引擎硬编码，不交给LLM。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何防止Agent被恶意询盘诱导给出错误报价？
  - **续答**：我们做了三层防护：第一，输入过滤，识别垃圾询盘和注入攻击；第二，工具调用时，价格计算API只接受结构化参数，且参数范围有限制；第三，输出前用规则引擎校验，比如折扣率不能超过阈值。另外，我们记录了所有Agent的决策日志，定期审计。
- **追问 2**：如果商品库有百万级SKU，如何快速检索？
  - **续答**：我们用了向量检索加关键词过滤。先将商品标题和属性向量化，存到Milvus。查询时，先提取关键属性做过滤，再向量检索Top 20，然后用精排模型排序。为了降低延迟，我们做了两级缓存：热门商品缓存和查询结果缓存。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成淘宝客服，需处理更口语化的表达，并接入订单和物流API。
2. 如果换成跨境支付场景，需增加汇率转换和合规检查工具。
3. 如果换成B2B批发，报价需考虑阶梯价格和MOQ，工具调用更复杂。
:::

### 题 3：腾讯会议：如何设计大模型长程评测方案以保障会议纪要质量？

> 🏢 **真题来源**：腾讯 · 腾讯会议AI小助手 / 大模型长程评测面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察长文本场景下的评测集构建、指标设计、人工与自动评估结合，以及如何持续监控线上质量。
:::

::: tip 💡 参考回答示范
> “我负责腾讯会议AI纪要的评测。会议纪要的特点是长文本（1小时会议约1万字）和多说话人。样本是200场真实会议，覆盖不同行业和口音，口径是纪要的完整性、准确性和可读性。我们构建了分层评测集：第一层是事实性，抽取会议中的关键决策、待办、时间点，人工标注标准答案，计算召回率和准确率；第二层是摘要质量，用ROUGE和BERTScore，但更看重人工评分（1-5分）；第三层是格式，检查是否包含决议、待办、责任人等结构化字段。自动评估上，我们训练了一个小模型来预测人工评分，相关性达到0.85。线上监控方面，我们每天抽样100条纪要，人工快速标注，如果连续3天评分下降超过10%，就触发告警。我们还做了A/B测试，对比不同LLM版本。关键点是：长文本评测不能只看整体，要分段落评估，因为模型可能在中间部分丢失信息。我们用了“关键信息点”的方式，每个会议标注10-20个关键点，检查纪要是否覆盖。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何评估多说话人场景下的纪要准确性？
  - **续答**：我们增加了说话人归属的评估：检查每个待办是否关联到正确的说话人。人工标注时，会标记说话人ID。自动评估用说话人识别准确率，目前是92%。对于归属错误，我们会在后处理中用规则修正，比如根据上下文判断。
- **追问 2**：如果会议中有专业术语，如何保证纪要质量？
  - **续答**：我们构建了行业术语库，在ASR和LLM阶段都做了热词增强。评测时，专门抽取包含术语的片段，检查是否准确。另外，我们允许用户自定义术语，并实时生效。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成飞书妙记，需适配飞书的文档格式和协作功能。
2. 如果换成英文会议，需考虑语言差异和跨文化表达。
3. 如果换成电话会议，需处理低质量音频和更少的视觉线索。
:::

### 题 4：百度文心一言：如何计算和优化大模型推理的Token成本？

> 🏢 **真题来源**：百度 · 文心一言企业版 / Token成本算账面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对LLM推理成本结构的理解，包括输入输出Token、缓存、批处理、模型选择等，以及如何平衡成本与效果。
:::

::: tip 💡 参考回答示范
> “我在百度文心一言企业版负责成本优化。当时业务方抱怨API调用费用太高。样本是过去一个月100万次调用，口径是每千Token成本和平均响应时间。我们首先做了成本拆解：输入Token占60%，输出Token占40%。优化措施：1）输入侧，压缩Prompt，去掉冗余示例，用系统指令替代少样本示例，平均减少30%输入Token；2）输出侧，设置max_tokens，并让模型学会简洁回答，通过微调降低输出长度；3）缓存，对常见问题（如FAQ）的答案进行缓存，命中率25%，直接节省这部分成本；4）批处理，将多个请求合并成一个批次，提高GPU利用率，但会增加延迟，我们只对非实时场景使用；5）模型选择，简单任务用ERNIE Tiny，复杂任务用ERNIE 4.0，通过路由模型自动选择。最终每千Token成本降低45%，响应时间基本不变。我们还建立了成本监控看板，按业务线分摊，每周review。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何评估缓存策略对回答质量的影响？
  - **续答**：我们只对确定性高的问题缓存，比如“公司地址”。缓存前会人工审核一批，确保答案准确。线上监控缓存命中的用户满意度，如果低于非缓存，就调整缓存范围。
- **追问 2**：如果业务要求低延迟，如何平衡批处理？
  - **续答**：我们区分实时和非实时场景。实时场景不用批处理，而是用动态批处理（连续批处理）技术，在GPU上同时处理多个请求，但每个请求独立返回。这需要推理框架支持，我们用了vLLM。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成阿里通义千问，需考虑其计费方式和模型版本差异。
2. 如果换成自研模型，需计算GPU折旧和电费，而不仅是API费用。
3. 如果换成边缘设备，需考虑内存和算力限制，可能用量化模型。
:::

### 题 5：美团：如何设计高危写操作的风控机制防止AI误操作？

> 🏢 **真题来源**：美团 · 美团智能客服 / 高危写操作风控面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察AI产品在涉及资金、权限等写操作时的安全设计，包括权限控制、二次确认、审计日志和熔断机制。
:::

::: tip 💡 参考回答示范
> “我在美团智能客服负责退款和改单等写操作。这些操作一旦出错，会导致资损或用户投诉。样本是过去半年10万次写操作请求，口径是误操作率和拦截率。我们设计了四层风控：第一层，意图识别，只有明确且置信度高于0.95的请求才进入写操作流程，否则转人工；第二层，权限校验，AI只能操作授权范围内的订单，且金额超过500元必须人工审批；第三层，二次确认，AI会向用户复述操作内容，用户确认后才执行；第四层，执行前校验，调用业务API前，检查订单状态、用户身份等，防止条件不满足。我们还设置了熔断：如果某类操作失败率超过5%，自动暂停AI执行，转人工。审计日志记录所有AI决策和操作，便于回溯。最终误操作率从0.5%降到0.1%，拦截了2000次高风险请求。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何防止用户诱导AI进行未授权的操作？
  - **续答**：我们做了对抗训练，让模型识别诱导性语言。同时，权限校验是硬性的，不依赖模型判断。即使模型被诱导，API层也会拒绝。
- **追问 2**：如果AI误操作已经发生，如何快速补救？
  - **续答**：我们设计了回滚机制，对于可逆操作（如退款），支持一键撤销。对于不可逆操作，有应急流程，客服可手动补偿。同时，我们会分析误操作原因，更新风控规则。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成滴滴行程修改，需考虑实时位置和司机接单状态。
2. 如果换成银行转账，需增加生物识别和多重审批。
3. 如果换成电商改价，需考虑促销规则和库存影响。
:::

### 题 6：小红书：如何利用多模态大模型提升笔记审核效率？

> 🏢 **真题来源**：小红书 · 社区内容安全 / 多模态审核面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察多模态模型在内容审核中的应用，包括图文匹配、违规识别、误杀与漏杀平衡，以及人机协同流程。
:::

::: tip 💡 参考回答示范
> “我在小红书负责笔记审核的多模态升级。之前审核主要靠文本和图像分开，漏杀率较高。样本是100万条笔记，口径是违规召回率和误杀率。我们引入了多模态大模型，同时理解图片和文本，判断是否违规。具体做法：1）用CLIP-like模型做图文匹配，检测图文不符（如用美女图卖假货）；2）用多模态LLM对疑似违规内容进行细粒度分类，比如软色情、违禁品等；3）对于高风险类别，直接机审拦截，低风险转人工。为了降低误杀，我们设置了置信度阈值，只有高于0.9才自动拦截，0.7-0.9转人工复核。同时，我们构建了对抗样本库，持续训练模型。最终违规召回率从85%提升到95%，误杀率从2%降到0.8%。人机协同上，机审覆盖80%的流量，人工只处理疑难。我们还做了可解释性，模型会输出违规原因，帮助人工快速判断。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何应对新型违规内容？
  - **续答**：我们建立了主动学习循环：人工审核中发现的漏杀样本，会加入训练集，每周更新模型。同时，用异常检测发现新违规模式。
- **追问 2**：多模态模型推理成本高，如何优化？
  - **续答**：我们用了模型蒸馏，将大模型能力蒸馏到小模型，部署在边缘。对于简单任务，用小模型；复杂任务才用大模型。另外，我们用了缓存，相同图片哈希只推理一次。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成抖音短视频审核，需处理视频帧和音频，时序信息更复杂。
2. 如果换成淘宝商品审核，需结合商品类目和属性。
3. 如果换成微信朋友圈审核，需考虑隐私和社交关系。
:::
