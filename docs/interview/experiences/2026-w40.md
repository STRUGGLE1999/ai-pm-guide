### 题 1：字节跳动飞书智能助手：如何设计企业知识库RAG的检索与切分策略？

> 🏢 **真题来源**：字节跳动 · 飞书智能助手 / 企业知识库RAG产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：核心考察RAG系统中文档切分粒度、检索召回与重排的工程化权衡，以及如何平衡回答准确率与响应延迟。
:::

::: tip 💡 参考回答示范
> “我负责过飞书智能助手的企业知识库问答模块。当时业务痛点是员工搜索内部文档时，答案经常不完整或答非所问。我们样本是5000份飞书文档和1000条真实员工提问，口径是回答准确率（人工评估）和端到端延迟。首先，切分策略上，我们没有用固定长度，而是基于文档结构：标题、列表、表格分别处理。标题作为元数据，列表按项切分，表格转为Markdown后按行切分并保留表头。每个chunk控制在200-400字，重叠50字。检索阶段，我们用了混合检索：BM25召回Top 50，向量检索（用bge-large-zh）召回Top 50，然后合并去重，用交叉编码器重排Top 10。为了降低延迟，向量检索用了HNSW索引，重排模型用了蒸馏版。最终准确率从62%提升到85%，P99延迟从3.2秒降到1.8秒。关键决策是：对于表格类查询，我们额外增加了表头匹配的规则召回，因为向量模型对表格结构不敏感。另外，我们设置了兜底策略：如果重排后最高分低于阈值，就返回“未找到相关文档”并引导用户缩小范围。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果文档更新频繁，如何保证检索的实时性？
  - **续答**：我们设计了增量索引管道：文档变更时，通过飞书开放平台的事件订阅触发重新切分和向量化，只更新变化的chunk。向量库支持upsert，BM25索引也做增量更新。对于删除操作，我们做了软删除标记，检索时过滤。为了应对突发大量更新，我们用了消息队列削峰，并设置索引版本号，确保检索时看到一致快照。实测文档更新后，新内容在30秒内可被检索到。
- **追问 2**：如何评估RAG系统的回答质量？
  - **续答**：我们构建了包含500个问题的评测集，覆盖事实型、对比型、总结型。人工标注了标准答案和关键点。自动评估用ROUGE和BERTScore，但主要看人工评估的准确率和完整性。我们还监控了“无答案率”和“用户点踩率”，作为线上反馈。每周抽样100条线上日志做人工复核，发现badcase就归因到切分、检索或生成环节。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成钉钉知识库，需要适配钉钉文档的API和权限体系，切分时注意钉钉的富文本格式。
2. 如果换成微信客服场景，需考虑短文本和口语化查询，检索时增加同义词扩展和意图识别。
3. 如果换成内部Wiki，可以引入用户点击行为作为弱监督信号，优化重排模型。
:::

### 题 2：阿里巴巴国际站：如何用Agent工作流自动处理买家询盘并生成报价？

> 🏢 **真题来源**：阿里巴巴 · 国际站AI外贸助手 / Agent工作流编排面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察多步骤Agent编排中的状态管理、工具调用、异常处理与人工兜底机制，以及如何量化业务提效。
:::

::: tip 💡 参考回答示范
> “我在国际站负责过一个询盘自动处理Agent。业务场景是：买家发来询盘，Agent需要理解需求、查询商品库、计算价格、生成报价单并回复。样本是过去3个月5000条真实询盘，口径是自动处理率（无需人工介入）和报价准确率。我们用了LangChain式的编排，但自研了状态机。流程分四步：1）意图识别和实体抽取，用微调的BERT模型，抽取产品、数量、目标价等；2）工具调用，包括商品搜索API、价格计算API、库存API；3）报价单生成，用LLM填充模板；4）发送前审核，如果价格低于底价或库存不足，转人工。关键点是状态管理：每个步骤的输出作为下一步输入，并记录中间状态，便于回溯。异常处理上，如果工具调用超时或返回错误，重试2次后转人工。最终自动处理率达到65%，报价准确率98%（人工抽检200条）。我们设置了风控规则：报价必须经过价格校验，且不能承诺交期，这些由规则引擎硬编码，不交给LLM。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何防止Agent被恶意询盘诱导给出错误报价？
  - **续答**：我们做了三层防护：第一，输入过滤，识别垃圾询盘和注入攻击；第二，工具调用时，价格计算API只接受结构化参数，且参数范围有限制；第三，输出前用规则引擎校验，比如折扣率不能超过阈值。另外，我们记录了所有Agent的决策日志，定期审计。
- **追问 2**：如果商品库有百万级SKU，如何快速检索？
  - **续答**：我们用了向量检索加关键词过滤。先将商品标题和属性向量化，存到Milvus。查询时，先提取关键属性做过滤，再向量检索Top 20，然后用精排模型排序。为了降低延迟，我们做了两级缓存：热门商品缓存和查询结果缓存。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成淘宝客服，需处理更口语化的表达，并接入订单和物流API。
2. 如果换成跨境支付场景，需增加汇率转换和合规检查工具。
3. 如果换成B2B批发，报价需考虑阶梯价格和MOQ，工具调用更复杂。
:::

### 题 3：腾讯会议：如何设计大模型长程评测方案以保障会议纪要质量？

> 🏢 **真题来源**：腾讯 · 腾讯会议AI小助手 / 大模型长程评测面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察长文本场景下的评测集构建、指标设计、人工与自动评估结合，以及如何持续监控线上质量。
:::

::: tip 💡 参考回答示范
> “我负责腾讯会议AI纪要的评测。会议纪要的特点是长文本（1小时会议约1万字）和多说话人。样本是200场真实会议，覆盖不同行业和口音，口径是纪要的完整性、准确性和可读性。我们构建了分层评测集：第一层是事实性，抽取会议中的关键决策、待办、时间点，人工标注标准答案，计算召回率和准确率；第二层是摘要质量，用ROUGE和BERTScore，但更看重人工评分（1-5分）；第三层是格式，检查是否包含决议、待办、责任人等结构化字段。自动评估上，我们训练了一个小模型来预测人工评分，相关性达到0.85。线上监控方面，我们每天抽样100条纪要，人工快速标注，如果连续3天评分下降超过10%，就触发告警。我们还做了A/B测试，对比不同LLM版本。关键点是：长文本评测不能只看整体，要分段落评估，因为模型可能在中间部分丢失信息。我们用了“关键信息点”的方式，每个会议标注10-20个关键点，检查纪要是否覆盖。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何评估多说话人场景下的纪要准确性？
  - **续答**：我们增加了说话人归属的评估：检查每个待办是否关联到正确的说话人。人工标注时，会标记说话人ID。自动评估用说话人识别准确率，目前是92%。对于归属错误，我们会在后处理中用规则修正，比如根据上下文判断。
- **追问 2**：如果会议中有专业术语，如何保证纪要质量？
  - **续答**：我们构建了行业术语库，在ASR和LLM阶段都做了热词增强。评测时，专门抽取包含术语的片段，检查是否准确。另外，我们允许用户自定义术语，并实时生效。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成飞书妙记，需适配飞书的文档格式和协作功能。
2. 如果换成英文会议，需考虑语言差异和跨文化表达。
3. 如果换成电话会议，需处理低质量音频和更少的视觉线索。
:::

### 题 4：百度文心一言：如何计算和优化大模型推理的Token成本？

> 🏢 **真题来源**：百度 · 文心一言企业版 / Token成本算账面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对LLM推理成本结构的理解，包括输入输出Token、缓存、批处理、模型选择等，以及如何平衡成本与效果。
:::

::: tip 💡 参考回答示范
> “我在百度文心一言企业版负责成本优化。当时业务方抱怨API调用费用太高。样本是过去一个月100万次调用，口径是每千Token成本和平均响应时间。我们首先做了成本拆解：输入Token占60%，输出Token占40%。优化措施：1）输入侧，压缩Prompt，去掉冗余示例，用系统指令替代少样本示例，平均减少30%输入Token；2）输出侧，设置max_tokens，并让模型学会简洁回答，通过微调降低输出长度；3）缓存，对常见问题（如FAQ）的答案进行缓存，命中率25%，直接节省这部分成本；4）批处理，将多个请求合并成一个批次，提高GPU利用率，但会增加延迟，我们只对非实时场景使用；5）模型选择，简单任务用ERNIE Tiny，复杂任务用ERNIE 4.0，通过路由模型自动选择。最终每千Token成本降低45%，响应时间基本不变。我们还建立了成本监控看板，按业务线分摊，每周review。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何评估缓存策略对回答质量的影响？
  - **续答**：我们只对确定性高的问题缓存，比如“公司地址”。缓存前会人工审核一批，确保答案准确。线上监控缓存命中的用户满意度，如果低于非缓存，就调整缓存范围。
- **追问 2**：如果业务要求低延迟，如何平衡批处理？
  - **续答**：我们区分实时和非实时场景。实时场景不用批处理，而是用动态批处理（连续批处理）技术，在GPU上同时处理多个请求，但每个请求独立返回。这需要推理框架支持，我们用了vLLM。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成阿里通义千问，需考虑其计费方式和模型版本差异。
2. 如果换成自研模型，需计算GPU折旧和电费，而不仅是API费用。
3. 如果换成边缘设备，需考虑内存和算力限制，可能用量化模型。
:::

### 题 5：美团：如何设计高危写操作的风控机制防止AI误操作？

> 🏢 **真题来源**：美团 · 美团智能客服 / 高危写操作风控面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察AI产品在涉及资金、权限等写操作时的安全设计，包括权限控制、二次确认、审计日志和熔断机制。
:::

::: tip 💡 参考回答示范
> “我在美团智能客服负责退款和改单等写操作。这些操作一旦出错，会导致资损或用户投诉。样本是过去半年10万次写操作请求，口径是误操作率和拦截率。我们设计了四层风控：第一层，意图识别，只有明确且置信度高于0.95的请求才进入写操作流程，否则转人工；第二层，权限校验，AI只能操作授权范围内的订单，且金额超过500元必须人工审批；第三层，二次确认，AI会向用户复述操作内容，用户确认后才执行；第四层，执行前校验，调用业务API前，检查订单状态、用户身份等，防止条件不满足。我们还设置了熔断：如果某类操作失败率超过5%，自动暂停AI执行，转人工。审计日志记录所有AI决策和操作，便于回溯。最终误操作率从0.5%降到0.1%，拦截了2000次高风险请求。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何防止用户诱导AI进行未授权的操作？
  - **续答**：我们做了对抗训练，让模型识别诱导性语言。同时，权限校验是硬性的，不依赖模型判断。即使模型被诱导，API层也会拒绝。
- **追问 2**：如果AI误操作已经发生，如何快速补救？
  - **续答**：我们设计了回滚机制，对于可逆操作（如退款），支持一键撤销。对于不可逆操作，有应急流程，客服可手动补偿。同时，我们会分析误操作原因，更新风控规则。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成滴滴行程修改，需考虑实时位置和司机接单状态。
2. 如果换成银行转账，需增加生物识别和多重审批。
3. 如果换成电商改价，需考虑促销规则和库存影响。
:::

### 题 6：小红书：如何利用多模态大模型提升笔记审核效率？

> 🏢 **真题来源**：小红书 · 社区内容安全 / 多模态审核面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察多模态模型在内容审核中的应用，包括图文匹配、违规识别、误杀与漏杀平衡，以及人机协同流程。
:::

::: tip 💡 参考回答示范
> “我在小红书负责笔记审核的多模态升级。之前审核主要靠文本和图像分开，漏杀率较高。样本是100万条笔记，口径是违规召回率和误杀率。我们引入了多模态大模型，同时理解图片和文本，判断是否违规。具体做法：1）用CLIP-like模型做图文匹配，检测图文不符（如用美女图卖假货）；2）用多模态LLM对疑似违规内容进行细粒度分类，比如软色情、违禁品等；3）对于高风险类别，直接机审拦截，低风险转人工。为了降低误杀，我们设置了置信度阈值，只有高于0.9才自动拦截，0.7-0.9转人工复核。同时，我们构建了对抗样本库，持续训练模型。最终违规召回率从85%提升到95%，误杀率从2%降到0.8%。人机协同上，机审覆盖80%的流量，人工只处理疑难。我们还做了可解释性，模型会输出违规原因，帮助人工快速判断。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如何应对新型违规内容？
  - **续答**：我们建立了主动学习循环：人工审核中发现的漏杀样本，会加入训练集，每周更新模型。同时，用异常检测发现新违规模式。
- **追问 2**：多模态模型推理成本高，如何优化？
  - **续答**：我们用了模型蒸馏，将大模型能力蒸馏到小模型，部署在边缘。对于简单任务，用小模型；复杂任务才用大模型。另外，我们用了缓存，相同图片哈希只推理一次。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成抖音短视频审核，需处理视频帧和音频，时序信息更复杂。
2. 如果换成淘宝商品审核，需结合商品类目和属性。
3. 如果换成微信朋友圈审核，需考虑隐私和社交关系。
:::

### 题 7：字节跳动飞书智能伙伴：如何设计多轮工具调用的Agent工作流，避免死循环与Token爆炸？

> 🏢 **真题来源**：字节跳动 · 飞书智能伙伴 / Agent平台产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察Agent工作流编排中对工具调用链路的控制能力，包括循环检测、预算控制与状态管理。
:::

::: tip 💡 参考回答示范
> “我在飞书智能伙伴项目里负责过Agent工具调用的链路设计。当时业务方要求智能伙伴能自动查日程、发消息、改文档，但测试时经常出现模型反复调用同一个接口，或者陷入'查不到就重试'的死循环，一次对话消耗几万Token。我的解法是三层控制：第一，在编排层加一个'调用轨迹栈'，记录每一步的tool_name和参数指纹，如果连续两次调用相同工具且参数相似度超过0.9，就强制中断并返回兜底话术，比如'我暂时无法完成这个操作，建议您手动处理'。第二，给每个会话设置硬性Token预算，比如单轮对话上限8000 Token，达到阈值后自动降级为纯文本回复并提示用户'当前操作较复杂，请简化需求'。第三，用状态机管理任务阶段，把'查日程-改日程-发通知'拆成三个独立状态，每个状态只允许调用特定工具集，避免模型自由发挥。上线后死循环率从12%降到0.8%，单次任务平均Token消耗从1.2万降到4500。样本是飞书内部200个真实用户一周的日志，口径是单次用户主动发起的任务会话。这里严禁编造，所有数字都来自我们埋点统计。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果模型在某个状态下反复调用工具但参数不同，比如每次改一点时间，你怎么判断是正常迭代还是无效循环？
  - **续答**：我会引入'目标漂移检测'。在状态机里为每个任务预设一个目标向量，比如'改日程'的目标是最终确认一个时间点。每次工具调用后，计算当前结果与目标的语义距离，如果距离连续三次没有缩小，就判定为无效循环，触发人工确认或终止。同时设置最大迭代次数，比如改日程最多允许5次尝试，超过就转人工。
- **追问 2**：Token预算用完后直接降级，会不会导致用户体验断裂？有没有更平滑的降级策略？

::: warning ⚠️ 连环追问与高分续答

- **追问 2**：如果商品描述本身结构混乱，没有明确规格表，怎么切分？
  - **续答**：我会先用小模型做结构识别，把文本分成'属性-值'对。如果识别失败，就退化为滑动窗口切分，窗口大小256 Token，重叠50 Token，并给每个chunk打上'低置信度'标签，生成时提示用户'该信息可能不完整，请核实'。

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户连续追问同一个工具，但每次参数都不同，状态机怎么处理？
  - **续答**：我会把工具调用参数作为状态的一部分存下来，每次新参数进来先做参数差异比对。如果参数变化在允许范围内（比如时间偏移不超过 1 小时），就合并成一次调用；如果变化太大，就重置状态机到‘工具就绪’并重新收集参数。同时会记录参数变更次数，超过 3 次就主动询问用户是否要放弃当前任务。
- **追问 2**：状态机持久化到 Redis 后，如何保证多实例部署下的并发一致性？
  - **续答**：我们用的是 Redis 分布式锁，key 是会话 ID，锁超时 5 秒。每次状态变更前先获取锁，变更后释放。如果获取锁失败，就返回‘系统繁忙，请重试’。另外，状态数据用 Hash 结构存储，每个字段单独更新，避免全量覆盖。监控上会统计锁等待时长和失败率，超过阈值就告警。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成钉钉场景：把飞书工具链换成钉钉的审批、考勤、日志接口，状态机不变，但需要适配钉钉的异步回调机制。
2. 换成微信客服场景：状态机增加‘转人工’状态，因为微信侧用户期望快速响应，工具调用失败直接转人工。
3. 换成内部 IT 运维 Agent：工具调用变成重启服务、查日志等，风控要求更高，所有写操作需要工单审批。
:::

### 题 14：阿里巴巴 RAG 检索增强生成中，如何设计切分策略以平衡召回与精度？

> 🏢 **真题来源**：阿里巴巴 · 通义千问 / 企业知识库 RAG 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察文档切分粒度、重叠窗口、元数据过滤对检索效果的影响，本质是信息检索中的召回率与准确率权衡。
:::

::: tip 💡 参考回答示范
> “在通义千问企业知识库项目中，我负责设计切分策略。样本是 5000 份产品文档，口径是人工标注的 200 个问答对。我们对比了三种切分方式：固定 512 token 切分、按段落切分、按语义相似度切分。固定切分召回率 78%，但精度只有 62%，因为很多答案被切到两个块里；按段落切分召回率 85%，精度 74%；语义切分召回率 91%，精度 82%，但计算成本高。最终我们采用混合策略：先用段落切分作为基础，再对超过 800 token 的段落用语义相似度二次切分，重叠窗口设 128 token。元数据上，每个块都带上文档标题、章节、更新时间，检索时先按元数据过滤（比如只搜最近 3 个月的文档），再做向量检索。重排序阶段用 cross-encoder 对 top 20 结果重新打分，取 top 5 送给 LLM。指标上，端到端回答准确率从 68% 提升到 86%。成本方面，切分和索引是一次性开销，检索时向量搜索延迟在 50ms 以内。风控上，如果检索结果相似度低于 0.7，就触发‘未找到相关内容’的兜底回复。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果文档更新频繁，如何避免旧块残留导致检索到过时信息？
  - **续答**：我们给每个块加了版本号和生效时间。文档更新时，先标记旧块为失效，再插入新块。检索时过滤掉失效块。另外，每天凌晨跑一次全量索引重建，确保一致性。监控上会统计失效块占比，超过 10% 就告警。
- **追问 2**：语义切分具体怎么实现？用了什么模型？
  - **续答**：我们用 BERT 做句子嵌入，计算相邻句子的余弦相似度，低于阈值 0.6 就切分。模型是开源的 paraphrase-multilingual-MiniLM，部署在 GPU 上，切分 5000 份文档耗时约 2 小时。为了降本，我们只对超过 800 token 的段落做语义切分，其余用段落切分。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成腾讯文档场景：文档类型更多（表格、PPT），需要针对不同格式设计切分规则，表格按行切分，PPT 按页切分。
2. 换成百度搜索场景：检索结果需要实时性，切分策略要更轻量，可能用固定 256 token 切分，牺牲一点精度换速度。
3. 换成小红书笔记场景：文本短且口语化，切分粒度可以更细，比如按句子切分，重叠窗口设 64 token。
:::

### 题 15：腾讯混元大模型长程评测如何设计多轮对话的自动化打分体系？

> 🏢 **真题来源**：腾讯 · 混元大模型 / 对话评测产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察长程对话中一致性、连贯性、任务完成度的自动化评估方法，本质是 NLP 评测中的指标设计与人工对齐。
:::

::: tip 💡 参考回答示范
> “在混元大模型长程评测项目中，我设计了一套自动化打分体系。样本是 1000 组多轮对话，每组 5-10 轮，口径是人工标注的 4 个维度：一致性、连贯性、任务完成度、安全性。自动化打分用 GPT-4 作为裁判，但直接打分与人工相关性只有 0.6。后来我们改成 pairwise 比较：让 GPT-4 对比两个模型的回复，选出更好的，准确率提升到 0.78。具体做法是：每轮对话后，把历史上下文和当前回复一起给裁判，裁判输出 A/B 或平局。为了降低成本，我们只对关键轮次（如任务完成轮）做 pairwise，其他轮次用规则打分（如重复率、长度）。一致性用实体追踪：提取对话中的实体，检查前后是否矛盾。连贯性用句子嵌入的余弦相似度。任务完成度用槽位填充率。安全性用敏感词库加分类器。最终综合得分是加权平均，权重通过人工标注数据拟合。指标上，自动化得分与人工评分的 Spearman 相关系数达到 0.82。风控上，所有评测数据脱敏，裁判模型不接触用户隐私。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果裁判模型本身有偏见，怎么校准？
  - **续答**：我们做了两件事：一是用多个裁判模型（GPT-4、Claude、混元）投票，取多数结果；二是定期用人工标注数据做校准，如果某个裁判与人工偏差大，就调整它的权重或弃用。另外，我们还会分析裁判的偏好，比如是否偏爱长回复，然后针对性修正。
- **追问 2**：长程对话中，如何评估模型是否记住了早期信息？
  - **续答**：我们设计了一个‘记忆探测’任务：在对话早期插入一个事实（如‘我明天要去北京’），然后在第 5 轮问‘我明天去哪？’。模型答对率作为记忆指标。另外，我们还用注意力可视化检查模型是否关注了早期 token。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成字节豆包场景：评测维度增加‘趣味性’，因为豆包面向 C 端，需要更活泼的回复。
2. 换成华为盘古场景：评测更注重行业知识准确性，需要引入领域专家标注。
3. 换成美团场景：评测任务完成度时，要结合具体业务指标，如外卖订单转化率。

### 题 19：字节跳动 · 飞书智能伙伴：如何设计 Agent 工作流编排让审批流自动流转？

> 🏢 **真题来源**：字节跳动 · 飞书 AI 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：Agent 工作流编排与业务系统集成，核心是任务拆解、状态机与异常兜底。
:::

::: tip 💡 参考回答示范
> “我在飞书智能伙伴项目里负责审批流 Agent 的编排设计。首先，我们把审批场景拆成三类节点：信息抽取、规则判断、动作执行。信息抽取用大模型从聊天记录或文档里抽字段，比如报销单的金额、事由、发票号；规则判断走确定性规则引擎，比如金额超过 5000 必须加签；动作执行调飞书审批 API 发起流程。编排上我用 DAG 定义节点依赖，每个节点有超时和重试策略。关键指标是端到端成功率，样本是过去 30 天 1.2 万条真实审批请求，口径是首次发起即成功且无人工干预。上线后成功率从 68% 提到 89%，平均耗时从 4.2 分钟降到 1.1 分钟。风控上，所有写操作前必须让用户二次确认，且记录操作日志。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果大模型抽取出错导致审批金额错误，你怎么兜底？
  - **续答**：我们做了三层兜底：第一层，抽取结果置信度低于 0.9 时强制转人工；第二层，金额字段与原始凭证做正则校验，不一致就拦截；第三层，审批发起后 30 秒内允许用户撤回。样本是 200 次模拟错误注入，口径是错误金额流出率，结果是 0.3%。
- **追问 2**：Agent 工作流和传统 BPM 引擎有什么区别？
  - **续答**：传统 BPM 是固定路径，Agent 工作流是动态路径。我们的做法是混合编排：确定性环节走 BPM，非确定性环节走大模型。比如报销标准判断，不同城市差旅标准不同，大模型根据员工城市和职级动态选择规则，再交给 BPM 执行。
:::

::: details 🛠️ 换成你自己的项目时改这三处

### 题 20：阿里巴巴 · 通义千问企业知识库：RAG 切分粒度如何影响召回准确率？

> 🏢 **真题来源**：阿里巴巴 · 通义千问 RAG 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：RAG 文档切分策略与召回评估，核心是 chunk size、重叠窗口与语义完整性。
:::

::: tip 💡 参考回答示范
> “我在通义千问企业知识库项目里负责 RAG 切分调优。我们对比了三种切分：固定 512 token、按段落切、按语义相似度切。样本是 5000 篇内部技术文档，口径是 Top-5 召回率，人工标注了 2000 个问答对。固定 512 token 召回率 72%，按段落切 81%，按语义切 87%。但语义切分耗时是固定切分的 3 倍，我们最终采用混合策略：先用段落切，再对超过 800 token 的段落做语义二次切分，召回率 85%，耗时只增加 40%。关键发现是，切分必须保留标题和上下文，否则模型会丢失关键约束。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果文档里有表格和图片，你怎么切分？
  - **续答**：表格单独走结构化解析，转成 markdown 后作为一个 chunk，并保留表头。图片用 OCR 提取文字，再和周围段落合并。样本是 300 份含表格的文档，口径是表格相关问题的召回率，从 45% 提到 78%。
- **追问 2**：切分粒度变小，召回率会一直提升吗？
  - **续答**：不会。我们做过实验，chunk size 从 512 降到 128，召回率反而从 72% 降到 65%，因为上下文碎片化。最佳区间在 256 到 512 token 之间，具体要看文档类型。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成腾讯混元知识库，切分策略不变，但评估集换成客服对话记录。
2. 把召回率指标换成 MRR，更关注排名第一的准确性。
3. 增加多语言场景，中英文混合文档切分需考虑 token 差异。
:::

### 题 21：腾讯 · 混元大模型长程评测：如何设计 100 轮对话一致性评估？

::: info 🎯 核心考点与破题关键
- **考点实质**：长程对话评测体系，核心是记忆衰减、角色一致性与任务完成度。
:::

::: tip 💡 参考回答示范
> “我在腾讯混元评测组负责长程对话评测。我们设计了一个 100 轮对话任务：用户先设定角色和背景，然后逐步增加约束，最后要求模型总结。评测维度有三个：角色一致性、事实一致性、任务完成度。样本是 200 组对话，每组 100 轮，口径是每 10 轮做一次人工打分。结果发现，模型在 30 轮后角色一致性从 95% 降到 70%，事实一致性从 90% 降到 60%。我们引入滑动窗口记忆和关键信息摘要，把 100 轮后的角色一致性提到 85%。关键是要在评测集里埋设冲突信息，看模型是否会被带偏。”

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：长程评测和短程评测的指标差异是什么？

- **追问 2**：如何自动化长程评测？
  - **续答**：我们用另一个大模型做裁判，但裁判本身也有偏见。所以采用双裁判加人工抽检：两个裁判模型打分一致时采纳，不一致时转人工。样本是 1000 轮对话，口径是裁判与人工一致率，达到 88%。
:::

::: details 🛠️ 换成你自己的项目时改这三处

2. 把 100 轮改成 50 轮，因为业务场景对话通常不超过 50 轮。
3. 增加情感一致性维度，评估模型是否保持同理心。

::: info 🎯 核心考点与破题关键

:::

::: tip 💡 参考回答示范
> “我在文心一言商业化团队负责成本优化。我们算过一笔账：一次 4K 上下文对话，输入 3000 token，输出 1000 token，按文心 4.0 价格，单次成本约 0.12 元。如果日活 10 万，每人 10 次，日成本 12 万。优化手段有三个：第一，高频问题走缓存，命中率 30%，省 3.6 万；第二，简单问题走小模型，比如文心 3.5，成本降 60%；第三，压缩 prompt，去掉冗余示例，输入 token 降 20%。综合下来日成本降到 6.8 万。关键指标是每有效对话成本，样本是 7 天线上数据，口径是总成本除以有效对话数。”

- **追问 2**：小模型效果下降怎么办？
  - **续答**：我们做了路由模型，用一个小分类器判断问题难度，简单问题走小模型，复杂问题走大模型。样本是 5000 条问题，口径是路由准确率，达到 92%，整体效果只下降 2%。

### 题 24：小红书 · 多模态笔记理解：如何用 CLIP 提升搜索相关性？

> 🏢 **真题来源**：小红书 · 多模态搜索 AI 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：多模态内容理解与搜索排序，核心是图文联合嵌入与相关性评估。
:::

::: tip 💡 参考回答示范
> “我在小红书搜索团队负责多模态笔记理解。小红书笔记是图文混合，传统文本搜索会丢失图片信息。我们引入 CLIP 模型，把图片和文本映射到同一向量空间，然后做图文联合召回。样本是 10 万篇笔记，口径是 Top-20 相关性，人工标注了 5000 个查询。纯文本召回相关性 65%，图文联合召回 78%。关键优化点：第一，图片要过滤低质图，比如模糊、纯色图；第二，文本要提取标题和标签，权重高于正文；第三，查询也要做多模态，比如用户上传图片搜相似笔记。上线后搜索点击率提升 12%。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：CLIP 模型对中文支持不好怎么办？
  - **续答**：我们用中文 CLIP 变体，比如 Chinese-CLIP，并在小红书数据上微调。样本是 1 万篇笔记，口径是召回率，微调后从 70% 提到 82%。
- **追问 2**：多模态召回延迟高怎么优化？
  - **续答**：我们做了向量量化，把 float32 降到 int8，索引大小减少 75%，延迟从 50ms 降到 20ms。样本是 100 万向量，口径是 P99 延迟。
:::

::: details 🛠️ 换成你自己的项目时改这三处

3. 增加实时性要求，新笔记 1 分钟内可被搜索到。
:::
