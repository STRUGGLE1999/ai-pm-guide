### 题 1：字节跳动豆包企业版 Agent 工作流编排：如何设计多步骤审批链避免死循环与超时？

> 🏢 **真题来源**：字节跳动 · 豆包企业版 / 智能体平台产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：Agent 工作流中多步任务的状态机设计、超时与重试机制、人工介入节点，以及避免无限循环导致 Token 成本失控。
:::

::: tip 💡 参考回答示范
> “我遇到的问题是，企业审批场景里，一个 Agent 要串联起表单填写、部门审批、法务审核、财务打款四个步骤，但模型有时会卡在第二步反复调用同一个工具，或者因为等待人工审批超时直接失败。我的做法是：第一，把工作流拆成显式状态机，每个节点有唯一 ID 和超时时间，比如表单填写节点 5 分钟，审批节点 24 小时，超时后自动转人工兜底队列。第二，在工具调用层加一个调用频次和参数指纹的缓存，如果 10 秒内相同工具相同参数被调用超过 3 次，就强制中断并记录日志。第三，设计人工介入的“审批挂起”状态，Agent 把上下文和待办链接推送到飞书审批卡片，人点通过或驳回后，回调恢复工作流。第四，所有状态流转都打点，样本是上周 1200 条审批流，口径是端到端完成率，目前从 67% 提升到 89%，其中因死循环导致的失败从 14% 降到 2% 以下。最后，Token 成本方面，每次循环都会消耗上下文，所以我在 prompt 里明确要求模型在连续两次调用同一工具后必须输出“等待人工”，而不是继续尝试。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果人工审批人一直不处理，怎么避免整个流程无限期挂起？
  - **续答**：我会设置多级超时：第一级是审批人 4 小时未处理，自动提醒；第二级是 24 小时未处理，转交给审批人的上级；第三级是 48 小时未处理，自动驳回并通知发起人重新提交。同时，挂起的流程不占用模型调用资源，只存状态，所以不会产生额外 Token 成本。
- **追问 2**：如何评估这种工作流编排的稳定性？
  - **续答**：我主要看三个指标：端到端成功率、平均完成时长、人工介入率。样本是过去 30 天 5600 条流程，口径是首次提交即完成，目前成功率 86%，平均时长 2.3 小时，人工介入率 12%。我会每周拉一个漏斗，看哪个节点流失最多，针对性优化。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 把审批链换成客服工单流转，状态机不变，但超时时间缩短到 30 分钟，因为客服场景对时效要求更高。
2. 把飞书审批卡片换成企业微信消息，回调接口不同，但挂起恢复逻辑一致。
3. 如果企业没有现成审批系统，可以用 Agent 内置的轻量级状态存储，但需要额外设计权限校验。
:::

### 题 2：阿里巴巴通义千问 RAG 检索切分：电商知识库如何平衡召回率与答案精准度？

> 🏢 **真题来源**：阿里巴巴 · 通义千问 / 电商知识库 RAG 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：RAG 中文档切分粒度、检索策略（混合检索、重排序）、以及如何用评测集驱动切分参数调优。
:::

::: tip 💡 参考回答示范
> “我们做的是电商规则知识库，比如退货政策、优惠券叠加规则，用户问“双十一买的衣服能退吗”，需要精准引用具体条款。最初用固定 512 token 切分，结果一个完整条款被切成两半，检索出来只召回一半，答案就错了。我的改进：第一，按语义结构切分，优先按标题、段落、列表项切，每个 chunk 不超过 300 token，并且保留父级标题作为元数据。第二，检索时用混合检索，BM25 加向量，各取 top 20，再用一个轻量级重排序模型（比如 bge-reranker）取 top 5 送给大模型。第三，构建评测集，样本是 500 条真实用户问题，口径是答案完全正确且引用条款无误，初始准确率 61%，调优后到 84%。第四，对于表格类规则，单独走结构化解析，把表格转成键值对，不参与文本切分。第五，切分参数不是拍脑袋，我做了 A/B 测试，chunk size 从 200 到 600，重叠 50，最终 300 加 50 重叠效果最好。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果用户问题需要跨多个 chunk 才能回答，怎么处理？
  - **续答**：我会在检索后做一步“上下文聚合”，把同一文档内相邻的 chunk 合并，或者用一个小模型判断是否需要多跳检索。比如问“退货和运费谁承担”，可能需要同时召回退货政策和运费规则两个 chunk，我就让模型先输出需要哪些条款，再分别检索。
- **追问 2**：怎么防止大模型在 RAG 中编造条款？
  - **续答**：第一，在 prompt 里强制要求“只根据提供的上下文回答，如果上下文没有就说不知道”。第二，后处理校验，把模型引用的条款 ID 和检索结果比对，如果不一致就丢弃重试。第三，评测集里专门加 50 条“无答案”问题，看模型是否老实说不知道，目前拒答准确率 92%。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成金融产品说明书，切分要更细，因为条款之间引用关系强，需要加条款编号作为元数据。
2. 换成多语言知识库，切分要按语言分别处理，检索时用多语言向量模型。
3. 如果知识库更新频繁，需要设计增量索引，只重新切分和索引变更的文档，避免全量重建。
:::

### 题 3：腾讯混元大模型长程评测：如何设计多轮对话的自动化评估体系？

> 🏢 **真题来源**：腾讯 · 混元大模型 / 对话系统产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：长程多轮对话的评测维度设计、自动化打分与人工校验的结合、以及如何用评测结果驱动模型迭代。
:::

::: tip 💡 参考回答示范
> “我们做的是智能客服多轮对话，用户可能来回问 10 轮以上，传统单轮评测不够用。我的方案：第一，定义四个核心维度：任务完成率、上下文一致性、信息准确率、用户满意度（用模型模拟用户打分）。第二，构建评测集，样本是 300 段真实对话，每段 5 到 15 轮，口径是整段对话是否解决用户问题且没有矛盾。第三，自动化评估用两个模型：一个裁判模型逐轮检查是否偏离主题或自相矛盾，另一个模型看最终是否完成任务。第四，人工抽检 10% 的对话，校准自动打分，目前自动和人工的一致率是 87%。第五，评测结果按周汇总，发现“上下文一致性”是弱项，尤其是用户改地址后模型还引用旧地址，我们就针对性加了对话状态跟踪模块，把关键实体（地址、订单号）显式维护，一致性从 72% 提升到 91%。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：裁判模型本身也会出错，怎么保证评测可信？
  - **续答**：我会用多个裁判模型投票，比如三个不同 prompt 的裁判，取多数。另外，对于争议样本，人工介入标注，再反过来微调裁判模型。目前裁判模型的准确率经过 200 条人工标注校验，是 89%。
- **追问 2**：长程评测的 Token 成本很高，怎么控制？
  - **续答**：我会把对话压缩成摘要再送给裁判模型，只保留关键实体和意图，这样 Token 消耗降低 60%。另外，评测不是每轮都跑，而是每 3 轮或任务结束时跑一次，平衡成本和覆盖度。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成教育场景的辅导对话，评测维度要加“引导性”和“不直接给答案”。
2. 换成电话客服，需要加语音转文本的误差评估，评测集要包含 ASR 错误样本。
3. 如果对话轮次特别长（超过 30 轮），需要分段评测再聚合，避免模型上下文超限。
:::

### 题 4：百度文心一言 Token 成本算账：如何在不降效果的前提下把推理成本降低 40%？

> 🏢 **真题来源**：百度 · 文心一言 / 大模型应用产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：大模型推理成本结构、缓存策略、模型蒸馏与量化、以及如何用业务指标衡量成本优化效果。
:::

::: tip 💡 参考回答示范
> “我负责一个文心一言的写作助手，每天 50 万次调用，平均每次输入 800 token，输出 400 token，成本压力很大。我的优化分四步：第一，分析调用日志，发现 30% 的请求是重复或高度相似的，比如“帮我写周报”，我就加了一层语义缓存，用向量相似度匹配，命中缓存直接返回，缓存命中率 22%，这部分成本降为零。第二，对输出长度做动态控制，根据用户历史行为预测需要多长，比如用户经常只读前 200 字，我就把 max_tokens 从 800 降到 400，成本降 15%。第三，把部分简单任务（如格式化、纠错）路由到小模型，比如 7B 模型，成本是大模型的十分之一，路由比例 35%。第四，用 prompt 压缩，把系统提示从 300 token 压到 120 token，不影响效果。综合下来，样本是优化前后各一周的账单，口径是每千次调用成本，从 12 元降到 7.1 元，降幅 41%，同时人工评估效果没有下降，任务完成率保持在 94%。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：语义缓存怎么保证不返回过时或错误答案？
  - **续答**：我会给缓存加 TTL，比如 24 小时，并且对时效性强的请求（如“今天天气”）直接跳过缓存。另外，缓存命中后还会用一个小模型校验是否和当前问题一致，不一致就重新调用大模型。
- **追问 2**：路由到小模型后，效果下降怎么监控？
  - **续答**：我会对路由的请求做 A/B 测试，10% 走大模型作为对照组，比较任务完成率和用户点赞率。如果小模型组下降超过 2 个百分点，就调整路由阈值。目前小模型组完成率 91%，大模型组 94%，差距在可接受范围。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成字节豆包，缓存策略类似，但需要适配豆包的 API 限流和计费方式。
2. 换成自部署模型，成本优化重点在 GPU 利用率和批处理，而不是 API 调用。
3. 如果业务对延迟敏感，缓存和路由都要考虑增加延迟，需要做端到端延迟测试。
:::

### 题 5：美团高危写操作风控：Agent 自动改价、退款如何设计安全护栏？

> 🏢 **真题来源**：美团 · 智能客服 / 交易风控产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：Agent 执行写操作（改价、退款、取消订单）时的权限控制、二次确认、金额阈值与审计日志。
:::

::: tip 💡 参考回答示范
> “我们让 Agent 自动处理商家改价和用户退款，但写操作一旦出错就是资损。我的设计：第一，所有写操作必须经过“预执行”和“确认执行”两阶段，预执行只生成操作预览，不落库，确认执行需要人工点击或满足自动规则。第二，设置金额阈值，比如退款 50 元以下可自动，50 到 200 元需人工确认，200 元以上需主管确认。第三，Agent 只能调用封装好的风控 API，不能直接操作数据库，API 内部会校验操作者权限、订单状态、金额范围。第四，所有操作记录审计日志，包括 Agent ID、用户 ID、操作前后值、时间戳，保留 180 天。第五，设计熔断机制，如果 1 分钟内同一商家出现 5 次以上改价，自动暂停并告警。上线后，样本是 3 个月 2.1 万次写操作，口径是资损事件数，从每月 3 起降到 0 起，同时自动处理率从 45% 提升到 68%。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果 Agent 被恶意用户诱导执行错误退款怎么办？
  - **续答**：我会在风控 API 里加一层用户意图校验，比如退款必须关联真实订单，且订单状态必须是“已支付未发货”或“已收货”。另外，对高频退款用户做画像，触发人工审核。
- **追问 2**：怎么测试这些安全护栏的有效性？
  - **续答**：我会做红蓝对抗，让蓝军模拟恶意用户，尝试诱导 Agent 执行越权操作，记录成功率。目前蓝军攻击 200 次，成功 0 次。另外，每次风控规则变更都跑回归测试。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成金融场景，阈值要更严格，比如 0 元自动，所有操作人工确认。
2. 换成飞书审批，写操作是修改审批单状态，需要加审批流版本校验。
3. 如果 Agent 需要调用多个写操作，需要设计事务补偿，比如退款失败要回滚改价。
:::

### 题 6：小红书多模态笔记理解：如何用图文对齐提升搜索相关性？

> 🏢 **真题来源**：小红书 · 多模态搜索 / 内容理解产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：多模态内容理解中图文对齐、跨模态检索、以及如何用业务指标（点击率、收藏率）评估相关性。
:::

::: tip 💡 参考回答示范
> “小红书搜索里，用户搜“秋天穿搭”，笔记可能只有图片没有文字，或者文字和图片不一致。我的做法：第一，用多模态模型（如 CLIP）把图片和文本映射到同一向量空间，计算图文相似度，过滤掉图文不符的笔记。第二，对笔记做多模态摘要，用模型生成一句话描述图片内容，补充到文本索引里。第三，检索时同时用文本向量和图片向量，做混合检索，再重排序。第四，构建评测集，样本是 1000 条搜索 query，口径是前 10 个结果的点击率和收藏率。优化前点击率 8.2%，优化后 11.5%，收藏率从 2.1% 提升到 3.4%。第五，对于图文不符的笔记，降权处理，但不直接删除，避免误伤。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：多模态模型推理成本高，怎么平衡？
  - **续答**：我会离线批量处理图片，生成向量和摘要，在线只做检索和重排序。另外，只对高曝光笔记做多模态处理，长尾笔记用文本兜底。
- **追问 2**：怎么评估图文对齐的质量？
  - **续答**：我会人工标注 500 对图文，判断是否一致，作为评测集。模型判断的准确率目前是 88%，不一致的主要是抽象艺术类图片，需要单独处理。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 换成抖音短视频，需要加视频帧采样和音频转文本，多模态维度更多。
2. 换成淘宝商品，图文对齐还要考虑商品属性，比如颜色、款式。
3. 如果平台图片量特别大，需要设计分层处理，热门图片实时，冷门图片离线。
:::

### 题 7：字节跳动 · 飞书智能伙伴：Agent 工作流编排中如何处理多轮工具调用失败与状态回滚？

> 🏢 **真题来源**：字节跳动 · 飞书智能伙伴 / 企业级 Agent 产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对 Agent 编排中异常处理、状态一致性、用户体验降级的系统性设计能力。
:::

::: tip 💡 参考回答示范
> “我在设计飞书智能伙伴的审批 Agent 时，核心逻辑是‘先定义原子工具，再编排状态机’。比如一个报销审批流涉及：查预算、验发票、调审批接口、发通知。如果调审批接口超时，不能直接报错给用户，而是分三步：第一，工具层做幂等设计，每个工具调用带唯一 request_id，超时后重试两次；第二，状态机记录当前步骤的上下文快照，失败时回滚到上一步的待确认状态，并保留已填数据；第三，给用户明确的降级选项——‘审批接口暂时不可用，已为您保存草稿，可稍后重试或转人工’。样本上，我们内部灰度了 200 个审批流，口径是端到端成功率从 78% 提升到 94%，其中因工具失败导致的用户放弃率下降了 37%。关键指标是‘任务完成率’和‘人工介入率’，严禁编造数据，我们只统计真实埋点。”
:::

::: warning ⚠️ 连环追问与高分续答

### 题 10：百度 · 文心一言 Token 成本算账：如何通过 Prompt 压缩和缓存将单次对话成本降低 40%？

::: tip 💡 参考回答示范
> “在文心一言企业版中，我们算过一笔账：一次客服对话平均 1500 token 输入，500 token 输出，按 0.012 元/千 token 计算，单次成本约 0.024 元。日活 10 万次，日成本 2400 元。优化第一步：Prompt 压缩，把系统提示从 300 token 压到 120 token，去掉冗余示例，成本降 12%。第二步：引入语义缓存，对高频问题（如‘退货政策’）直接返回缓存答案，命中率 30%，成本再降 18%。第三步：输出长度控制，设置 max_tokens 和停止符，减少废话，成本降 10%。合计降低 40%，日成本从 2400 降到 1440。样本是 10 万次真实对话，口径是平均 token 消耗和缓存命中率，严禁编造，我们只统计线上日志。”

### 题 13：字节跳动 · 抖音电商 AI 客服 Agent 如何编排多轮工具调用与兜底策略？

::: tip 💡 参考回答示范
> “我在抖音电商智能客服项目中，负责将传统 FAQ 机器人升级为基于大模型的 Agent。核心思路是：不追求全自动，而是定义清晰的自动化边界。首先，我拆解了售后场景的 Top 10 意图，比如查物流、催发货、退差价、仅退款、投诉。每个意图背后需要调用的工具不同，比如订单查询、物流接口、退款接口、优惠券补发。我设计了一个三层的编排架构：第一层是意图路由，用轻量模型做分类，准确率要求 95% 以上；第二层是任务规划，对于多步任务（比如先查订单再退差价），用 Plan-and-Execute 模式，让大模型生成步骤，但每一步执行前都经过规则校验，比如退款金额超过 50 元必须转人工；第三层是执行与监控，每个工具调用都有超时和重试机制，失败时降级到预设话术并转人工。兜底策略上，我设定了三条红线：用户连续两次表达负面情绪、涉及资金操作超过阈值、工具调用连续失败两次，立即转人工。指标方面，我们看自助解决率、转人工率、用户满意度（CSAT）和平均处理时长。上线后自助解决率从 42% 提升到 61%，但转人工率也上升了 5 个百分点，因为有些用户就是想要人工。后来我们优化了转人工的引导话术，把转人工率控制在了合理范围。”

::: warning ⚠️ 连环追问与高分续答

:::

::: tip 💡 参考回答示范
> “在 1688 采购助手项目中，我们要帮买家从海量商品和供应商信息里找到匹配的货源。RAG 的难点在于文档形态复杂：商品标题、属性表、详情页图文、供应商资质 PDF、历史合同。我的切分策略是分而治之。对于商品，我按属性字段切分，比如材质、尺寸、起订量、价格阶梯，每个字段作为一个 chunk，并保留商品 ID 作为元数据。对于 PDF 合同，我用版面分析先识别段落和表格，再按语义切分，比如按条款切，每个条款一个 chunk，并加上条款标题。切分粒度上，我做了 A/B 测试，发现 256 token 的 chunk 在召回率上比 512 token 高 8%，但答案完整性差一些，最终选了 384 token 并设置 20% 重叠。检索阶段，我用了混合检索：向量检索用 bge-large-zh，关键词检索用 BM25，然后用一个轻量重排模型（比如 bge-reranker-base）对 Top 50 结果重排，取 Top 5 给大模型。评估上，我构建了 500 条标注数据，包括 query、相关 chunk、答案，用 Recall@5、MRR、答案准确率三个指标。上线后，采购助手的询盘转化率提升了 12%，但我们也发现对于长尾商品，召回还是不够，后来补充了同义词扩展和类目预测。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：你提到用 bge-reranker 重排，但重排模型会增加延迟，你怎么平衡效果和响应时间？
  - **续答**：我们做了延迟预算。整个 RAG 链路要求 P99 在 800ms 以内。向量检索大概 100ms，BM25 50ms，重排模型在 CPU 上跑 50 个文档要 300ms，GPU 上只要 80ms。所以我们在 GPU 上部署重排模型，并且只对 Top 30 重排，而不是 Top 50。另外，我们设置了动态策略：如果向量检索的 Top 1 分数很高（比如 cosine > 0.9），就跳过重排，直接返回。这样在保证效果的同时，把平均延迟控制在 400ms 左右。
- **追问 2**：如果商品信息更新频繁，比如价格每天变，你的 RAG 索引如何实时更新？
  - **续答**：我们用的是增量索引。商品价格、库存这类结构化字段，不走 RAG，而是通过 API 实时查询。RAG 只索引相对静态的文本，比如商品描述、资质文件。对于这些文本，我们监听数据库的 binlog，有更新就触发重新切分和 embedding，然后更新向量库。为了减少 embedding 成本，我们只对变更的 chunk 重新计算，而不是整个文档。另外，我们设置了 TTL，对于超过 30 天没更新的文档，降低检索权重。
:::

2. 切分策略可以改为按标题层级切分，或者按问答对切分。
3. 检索评估可以加入人工评估，比如答案有用性打分。

### 题 15：腾讯 · 混元大模型长程评测如何设计多轮对话与一致性指标？

> 🏢 **真题来源**：腾讯 · 混元大模型 / 对话系统评测产品面经

::: info 🎯 核心考点与破题关键
- **考点实质**：考察对长程对话评测体系的设计能力，包括多轮上下文一致性、角色保持、知识遗忘、话题漂移等维度的量化指标与数据构造。
:::

::: tip 💡 参考回答示范
> “在混元大模型的长程对话评测中，我发现传统的单轮评测完全不够用。用户和 AI 聊到第 10 轮，AI 可能忘了第 3 轮说过的偏好，或者角色设定崩了。所以我设计了一套多轮评测方案。首先，我构造了 200 组多轮对话剧本，每组 10-15 轮，覆盖角色扮演、任务型对话、闲聊、知识问答混合。每个剧本有明确的角色设定、背景知识、以及需要记住的关键信息（比如用户名字、喜好、之前提到的订单号）。评测指标分四个维度：一致性（AI 是否记住并遵守之前的信息）、角色保持（是否一直符合设定）、话题连贯性（是否答非所问）、知识准确性（事实是否正确）。一致性我们用 LLM-as-a-judge，让 GPT-4 根据剧本和对话历史打分，同时人工抽检 20% 校准。我们还设计了一个“记忆探测”任务，在第 5 轮插入一个关键信息，在第 12 轮提问，看 AI 能否回忆。评测结果发现，混元在 8 轮以内一致性很好，超过 10 轮后遗忘率明显上升。于是我们优化了上下文窗口管理，对早期对话做摘要，并加入关键信息缓存。优化后，15 轮的一致性得分从 72 提升到 86。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：LLM-as-a-judge 本身也有偏差，你怎么保证评测的可靠性？
  - **续答**：我们做了三件事。第一，用多个 judge 模型投票，比如 GPT-4、Claude、混元自己，取多数一致的结果。第二，人工标注 500 条对话作为黄金集，计算 judge 与人工的一致率，如果低于 85%，就调整 prompt 或换模型。第三，对于关键指标，比如事实准确性，我们采用规则校验和检索验证，而不是完全依赖 judge。另外，我们定期用黄金集重新校准 judge。
- **追问 2**：如果用户故意引导 AI 说错话，比如诱导它泄露系统提示，你的评测会覆盖这种对抗场景吗？
  - **续答**：会。我们专门有一个红队评测集，包含 100 种对抗攻击，比如提示注入、角色扮演越狱、诱导泄露隐私。评测指标是攻击成功率。如果成功率超过 5%，就视为不达标。我们还模拟了多轮攻击，比如先聊正常话题，再慢慢引导。这些评测结果会反馈给算法团队做 RLHF 和护栏优化。
:::

- **考点实质**：RAG 中文档切分策略对检索召回率、答案忠实度的实际影响，以及电商场景的特殊性。
:::

::: tip 💡 参考回答示范
> “在淘宝问问项目里，我们做商品知识问答，底层是 RAG。商品标题通常很短，比如‘苹果 iPhone 15 Pro 256G 原色钛金属’，但商品详情页很长。最初我们按固定 512 token 切分，结果检索时经常召回不相关的商品，因为一个 chunk 里混了多个商品的描述。后来我推动改成按商品维度切分：每个商品作为一个独立文档，标题和关键属性单独作为一个 chunk，详情描述按段落切分但保留商品 ID 元数据。检索时先用标题 chunk 做粗排，再用详情 chunk 做精排。口径是：样本为 5000 个真实用户 query，评估指标是 top5 召回率。切分优化前 top5 召回率 62%，优化后 81%。另外，我们加了‘答案必须引用商品 ID’的约束，避免模型编造不存在的商品。这里数字都是内部评测集的结果，严禁编造。”
:::

::: warning ⚠️ 连环追问与高分续答
- **追问 1**：如果商品标题本身信息量很少，比如‘夏季新款女装’，怎么切分？
  - **续答**：这种情况下标题 chunk 会结合类目和属性一起切，比如‘女装-连衣裙-夏季-碎花’，并且把销量、评分等结构化字段作为元数据参与检索。我们还会用 query 改写，把‘适合夏天的裙子’改写成‘夏季 连衣裙’，提升匹配。
- **追问 2**：怎么评估切分策略的好坏？除了召回率还看什么？
  - **续答**：还看答案忠实度，即生成的答案是否只基于检索到的 chunk。我们用人工标注 500 条答案，计算幻觉率。切分优化后幻觉率从 15% 降到 6%。另外看端到端响应时间，因为 chunk 变小会增加检索次数，需要平衡。
:::

::: details 🛠️ 换成你自己的项目时改这三处
1. 如果换成京东的 RAG 场景，商品标题结构不同，需要重新设计属性抽取规则。
2. 如果换成小红书，笔记内容更非结构化，切分要按段落和图片 OCR 文本结合。
3. 如果换成自研向量库，要额外考虑索引更新频率和商品上下架带来的 chunk 失效问题。
