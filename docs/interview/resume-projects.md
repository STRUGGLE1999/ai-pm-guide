# 简历项目包装

## 推荐结构

使用「背景 - 用户 - 痛点 - 方案 - 指标 - 风险 - 个人贡献」讲 AI 项目。每段至少说明背景、目标、自己的动作、关键难点、结果和复盘。结果优先使用可核验数据；没有数据时用交付物、用户反馈、验证结论和决策影响，不编造上线规模或业务收益。

## 示例表达

负责 AI 知识库助手产品方案设计，围绕企业内部资料检索和可信问答场景，设计文档解析、权限隔离、RAG 问答、引用溯源、用户反馈和后台运营机制，核心指标包括问题命中率、答案采纳率和未命中问题闭环率。

售后助手可以写成：针对电商售后「规则问答与换货办理」分离失败、口头承诺与系统不一致的问题，设计制度检索 + 订单查询 + 确认后建单的工作流，用 40 条真实问法回归乱承诺和查错单，将「已办结」话术从评测集中清零。若尚未上线，写清这是 PoC，以及验证了哪几条假设。

## 常见错误

- 只写“接入大模型”。
- 只展示页面，不讲业务结果。
- 只讲技术方案，不讲用户和指标。
- 把参与包装成主导，把 Demo 写成商业上线。
- 堆 RAG、Agent、MCP 关键词，却说不清为什么不用更简单的方案。

## 针对岗位改重点，不要只改标题

把 JD 拆成业务场景、核心任务、必备能力、加分经验和组织痛点，再选择最能证明这些能力的项目。事实可以重新组织和强化，但不能虚构。To B 强调流程、权限、集成和 ROI；To C 强调首次成功、留存和信任；商业岗强调漏斗、毛利和实验。岗位差异见 [岗位方向拆解](/interview/roles)。

## 项目经历表达模板

```markdown
项目背景：谁在什么流程中遇到什么问题，有什么证据。
目标：希望改善哪个业务指标，边界是什么。
判断：为什么选择 AI；比较过哪些非 AI 或更简单方案。
方案：Prompt / RAG / 工作流 / Agent 如何分工，人和系统责任如何划分。
验证：用什么样本、指标和用户测试验证。
结果：可核验的业务、产品、质量或交付结果。
复盘：最大失败、根因、下一步和仍未解决的问题。
```

写完自检：一个不懂你们公司的面试官，能否在 60 秒内说出用户、任务、你做的关键决策、以及怎样算成功。
