# AI 技术通识与认知边界题库

在技术类面试中，面试官并非要求产品经理去手动推导反向传播公式，而是考察你**能否准确理解技术边界、识别算法局限性，并将技术特性转化为可落地的产品架构与体验设计**。

---

## 题目 1：大模型与传统判别式 NLP 在产品落地逻辑上有何本质差异？

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察候选人是否具备从“确定性小模型”向“生成式大模型”转变的产品思维，理解概率生成、上下文依赖与泛化能力的本质区别。
- **解题框架**：
  1. **能力范式**：专用小模型（单任务判别） vs 通用大模型（少样本生成与跨领域推理）。
  2. **研发与上线周期**：重数据标注与算法训练 vs 重 Prompt 编排、上下文组装与业务评测。
  3. **产品确定性与交互容错**：严格分类输出 vs 概率性输出（需引入人机协同与幻觉防御）。
  4. **成本结构**：前期标注与算力成本大、推理极低 vs 前期启动极快、持续推理 Token 成本高。
:::

::: tip 💡 参考回答示范
> “作为 AI 产品经理，我认为大模型与传统 NLP 的差异不能只看‘更聪明’，而是底层的产品设计哲学发生了根本性转变：
> 
> **第一，在能力范式与灵活性上**：传统 NLP（如 BERT、CRF）是针对单一任务（如情感分类、NER 命名实体识别）训练的专用模型，需求微变就需重新收集语料并重训；而 LLM 具备强大的上下文少样本学习（Few-Shot）与通用推理能力，能直接通过指令执行多变的任务，冷启动周期从‘月级’降到‘小时级’。
> 
> **第二，在系统确定性与人机交互设计上**：传统 NLP 输出是确定性的分类概率，我们可以设严格阈值；而大模型是自回归概率生成，存在不可避免的‘幻觉’和‘指令漂移’。因此，产品设计必须从传统的‘功能交付’转变为‘人机协同（Human-in-the-loop）’与‘确定性工程兜底’（如结构化 JSON 校验、引用溯源、可编辑画布）。
> 
> **第三，在成本与架构演进上**：传统 NLP 是‘重前期训练标注，轻线上推理’；大模型则是‘轻前期接入，重持续推理成本与 Latency 治理’。产品经理需要从第一天起就设计模型路由（大模型兜底复杂任务，轻量小模型处理高频分类），在体验与 Token 成本之间取得动态平衡。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **扣分表达**：“大模型就是比传统 NLP 准确率更高、无所不能。”（暴露对大模型概率生成缺陷的不了解）。
- ❌ **扣分表达**：“大模型不需要标注数据了。”（忽视了 SFT 领域微调、RLHF 和黄金评测集对高质量标注数据的极高依赖）。
- 🔄 **高频追问**：*在你们实际业务中，有没有哪些环节依然坚持使用传统小模型而不是大模型？为什么？*
:::

## 题目 2：RAG vs 微调（Fine-Tuning）vs Prompt 工程，产品经理该如何做技术路径选型？

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察候选人面对实际业务需求时，能否从**数据时效性、专业领域知识、落地成本、幻觉控制及上线周期**五个维度做出理性、经济的技术选型。
- **解题框架**：三者的本质分工（Prompt 是指令规范、RAG 是外部开卷资料、Fine-Tuning 是行为内化与格式约束），结合具体选型矩阵分析。
:::

::: tip 💡 参考回答示范
> “在实际技术选型中，我遵循 **‘Prompt 优先 $\rightarrow$ RAG 补充知识 $\rightarrow$ 微调沉淀能力/降低成本’** 的递进原则，不会盲目推崇微调：
> 
> 1. **Prompt 工程（解决‘意图理解与任务引导’）**：
>    - **适用**：业务原型验证（PoC）、多步骤任务拆解、角色设定与少样本演示。
>    - **优势**：零改动成本、即时生效；**局限**：受上下文长度限制，无法注入大量动态知识。
> 2. **RAG 检索增强生成（解决‘动态私域知识与事实可信度’）**：
>    - **适用**：企业知识库、客服政策问答、合规政策查询、高频变动的业务数据。
>    - **优势**：知识实时更新、支持权限隔离、答案有明确原文引用溯源（大幅降低幻觉）；**局限**：依赖文档解析与检索召回质量。
> 3. **微调 Fine-Tuning（解决‘固定风格/专有领域语法/小模型提效’）**：
>    - **适用**：特定的输出格式（如严格的工业代码生成、病历结构化抽取）、固定语气风格、或者用 7B/14B 小模型蒸馏替代昂贵的 GPT-4o 以降低线上推理成本。
>    - **误区**：微调很难用于‘注入经常变动的知识’，且存在灾难性遗忘与长尾幻觉风险。
> 
> **总结选型法则**：‘要知识找 RAG，要格式与能力内化找微调，要敏捷验证用 Prompt’。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **扣分表达**：“企业要建立行业壁垒，第一步就应该拿几十万条公司文档去微调一个专属垂直大模型。”（典型的灾难选型，知识易混淆且无法实时更新）。
- 🔄 **高频追问**：*如果 RAG 检索出来的 Top-K 文档里包含相互矛盾的旧政策和新政策，大模型回答错了，你从产品层面怎么解？*
:::

## 题目 3：大模型幻觉（Hallucination）是如何产生的？从产品与系统层面如何解决？

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察对大模型统计学本质的认知，以及能否构建“全链路防御机制”，而不是把希望寄托在“等待下一个更完美的模型”。
- **解题框架**：
  1. **成因**：自回归概率预测机制、训练语料噪声与过期、上下文超长遗忘/受误导。
  2. **产品防御策略**：输入前处理（强检索约束） $\rightarrow$ 提示词约束（严禁推断/声明拒答） $\rightarrow$ 后处理校验（引用溯源/一致性检查） $\rightarrow$ 用户交互呈现（可信度打标/可溯源高亮）。
:::

::: tip 💡 参考回答示范
> “大模型本质上是一个‘基于统计概率的下一个 Token 预测器’，它追求的是**语言流畅度与语义连贯性**，而非客观事实的绝对真实。产生幻觉的根因包括预训练语料中的事实错误、知识压缩过程中的信息丢失，以及注意力机制在长文本中的注意力稀释。
> 
> 在产品和系统设计上，我采取**‘四层拦截闭环’**来治理幻觉：
> 
> 1. **检索层（Grounding 事实锚定）**：严格通过 RAG 注入高相关性的上下文片段，将模型的任务从‘依靠内部记忆自由生成’收敛为‘根据已知材料阅读理解与归纳’。
> 2. **提示工程层（约束与拒答机制）**：在 System Prompt 中加入强负向约束：*‘仅根据给定的参考资料作答；如果资料中未提及相关信息，必须明确告知无法回答，严禁主观推断’*。
> 3. **系统校验层（双重判定与交叉验证）**：引入轻量级裁判模型（LLM-as-a-Judge）对生成结果与检索原文做‘忠实度（Faithfulness）’比对，低于设定阈值则阻断并走降级策略（转人工或推荐相关文档）。
> 4. **UI/UX 交互层（降低盲信与建立信任）**：提供‘一键查看原文出处’、高亮对应引用段落，并在敏感场景（如法务/医疗）显著标识免责提示，支持用户一键纠错反馈。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **扣分表达**：“幻觉问题只要把 Temperature 设成 0 就彻底解决了。”（Temperature=0 只是降低输出随机性，对于模型本身的知识盲区依然会稳定地生成幻觉）。
- 🔄 **高频追问**：*在拒绝回答（拒答）和冒着幻觉风险给一个模糊答案之间，你们产品如何设定阈值？*
:::

## 题目 4：为什么做 Agent 必须依赖 Function Calling 和 MCP（Model Context Protocol）？

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察候选人对 Agent 从“聊天框”迈向“行动引擎（Action Engine）”的底层协议理解。
- **解题框架**：
  1. **痛点**：纯文本模型无法直接操作外部世界（查数据库、调 API、发邮件）。
  2. **Function Calling 价值**：让模型具备‘意图识别 $\rightarrow$ 结构化参数抽取 $\rightarrow$ 系统执行 $\rightarrow$ 结果反馈’的闭环能力。
  3. **MCP 协议的战略意义**：统一标准工具连接协议，打破系统孤岛，实现 Agent 即插即用。
:::

::: tip 💡 参考回答示范
> “大模型如果只停留在纯文本生成，它就只是一个‘顾问’；只有具备了 Function Calling 和标准协议支持，它才能成为具备落地价值的‘执行者（Agent）’：
> 
> 1. **Function Calling 的本质与价值**：
>    大模型本身并不直接运行外部代码，而是根据用户意图，**精准判断该调用哪个外部函数，并从自然语言中抽取出符合 JSON Schema 的结构化参数**。业务系统执行完后将结果回传给大模型，由其组织成自然语言交付用户。这使得 AI 能够连接 CRM、ERP、工单系统等核心业务资产。
> 
> 2. **引入 MCP（模型上下文协议）的革命性意义**：
>    过去每个产品为大模型封装工具时，接口标准各自为政，开发一个工具需要为不同模型框架重复写适配代码。Anthropic 推出的 MCP 相当于 AI 时代的 **USB 接口**——它标准化了数据源（Resources）、功能工具（Tools）和提示模板（Prompts）的交互协议。
>    作为产品经理，MCP 让我们的 Agent 系统能够像插件商店一样快速接入第三方企业服务（如 GitHub、Slack、Notion、本地文件系统），极大地降低了生态集成的研发成本。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **扣分认知**：以为 Function Calling 是模型直接去请求网络接口。（实际上是模型生成格式化指令，由宿主系统代理执行并做权限校验，产品必须设计鉴权与人机确认）。
- 🔄 **高频追问**：*对于高危的写操作（如删除数据库记录、发起转账支付），你如何在 Agent 工具链中设计安全确认机制？*
:::

## 题目 5：上下文窗口（Context Window）越来越大（如 1M~2M），为什么我们依然需要 RAG？

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察候选人是否有实际工程经验与成本/性能权衡意识，避免陷入“长上下文万能论”的认知误区。
- **解题框架**：从**推理成本（TCO）、响应延迟（Latency）、注意力稀释（Needle In A Haystack 缺陷）、权限隔离与多租户管理**四个维度展开。
:::

::: tip 💡 参考回答示范
> “虽然目前头部大模型（如 Gemini 1.5、Claude 3.5）支持 1M 甚至 2M Token 的超长上下文，但在企业级产品生产环境中，**长上下文永远无法替代 RAG，两者是互补而非替代关系**：
> 
> 1. **推理成本与经济性（TCO）**：
>    长上下文的计费是按输入 Token 线性（甚至超线性）累加的。如果每次用户问一个简单问题，我们都把整部 50 万字的员工手册（约 800k Token）塞进上下文，单次调用成本可能高达数元，商业上完全不可持续。而 RAG 只检索最相关的 3~5 个 Chunk（约 2k Token），成本降低 99% 以上。
> 2. **首字延迟（TTFT）与吞吐量**：
>    处理百万级 Token 的 Prompt 预填充（Prefill）需要数秒甚至数十秒，用户在端侧会感到极度卡顿；而 RAG 向量检索在毫秒级完成，能做到 500ms 内流式吐字。
> 3. **‘大海捞针’与注意力稀释（Lost in the Middle）**：
>    学术与实测均表明，当上下文极度膨胀时，模型对中间段落细节的提取准确率会显著下降；RAG 的精准切分与重排序（Rerank）能保证输入给模型的都是高信噪比上下文。
> 4. **企业级动态权限与多租户隔离**：
>    RAG 可以在检索阶段天然植入 ACL（访问控制列表）权限过滤，普通员工只能检索其有权限查看的文档；如果全塞进 Context，很难做到细粒度动态权限管控。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **常见误区**：“有了 100 万上下文，我们就不用做向量切分和知识库了，直接全灌进去最准。”
- 🔄 **高频追问**：*长上下文（Long Context）适合用在你们产品的什么特定场景下？（答：整本财报深度对比分析、超长复杂代码仓库重构、长视频切片理解等低频但需全局综合理解的高价值场景）。*
:::
