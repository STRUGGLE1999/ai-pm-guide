# 评测体系、指标与数据治理题库

业内有一句共识：**“没有科学评测的 AI 产品，迭代全凭玄学与运气。”** 
评测与数据能力是衡量 AI 产品经理专业度的关键试金石。面试官通过此类题目考察你是否具备量化质量、监控业务和建立防退化机制的扎实工程素养。

---

## 题目 1：如何从 0 到 1 搭建一个企业级 AI 产品的评测体系与黄金数据集（Gold Dataset）？

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察候选人是否具备严密的数据抽样方法论、评测标准制定能力以及将主观生成结果量化为可回归指标的实战经验。
- **解题框架**：
  1. **评测集样本来源与分层抽样**：覆盖真实流量、长尾场景、边界异常与对抗用例。
  2. **评测标准制定（Rubric）**：分维度建立 1~5 分评分细则或 Pass/Fail 判定标准。
  3. **标注与基准建立（Ground Truth）**：双人独立标注 + 专家仲裁，计算 Kappa 一致性系数。
  4. **评测流水泥化（CI/CD 集成）**：Prompt/模型改动时自动运行离线回归，形成上线阻断机制。
:::

::: tip 💡 参考回答示范
> “构建一套高水准的企业级评测体系，我分为四个阶段推进：
> 
> ```mermaid
> flowchart LR
>     A[样本分层抽样] --> B[制定评分标准 Rubric]
>     B --> C[人工/模型标注对齐]
>     C --> D[CI/CD 自动化回归]
> ```
> 
> **1. 样本集的科学分层（拒绝全凭主观造题）**：
> 一个健康的评测集（通常 300~500 条代表性 Case）应由四部分构成：
> - **头部高频 Case (40%)**：从线上真实用户历史 Query 中按聚类结果等比抽取；
> - **长尾与复杂意图 Case (30%)**：多约束条件、长上下文、多轮追问与模糊提问；
> - **边界与无答案 Case (15%)**：知识库缺失、越权提问、故意诱导，用于评测**拒答率与幻觉抑制**；
> - **安全性与对抗攻击 Case (15%)**：Prompt 注入攻击（Jailbreak）、涉政涉黄涉敏违规提问。
> 
> **2. 明确的量化标准（Rubrics）**：
> 拒绝‘好/不好’这种模糊主观评价。我们针对 RAG 问答制定四个离散维度：
> - **检索相关性（Context Relevance）**：召回片段是否包含答题所需充分必要信息（0/1）；
> - **生成忠实度（Faithfulness）**：答案是否有任何超出参考材料的捏造（0/1）；
> - **答案完备性（Answer Completeness）**：是否完整覆盖了用户的所有子问题（1~5分）；
> - **格式合规性（Format Compliance）**：是否符合 JSON Schema 或指定 markdown 结构（Pass/Fail）。
> 
> **3. 自动化与工程闭环**：
> 评测集固化后接入 CI/CD 流水线。每次团队修改 System Prompt、更换 Embedding 模型或调整切分参数时，自动运行评测流水线，生成对比报表（Diff Report）。若核心维度的准确率出现负向退化（Regression > 1%），系统自动阻断发布。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **扣分回答**：“评测集就是我和算法同事在聊天框里随手试了几十个问题，看起来挺聪明的就上线了。”（典型的业余表现）。
- 🔄 **高频追问**：*当业务发展、知识库更新后，你怎么维持评测集的生命力与时效性？*
:::

## 题目 2：如何科学定义并监控 AI 产品的核心指标？请列出完整的指标看板。

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察候选人建立**全链路数据监控体系**的能力，涵盖质量指标、用户体验指标、工程性能指标与商业成本指标。
- **解题框架**：
  按照**「离线质量 $\rightarrow$ 在线行为 $\rightarrow$ 业务成效 $\rightarrow$ 成本吞吐」**四维指标矩阵展开。
:::

::: tip 💡 参考回答示范
> “在实际管理 AI 产品时，我会搭建一个包含四个层级的实时监控大盘：
> 
> | 指标分类 | 核心指标名称 | 定义与计算方式 | 业务与产品含义 |
> | :--- | :--- | :--- | :--- |
> | **1. 离线/近线质量** | **黄金集通过率**<br>**生成忠实度 (Faithfulness)** | 评测集中达标用例占比<br>答案中可由检索证据直接证明的比例 | 保证系统发版前的质量底线，防止模型幻觉爆发。 |
> | **2. 在线用户交互** | **答案采纳率 (Adoption Rate)**<br>**主动点踩率 (Negative Feedback)**<br>**人工二次编辑距离** | 发生复制/插入/采纳的会话 / 总生成数<br>点踩会话占比<br>用户最终修改文本与 AI 生成文本的差异比例 | 衡量生成的真实可用度；编辑距离越小，说明 AI 内容越直接可用。 |
> | **3. 最终业务结果** | **端到端自助解决率**<br>**任务流转人工率**<br>**人效提升倍数** | 用户未再发起工单/转人工的独立会话占比<br>需要人工兜底介入的比例<br>人均每日处理任务数同比变化 | 证明 AI 项目对于业务降本增效的真实 ROI。 |
> | **4. 工程与成本** | **首字响应延迟 (TTFT)**<br>**单次任务 Token 消耗成本**<br>**并发吞吐与报错率 (Error Rate)** | P95 用户等待首字流出毫秒数<br>(输入Token $\times$ 输入单价 + 输出Token $\times$ 输出单价)<br>API 超时与 5xx 占比 | 监控体验流畅度与商业毛利率，防止 Token 消耗失控。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **扣分回答**：把“日活跃用户数（DAU）”或“总生成次数”作为核心成功指标。（调用量大可能只是因为生成质量太差导致用户反复重试）。
- 🔄 **高频追问**：*用户如果不给你的回答点赞或点踩，你如何通过无感知的隐式行为数据判断答案好坏？*
:::

## 题目 3：如何应用 LLM-as-a-Judge（大模型作为裁判）？如何解决大模型裁判的固有偏置？

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察候选人对前沿自动化评测（如 Ragas、G-Eval）的实践深度，以及对 LLM 作为评测器时的局限性（位置偏置、长度偏置、自恋偏置）的纠偏策略。
- **解题框架**：
  1. **适用场景**：大规模回归测试、在线实时质量抽检、Prompt A/B 对比。
  2. **常见三大偏置**：位置偏置（Position Bias）、自恋偏置（Self-preference Bias）、冗长偏置（Verbosity Bias）。
  3. **产品与工程纠偏手段**：双向交换对比（Swap positions）、少样本锚定（Few-shot Rubric）、使用更高阶模型盲测、人类专家定期校准对齐。
:::

::: tip 💡 参考回答示范
> “人工评测准确但极其昂贵且无法规模化，因此在实践中我们广泛采用 **LLM-as-a-Judge** 做自动化质量初筛与大规模回归。但大模型当裁判存在天然的认知偏置，我们必须在系统设计中加入纠偏机制：
> 
> 1. **三种典型偏置与纠偏手段**：
>    - **位置偏置（Position Bias）**：在做模型 A/B 对比时，大模型倾向于给排在前面的答案打高分。**解决方案**：每次对比自动执行正反两次评测（A vs B 和 B vs A），只有两次结论一致才计入有效胜率，否则标记为平局。
>    - **冗长偏置（Verbosity Bias）**：大模型本能觉得字数多、排版长的答案更好。**解决方案**：在 Judge Prompt 中明确约束：*‘重点评估信息的准确性与精炼度，废话冗余将作为扣分项’*。
>    - **自恋偏置（Self-preference Bias）**：GPT-4 评测时倾向于喜欢 GPT-4 风格的生成。**解决方案**：统一采用行业最高能力模型（如 Claude 3.5 Sonnet 或 GPT-4o）作为独立裁判，并在评测时抹去所有模型的身份元信息进行双盲评审。
> 
> 2. **人机一致性校准（Human-in-the-loop Alignment）**：
>    每周随机抽取 100 条 LLM-as-a-Judge 的评测打分，由业务专家进行二次复核，计算两者的 **Cohen's Kappa 一致性系数**。当一致性低于 0.8 时，重新迭代 Judge Prompt 中的评估准则与 Few-shot 样例，确保自动化评测始终对齐真实业务标准。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **扣分认知**：认为拿一个小模型（如 7B/14B）随便写一段 Prompt 就能充当裁判。（低阶模型自身的推理能力不足以做精准语义评估，会导致大量误判）。
- 🔄 **高频追问**：*在生产环境中，你如何控制 LLM-as-a-Judge 自身的 Token 调用成本？*
:::

## 题目 4：线上产品上线后，出现大量用户投诉“回答变差/出现错误”，你的排查与闭环流程是怎样的？

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察候选人在高压故障场景下的应急处理、工程链路溯源（根因分析 RCA）与建立长效防御机制的综合管理能力。
- **解题框架**：按照**「止血与快速定位 $\rightarrow$ 四层归因排查 $\rightarrow$ 分流修复 $\rightarrow$ 沉淀回归集」**展开。
:::

::: tip 💡 参考回答示范
> “面对线上质量波动的客诉，我遵循 **‘先止血隔离，再链路归因，后防退化闭环’** 的标准化流程：
> 
> 1. **第一步：止血与应急响应（< 15 分钟）**：
>    - 检查大盘指标与客诉集中点，确认是偶发还是大面积异常；
>    - 若是重大核心业务事故，立即执行降级策略（如临时切回上一个稳定版本的 Prompt/模型路由，或提高拒答阈值、引导转人工）。
> 
> 2. **第二步：端到端日志排查与四层归因（RCA 分析）**：
>    调取报错 Session 的全链路 Trace 日志（包含原始 Query、分词结果、检索到的 Top-K 片段、组装后的完整 Prompt、模型原始 Output）：
>    - **数据源层**：是否近期上传了矛盾、过期或格式损坏的源文档？
>    - **检索层**：向量相似度阈值是否过低召回了无关垃圾噪音，或者 Chunk 切断了关键上下文？
>    - **模型层**：上游模型提供方是否发生了隐式模型权重更新或上下文长度截断？
>    - **后处理层**：是否因为正则提取或 JSON 解析失败导致直接返回默认兜底文案？
> 
> 3. **第三步：分流修复与长效闭环**：
>    - 属于文档问题的，推动业务管理员下架清洗；属于检索问题的，调整切块策略与 Rerank 权重；属于指令漂移的，强化 System Prompt 负向约束。
>    - **最关键动作**：将本次客诉中的所有 Bad Case 转化为标准的 **Regression Test Case（回归评测用例）**，加入自动化测试流水线，确保后续任何系统改动绝不再犯同样错误。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **扣分表现**：一遇到问题就盲目甩锅给大模型 API 服务商，没有全链路 Trace 日志分析的工程思维。
- 🔄 **高频追问**：*如果排查发现是第三方大模型 API 服务商偷偷更新了底层模型导致的效果退化，你在架构上如何防范这种风险？*
:::
