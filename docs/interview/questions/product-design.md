# AI 原生产品与场景设计题库

产品设计题是 AI PM 面试中占比最重的一环。面试官通过此类题目考察你**是否真正做过复杂的 AI 原生业务系统，能否妥善处理多模态输入、工具调用编排、权限隔离、人机协同（Human-in-the-loop）与确定性兜底机制**。

---

## 题目 1：请从 0 到 1 设计一个企业级 AI 知识库系统，说明关键产品链路与设计决策。

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察对 Enterprise RAG 全链路工程与产品架构的掌握，包括文档解析、多租户权限、混合检索、溯源呈现与后台运营闭环。
- **解题框架**：
  1. **输入与数据层**：多源接入（PDF/Word/Markdown/飞书/语雀）、文档解析与智能切分（Chunking）、元数据标引（Metadata）。
  2. **权限与安全层**：企业组织架构集成、文档级与段落级 ACL 权限过滤、敏感词脱敏。
  3. **检索与增强层**：混合检索（向量语义 + BM25 关键词） + 重排序（Rerank）。
  4. **交互与消费层**：流式生成、角标原文引用高亮、一键跳转溯源、拒答与置信度提示。
  5. **运营与治理后台**：未命中问答聚类、Bad Case 标注、文档冷热度监控与知识过期更新机制。
:::

::: tip 💡 参考回答示范
> “设计一个真正能在企业落地、员工敢信敢用的 AI 知识库，绝不仅是‘把文档扔进向量库’，我将其拆解为五个核心子系统：
> 
> ```mermaid
> flowchart LR
>     A[数据接入与解析] --> B[混合检索与权限过滤]
>     B --> C[生成与证据溯源]
>     C --> D[端侧协同交互]
>     D --> E[运营与评测闭环]
> ```
> 
> **1. 数据接入与解析治理（决定数据质量上限）**：
> 针对复杂企业文档（如带嵌套表格、流程图的 PDF 制度），采用 Layout-aware 解析引擎（如 MinerU），保留标题层级结构与表格 Markdown 语义。采用‘父子切块（Parent-Child Chunking）’策略：子块（200-300 Token）用于精准语义匹配，父块（1000 Token）作为上下文送给大模型，避免信息断章取义。
> 
> **2. 企业级权限隔离与混合检索（保障合规与准度）**：
> 在向量库中为每个 Chunk 绑定组织架构 ACL 标签。检索时执行‘先过滤后检索（Pre-filtering）’，确保员工绝对查不到权限外的薪酬或财务数据。同时采用 **Dense（向量） + Sparse（BM25 关键词） + Rerank 混合检索**，彻底解决专有名词、产品型号等关键词搜不准的行业顽疾。
> 
> **3. 交互呈现与可信溯源（建立用户信任）**：
> 答案中强制插入数字引用角标 `[1]` `[2]`。点击角标直接在右侧分屏打开源文档，并自动滚动到对应高亮段落。若置信度低于阈值，系统主动拒答并提示：*‘知识库中未找到确切依据，为您推荐相关联系人或转接人工’*。
> 
> **4. 后台知识飞轮与运营治理（解决知识时效性）**：
> 搭建‘未命中问题看板’，通过无监督聚类将用户常问但知识库缺失的高频问题归纳成待办工单，推送给业务知识库管理员补充，形成‘问答 $\rightarrow$ 发现盲区 $\rightarrow$ 补充文档 $\rightarrow$ 质量提升’的持续飞轮。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **扣分回答**：只讲前端聊天框界面，完全忽略文档解析（如表格/扫描件/乱码）、企业权限隔离和后台知识更新机制。
- 🔄 **高频追问**：*如果知识库里有新旧两版产品手册，内容相互冲突，大模型生成了旧版本的回答，你从产品层面怎么根治？*
:::

## 题目 2：如何设计一个多工具调用的销售线索处理 Agent（Sales Agent）？

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察候选人设计复杂 Agent 工作流（Workflow）的能力，涉及多意图路由、外部工具调用（CRM/邮件/日历）、状态机维护与高危操作的人工确认。
- **解题框架**：任务拆解 $\rightarrow$ 工具库定义 $\rightarrow$ 意图规划与状态机 $\rightarrow$ 异常重试与人机协同 $\rightarrow$ 交付确认。
:::

::: tip 💡 参考回答示范
> “销售线索处理是一个典型的高价值多步骤 Agent 场景。我将其设计为 **‘规划-执行-确认-沉淀’** 的确定性工作流 Agent：
> 
> 1. **标准化工具集（Tools Definition）**：
>    - `search_company_info`：调用企查查/天眼查 API 获取客户规模、融资与主营业务。
>    - `query_crm_duplicate`：查询内部 CRM 是否有销售人员已跟进该客户（防止撞单）。
>    - `score_lead_quality`：根据客户画像与线索评分规则给出 BANT 评级（A/B/C/D）。
>    - `create_crm_lead`：将合格线索写入 CRM 并自动分配销售。
>    - `draft_outreach_email`：根据客户行业背景生成个性化破冰邮件草稿。
> 
> 2. **Agent 核心执行状态机与风控（Human-in-the-loop）**：
>    - **自动化阶段**：Agent 接收新线索 $\rightarrow$ 并行调用工具查背景与查重 $\rightarrow$ 计算线索分值与推荐跟进策略。
>    - **强人工确认（HITL）卡点**：对于‘新建 CRM 客户’和‘发送正式邮件’等对外及写库动作，**严禁 Agent 全自动执行**。系统在界面上生成一张结构化卡片（包含客户摘要、线索评级、建议草稿），由销售一键确认或微调后再触发 API 执行。
> 
> 3. **容错与超时机制**：
>    为 Agent 设置最大重试次数（Max Iterations = 3）和 Token 上限，单步工具失败时降级走人工工单，并在界面展示透明的‘思考与调用步骤日志’，降低用户等待焦虑。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **扣分回答**：“让大模型自由发挥，全自动给客户发送营销邮件并自动改写 CRM 数据库。”（完全缺乏企业级风控和合规常识）。
- 🔄 **高频追问**：*如果外部 API 报错或者大模型抽取的参数不符合 JSON Schema 规范，你的 Agent 如何自我纠错？*
:::

## 题目 3：如何设计 AI 产品的“人机协同（Human-in-the-loop）”机制与失败状态交互？

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察候选人对 AI 不确定性特征的深度理解。优秀的产品经理不会假定 AI 百分百正确，而是通过极致的 UI/UX 设计将人机摩擦降到最低。
- **解题框架**：
  1. **事前（Pre-execution）**：意图澄清、预置选项、透明的预期管理。
  2. **事中（In-progress）**：流式输出（Streaming）、中间状态指示（如正在搜索文档/调用工具）、支持随时打断（Stop Generating）。
  3. **事后（Post-generation）**：分块可编辑、一键采纳/替换、多版本对比（Diff）、清晰的置信度标示与拒答兜底。
:::

::: tip 💡 参考回答示范
> “AI 产品与传统软件最大的区别在于**‘从确定性交付变为概率性协同’**。设计人机协同与失败状态时，我坚持三个原则：
> 
> 1. **全流程透明度与控制权归还用户（User in Control）**：
>    - **过程可感知**：当 Agent 执行耗时任务时，用折叠步骤卡片实时展示状态（如：*‘🔍 正在检索 2024 年 Q3 财报...’* $\rightarrow$ *‘📊 正在提取毛利率数据...’*），让用户清楚 AI 的思考路径。
>    - **随时可刹车**：提供即时的‘终止生成’按钮，避免用户在模型明显偏离意图时被迫等待。
> 
> 2. **结果‘可消费、可编辑、可对比’（Consumable & Editable）**：
>    - 拒绝只给一段只读的长文本。例如在 AI 写作或报告助手场景中，采用 **Canvas 双栏交互**（左侧对话、右侧富文本文档），支持对单段落划词‘扩写/润色/精简’，并提供修改前后的 Diff 对比与‘撤销/采纳’动作。
> 
> 3. **优雅的降级与失败兜底（Graceful Degradation）**：
>    - **低置信度处理**：当系统判定相关性不足时，不强行编造，而是采用‘诚实拒答 + 引导追问’（如：*‘我无法确定该报销标准，您是指国内出差还是海外出差？’*）。
>    - **系统故障兜底**：模型超时或接口报错时，给出明确原因，并保留用户输入的 Prompt，提供一键‘换个模型重试’或‘转为人工工单’通道。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **扣分设计**：弹窗弹出一长串系统错误代码（如 `504 Gateway Timeout`），或者清空用户的输入框让用户重新手打一遍。
- 🔄 **高频追问**：*在 C 端和 B 端场景中，人机协同的干预颗粒度应该有什么差别？*
:::

## 题目 4：AI 搜索（如 Perplexity / 秘塔）与传统搜索引擎在产品交互与系统架构上有何本质差异？

::: info 🎯 核心考察点与解题思路
- **考察意图**：考察对生成式搜索（Generative Search / Answer Engine）的产品形态变革与底层商业模式变迁的洞察。
- **解题框架**：从信息组织形式、交互链条、后端检索架构、可信度保障与商业变现五个维度展开对比。
:::

::: tip 💡 参考回答示范
> “AI 搜索不是传统搜索引擎的简单换皮，而是从‘信息索引分发’向‘直接交付答案与洞察’的物种演进：
> 
> | 维度 | 传统搜索引擎（Google/Baidu） | AI 原生搜索（Perplexity/秘塔） |
> | :--- | :--- | :--- |
> | **核心交付物** | 10 条网页链接列表（用户自行点击筛选） | 结构化综述答案 + 关键证据引用（直接消费） |
> | **查询理解** | 关键词切词匹配（Keyword Matching） | 复杂自然语言语义理解 + 自动子问题拆解（Query Decomposition） |
> | **交互模式** | 单次单向搜索（搜完即走） | 多轮对话深入探索 + 主动推荐延伸问题（Topic Exploration） |
> | **后端架构** | 网页抓取 $\rightarrow$ 倒排索引 $\rightarrow$ PageRank 排序 | 实时多源检索 $\rightarrow$ 网页抓取清洗 $\rightarrow$ Rerank $\rightarrow$ LLM 事实综合与溯源 |
> | **商业模式** | 关键词竞价排名广告（CPC/CPM） | 订阅制会员（SaaS/Pro） + API 消费 + 场景化商品推荐 |
> 
> **产品核心挑战**：
> AI 搜索最大的痛点在于**单次查询成本高（传统搜索百倍以上）**和**时效性与幻觉控制**。因此产品上必须做到‘快搜与深搜（Deep Research）分级’：高频简单问题走快速小模型，复杂研报问题走多步 Agent 并发检索。”
:::

::: warning ⚠️ 踩坑提示与扣分点
- ❌ **误区**：“AI 搜索会彻底消灭网页，以后没人需要去原网站了。”（忽视了内容创作者生态、版权诉讼风险以及深度一手信源的不可替代性）。
- 🔄 **高频追问**：*如果你来负责 AI 搜索的体验优化，你首要关注哪三个核心指标？*
:::
