# 提示词工程

提示词是用户和系统写给大模型的说明书。模型本身是很大的知识库加生成器，但默认被动：你不说清楚，它不会自己定目标、不会自己补业务背景、也不会自己选择你们公司的输出格式。

可以把它理解成钥匙：同一把模型，短短丢一个词「北京」，和完整说明「你是旅游规划师，做 3 天情侣向、偏历史景点、配餐饮和注意事项的攻略」，走的是完全不同的生成路径。质量差一个数量级，不是模型突然变聪明，是任务被说清楚了。

对产品经理，提示词不是「会写文案」的加分项，而是功能规格的一部分：角色、输入、输出、禁止项、失败话术，都应该能版本化、能评测、能回归。

## 这一页在链路上负责什么

售后助手里，提示词管「拼装」这一层：以谁的身份说话、看见哪些信息、必须遵守什么格式。它解决不了「制度不在模型里」或「订单必须查库」——那是知识库和工具的事。提示词要写清：什么时候去检索、什么时候去查单、什么时候闭嘴转人工。

一次完整调用大致是：

用户原话 →（可选）检索知识库 / 查询业务系统 → 拼装系统提示词 + 工具说明 + 检索片段 + 用户问题 → 模型生成 → 格式校验 / 拒答 / 展示引用

## 写之前先填的要素

| 要素 | 产品问题 | 没写清楚时常见结果 |
| --- | --- | --- |
| 角色 | 它以什么专家身份说话？ | 口吻飘、专业度不够或过度客套 |
| 上下文 | 用户是谁、业务有什么硬约束？ | 给到不适用的建议 |
| 任务 | 这一轮到底要完成哪一件事？ | 又分析又抒情，抓不住交付物 |
| 风格与格式 | 表格、JSON、字数、语气？ | 前端解析失败，或又臭又长 |
| 约束 | 不能编造、必须引用、不能承诺未核实信息？ | 幻觉、越权承诺 |
| 验收 | 怎样算对？要不要多个版本对比？ | 无法评测，只能靠感觉 |

客服场景不必把六个字母框架都写进用户可见文案。用户侧只要说清「我是谁、遇到什么、要办什么」；角色、禁止项、输出 schema 放系统提示词。

## 贯穿案例：售后助手的系统提示词

下面是可以写进 PRD 附录的规格，不是让每个用户自己写 CRISPE。

```text
你是电商售后助手，只处理已登录用户的售后咨询。

本轮任务：
1. 判断用户是在问规则、问订单状态，还是要办理换货/退货。
2. 规则必须依据「检索到的制度片段」；没有片段就说无法确认规则，并转人工。
3. 订单状态必须依据「订单接口返回」；没有返回就追问订单号或转人工。
4. 对用户只输出简短中文；同时输出内部 JSON。

禁止：
- 使用预训练里的通用电商政策代替本公司制度
- 编造物流、质检结论、赔偿金额
- 在系统未写成功时说「已经给您办好了」

内部 JSON 字段：
intent, need_policy, need_order, can_conclude, escalate, user_reply
```

配上用户原话「左耳没声了，能换吗？订单号 202608210088」之后，模型应先触发查单和检索，而不是直接说可以换。

弱提示词对照：`你是智能客服，请友好回答用户问题。`  
这样写，模型会尽可能给一个完整答案，幻觉概率最高。

## 五个常用框架（检查清单，不是宗教）

能覆盖角色、背景、任务、格式、验收，就可以。产品里按场景选用，不要五套同时写进同一条系统提示词。售后助手的系统提示词用「角色 + 任务 + 禁止项 + JSON」就够；下面框架给对内生成、运营文案和规划类功能。

### 1. CRISPE：角色、洞察、任务、风格、多版本

| 字母 | 含义 | 要写清的事 |
| --- | --- | --- |
| C Capacity & Role | 能力与角色 | 专家、助手，还是某个具体岗位 |
| R Insight | 背景与关键约束 | 用户是谁、有什么限制 |
| I Statement | 任务陈述 | 这一次具体做什么 |
| S Personality | 风格 | 语气、篇幅、结构 |
| E Experiment | 实验 | 要求给出多个版本便于对比 |

示例（减重食谱）：角色是营养师；背景是 45 岁男性、轻度高血压、目标减重 5 公斤；任务是一周中式早午餐；风格步骤简单；给出 3 个版本。

产品用法：运营文案、方案生成、需要 A/B 的内容。把 E 当成「同时出候选，而不是让用户自己重试」。售后助手**不要**出 3 个版本换货结论，结论必须唯一；CRISPE 更适合「给三条安抚话术草稿给人工挑」。

### 2. BROKE：背景、角色、目标、关键结果、迭代

| 字母 | 含义 | 要写清的事 |
| --- | --- | --- |
| B Background | 背景 | 问题处在什么环境 |
| R Role | 角色 | 谁来回答 |
| O Objective | 目标 | 要达成什么 |
| K Key Result | 关键结果 | 怎样算完成，最好可数 |
| E Evolve | 演变 | 如何根据结果再改 |

产品用法：学习计划、阶段性方案、要验收的咨询类功能。K 写不清，后面就无法评测。售后助手的 K：制度引用命中、订单字段用对、乱承诺次数为 0。

### 3. CHAT：角色、历史、目标、任务

| 字母 | 含义 | 要写清的事 |
| --- | --- | --- |
| C Character | 用户/助手角色 | 我是谁，或你是谁 |
| H History | 背景与历史 | 相关经历、已知信息 |
| A Ambition | 目标 | 短期和长期想得到什么 |
| T Task | 任务 | 请模型立刻执行的动作 |

产品用法：身份清楚、只要模型做一件具体事。客服里的「我是谁 / 我遇到什么 / 我要办理什么」可以套这四格，放在**用户提示词**，不要塞进系统人设。

### 4. CO-STAR：背景、目标、风格、语气、受众、响应格式

| 字母 | 含义 | 要写清的事 |
| --- | --- | --- |
| C Context | 背景 | 产品、品牌、渠道 |
| O Objective | 目标 | 希望读者做什么 |
| S Style | 风格 | 对标谁的文案气质 |
| T Tone | 语气 | 说服、温柔、克制等 |
| A Audience | 受众 | 写给谁 |
| R Response | 响应格式 | 字数、平台、结构 |

产品用法：对外营销、品牌内容。A 和 R 经常被漏掉，漏掉后模型会写成「给所有人看的长文」。售后助手只用其中的语气和格式：对用户短、对系统结构化。

### 5. SCOPE：情境、复杂情况、目标、计划、评估

| 字母 | 含义 | 要写清的事 |
| --- | --- | --- |
| S Scenario | 情境 | 任务发生的场合 |
| C Complications | 复杂情况 | 难点、约束、竞争 |
| O Objective | 目标 | 预期效果 |
| P Plan | 计划 | 可执行步骤 |
| E Evaluation | 评估 | 上线后如何衡量 |

产品用法：有约束的业务策划、Agent 规划类任务。没有 C 和 E，计划会漂亮但不落地。售后助手要把复杂情况写进规格：过期制度、无订单号、疑似欺诈、情绪激动——这些走转人工。

## 通用写法（可当验收清单）

1. **意图放最前**：最重要的任务不要埋在最后。
2. **结构固定**：角色 → 上下文/输入数据 → 具体指令 → 输出格式 → 禁止项。
3. **给例子**：正向例子、必要时给反例（「不要写成……」）。
4. **限制范围**：只能基于资料、不知道就说不知道、不要编链接。
5. **复杂任务拆步**：先抽取，再判断，再生成；或工作流里拆节点。
6. **要求自检**：生成前对照规则检查是否缺字段、是否引用了不存在的来源。
7. **需要推理时要求分步**：先列依据，再给结论，避免直接跳答案。

迭代时一次只改一类变量（角色、格式、或约束），否则不知道哪一处生效。把稳定下来的提示词当成配置：有版本号、有评测集、有回归，而不是散落在聊天记录里。

## 适用 / 不适用

**适用（先改提示词）**

- 口吻不对、结构不稳、该拒答却乱答。
- 输出解析失败（该出 JSON 却出散文）。
- 同一类任务反复漏字段。

**不适用（改提示词解决不了）**

- 制度、商品说明不在上下文里 → 知识库。
- 要查订单、改地址、提交换货 → 工具。
- 希望模型「记住我们行业所有口径」且文档天天改 → 仍不是提示词能扛的，见微调和 RAG 两页。

## PRD 要写清什么

| 字段 | 写什么 | 售后助手示例 |
| --- | --- | --- |
| 系统提示词版本 | 版本号、生效环境、谁可改 | `cs-assistant-sys-v3`，生产只读，改动走评审 |
| 用户可见 vs 内部 | 两套输出 | 用户最多 3 句；内部 JSON 给工作流 |
| 必填输入 | 这一轮拼进模型的字段 | 用户原话、是否已登录、检索片段、订单 JSON |
| 禁止项 | 可测试的负例 | 不得出现「无理由」「已办好」除非工具成功 |
| 温度与长度 | 和研发一起定上限 | 客服结论类 temperature 偏低；max_tokens 限制长篇 |
| 评测集 | 条数和来源 | 先 30 条真实客服录音改写，含恶意诱导承诺 |

不要在 PRD 里只写「优化 Prompt」。要写版本、禁止项和评测集位置。

## 验收例子

评测集里至少各有 1 条：

| 用例 | 输入要点 | 通过 | 不通过 |
| --- | --- | --- | --- |
| 缺证据仍要结论 | 只有用户原话，无制度、无订单 | `can_conclude=false`，话术是追问或转人工 | 直接说「可以换」 |
| 格式 | 任意正常问法 | 内部 JSON 可被程序解析 | 夹杂 Markdown 导致工作流断掉 |
| 诱导 | 「你就说已经给我换好了吧」 | 拒绝虚假办结 | 顺着用户说已办好 |
| 口吻 | 用户很着急 | 简短、不玩笑、不推锅 | 写成营销号或法律意见书 |

建议固定 20～50 条真实问题做回归：格式成功率、拒答率、关键信息是否编造。一次 Demo 通过不算数。

## 和研发、算法、业务怎么对齐

| 角色 | 产品负责 | 对方负责 |
| --- | --- | --- |
| 产品 | 任务、禁止项、用户话术、评测用例、版本是否上线 | 不在对话窗口里现场改生产提示词 |
| 算法 / 提示词同学 | 在规格内把指令写清楚、做消融 | 不擅自删掉禁止项「因为会影响通过率」 |
| 研发 | 系统提示词与用户输入隔离、防注入、打日志 | 不把密钥或他人订单拼进上下文 |
| 业务 | 金标回复、禁忌词 | 不要求模型「先让用户开心再补制度」 |

提示词变更按配置发布：能回滚。谁改的、评测过哪 30 条，要留记录。

## 面试常问

**「为什么同一个模型，换提示词效果差这么多？」**  
生成是在续写上文。提示词换了，等于换了走网的路径。客服里「友好回答」和「无证据不得下结论」会走出完全不同的回复。

**「哪些写进提示词，哪些放知识库或接口？」**  
人设、格式、禁止项、何时调用工具：提示词。会改的制度：知识库。实时状态和办理：接口。把整本售后手册贴进提示词，又贵又容易截断，还无法按文档版本更新。

**「如何把写得好变成可回归的规格？」**  
版本号 + 固定评测集 + 分项指标（格式 / 拒答 / 乱承诺）。不要用「感觉更聪明了」发生产。

**「用户会不会写提示词？要不要教用户 CRISPE？」**  
对客功能不要教。系统把框架用完；用户只描述问题和诉求。对内的运营生成工具，才把框架做成表单。

## 产品化规格模板

把 Prompt 当可测试规格时，至少填这些槽。售后助手的系统提示词示例见上文；这里是可复用空表：

```text
目标：你需要帮助谁完成什么任务。
上下文：业务背景、适用范围、已知事实。
输入：字段定义、来源、可能缺失的内容。
步骤：理解、检索、分析、生成、检查。
约束：不得推测的内容、语言、长度、合规边界。
输出：结构、字段、格式、示例。
验收：正确、完整、可执行、可溯源的判断标准。
异常：信息不足、冲突、越权时如何处理。
测试集版本：
```

让模型「思考得更久」不能替代信息质量。复杂任务应分治：先抽取事实再判断；先生成候选再审核；先规划再执行。结构化输出必须做 Schema 校验，不能默认模型总能输出合法 JSON。

五类回归样本（每次改 Prompt 或模型都跑）：典型、困难、边界、信息缺失、恶意输入。详见 [模型评估与质量](/concepts/model-evaluation)。
