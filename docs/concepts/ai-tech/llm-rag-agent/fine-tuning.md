# 微调该不该做

微调（Fine-tuning）是在已经预训练好的大模型上，用你们自己的领域数据继续训练，让它更适应该任务或该行业。通用模型像全科本科生，什么都懂一点，深度不够；微调像读研：还是同一个人，但吃过专业资料、做过专业练习。

产品讨论微调时，真正要回答的不是「微调酷不酷」，而是：**提示词、RAG、工具都试过之后，缺口还在不在，缺口值不值一笔训练和持续运维的成本。**

## 这一页在链路上负责什么

售后助手前面几层已经能：按口径说话、引用制度、查订单、确认后建单。微调动的是**模型权重**，不是文档，也不是接口。这一页给 go / no-go 清单和一笔练手账。默认答案是：**售后制度类产品先不要微调。**

## 微调在解决什么

- 让模型更熟悉领域用语、文档结构和你们的口径。
- 让输出格式更稳（总是按某种表、某种 JSON、某种客服话术）。
- 在专属测试集上，把准确率从「能用」推到「可过业务阈值」。有实验报告称企业专属集上可能看到约 10% 量级提升——这只说明「有时值得量化」，不是承诺。

它不自动解决：

- 文档天天改（更该 RAG）
- 订单实时变（更该查库）
- 提示词角色都没写清（先改提示词）
- 没有评测集（你无法知道微调是变好还是过拟合）

## 贯穿案例：耳机换货该不该微调

用户仍问那句能不能换。

| 你听到的痛点 | 先核实 | 通常该做 | 不该做 |
| --- | --- | --- | --- |
| 「模型不懂我们售后」 | 知识库有没有现行制度、检索是否命中 | 补文档、改切分、强制引用 | 立刻微调 |
| 「有时候 7 天会说成 15 天」 | 是片段没召回，还是提示词没约束数字 | RAG + grounded 校验 | 用几百条对话去训「记住 7」 |
| 「口吻不像我们客服」 | 系统提示词和示例全不全 | 提示词加 3～5 条正反例 | 为口气微调（除非量大且口径极稳） |
| 「JSON 经常坏」 | schema 有没有后处理 | 约束解码 / 校验重试 | 微调可以列为实验，但先上校验更便宜 |
| 「数据不能出域」 | 是否真的合规硬约束 | 私有化部署通用模型 + RAG | 把微调当成唯一合规方案 |

只有一种售后相关情况比较像微调实验：历史工单里**判断口径极稳、文档很难穷尽**，例如「什么程度算人为损坏」要靠大量已质检案例才能学；而且你愿意持续标数据、做回归、接受模型升级后重训。即便如此，案例库用 RAG 往往仍更先试。

## 为什么不先上提示词和 RAG

三件事会把团队「逼」向微调，但每件都要先核实是不是真约束：

**1. 准确率**  
通用模型 + RAG 仍过不了业务线，且错误类型是「领域判断/口径」而不是「没检索到」。这时才有微调实验的资格。

**2. 上下文长度和费用**  
提示词窗口有上限。提示越长，越贵，也越容易截断。把整本手册塞进提示词，既贵又不稳。手册应进 RAG；只有「反复出现、必须印在行为里」的模式，才考虑微调。

**3. 调用量和数据出境**  
量小的时候，用通用 API 往往更划算：无前置训练成本。量大以后，多出来的 Token 费可能超过自建/微调的前置成本，需要算账。数据不能发给第三方时，开源模型 + 自有微调的必要性上升。

## 决策清单（go / no-go）

下面全部为「是」，才值得开一轮**离线实验**（还不是生产切换）：

1. 已有固定评测集：好样本、坏样本、边界样本，且业务认金标。  
2. 提示词已版本化，做过至少一轮回归。  
3. 知识类问题已走 RAG，状态类问题已走工具，Bad Case 已按层复盘。  
4. 剩余错误以「同分布下的口径/格式」为主，而不是缺文档、缺接口。  
5. 训练数据合法：有权使用、已脱敏、不含不应进模型的个人信息。  
6. 有人负责数据版本、训练配置、评测报告、回滚。  
7. 算过账：前置成本有机会在可接受周期内被 Token 节省或质量收益盖住，或合规强制必须自有权重。

有一条为「否」，产品结论写 **no-go**，写明缺的是评测、RAG 还是合规，而不是「算法不配合」。

## 练手账（数字只用来算，不是报价）

假设售后助手日均 5000 次对话，每次约 2000 input + 400 output tokens，一个月约 15 万次。

下面单价是**随意假设**，方便把公式写进评审材料。上线必须换成你们合同里的价：

- 假设输入 ¥0.01 / 千 tokens，输出 ¥0.03 / 千 tokens  
- 月 Token 费 ≈ 15 万 × (2000×0.01 + 400×0.03) / 1000 = **约 ¥4800**

对照微调一次的常见显性成本（同样是假数）：

| 项 | 假想投入 | 说明 |
| --- | --- | --- |
| 标注 | 2000 条 × ¥8 = ¥16000 | 要客服班组长标，不是实习生随便写 |
| 训练与试错 | GPU 与调参 ¥2 万～5 万量级 | 失败重跑很常见 |
| 评测人力 | 2 人 × 1 周 | 含旧能力有没有被训坏 |
| 制度再改 | 又要标、又要训、又要回归 | 售后政策改一则时限就会发生 |

结论怎么写进评审：

- 若质量问题是「制度没入库」，花 ¥4800 级 API + 运营更新文档，比花数万微调更合理。  
- 若 API 月费已到数十万，且评测证明微调能少传很多上下文，再把「上下文缩短省下的 Token」算进回收周期。  
- 若合规禁止数据出境，账是「私有化推理 + 是否还要微调」两笔，不要混成一笔「上本地就等于微调」。

灾难性遗忘的产品表现：微调后换货更稳了，但问候、转人工、拒答欺诈变差。所以必须拿**旧评测集一起回归**，不能只报新任务提升。

## 产品经理需要认识的路线（不必会配参）

| 名称 | 在做什么 | 你会在什么场合听到 |
| --- | --- | --- |
| SFT 监督微调 | 用人工标好的示范数据，按监督学习方式继续训 | 「先让它按我们的格式说」 |
| RLHF | 把人的偏好当奖励，让输出更符合期望 | 对齐口吻、减少有害输出 |
| RLAIF | 类似 RLHF，反馈来自 AI，降低部分人工 | 要规模化偏好数据 |
| Prompt / Prefix Tuning | 基座参数基本不动，为任务训一小段前缀或附加参数 | 多任务、少动基座 |
| LoRA 等高效微调 | 认为大模型过参数化，只训低维关键适配模块 | 省算力的常见工程选项 |

可以记：全量改基座最贵；冻住基座、只训一小块，是为了在效果和成本之间折中。具体选哪条是算法和平台的事；产品要定义的是数据从哪来、怎样算合格、谁批准上线。

## 建议决策顺序

1. 建评测集（好样本、坏样本、边界样本）。  
2. 改提示词和输出 schema。  
3. 知识类问题走 RAG，状态类问题走工具。  
4. 工作流把稳定工序固定住。  
5. 仍然达不到阈值，且数据合法可训练，再开微调实验。  
6. 微调后必须回归：旧能力有没有被训坏（灾难性遗忘的产品表现）。

微调一旦上线，就要当模型版本管理：数据版本、训练配置、评测报告、回滚策略。不要当一次性项目。基座厂商发新模型时，默认假设要重评、可能要重训。

## 适用 / 不适用

**适用（实验资格）**

- 输出格式或领域判断在 RAG/工具之后仍系统性偏差。  
- 有稳定、合法、可更新的示范数据。  
- 有合规或成本账证明值得改权重。

**不适用**

- 用微调「记住」本周活动规则。  
- 评测集还没有，只凭领导 Demo。  
- 想替代鉴权和工具调用。

## PRD 要写清什么（一旦真做）

| 字段 | 写什么 |
| --- | --- |
| 假设 | 当前 Bad Case 类型统计，证明不是检索/工具问题 |
| 数据 | 来源、条数下限、脱敏规则、谁验收标注质量 |
| 成功标准 | 新集提升多少、旧集允许掉多少（例如旧集不得掉超过 2 个点） |
| 对照 | 必须和「未微调 + 同一提示词/RAG」同集对比 |
| 发布 | 灰度比例、回滚到哪一版基座、谁签字 |
| 运维 | 制度变更是否触发重训；基座升级流程 |

开实验的 PRD 和开生产切换的 PRD 要分开。很多团队把实验成功当成上线，缺少回滚。

## 验收例子

| 用例 | 通过 | 不通过 |
| --- | --- | --- |
| 实验门禁 | 复盘记录显示 Top 错误是口径，不是空知识库 | 「感觉不懂行业」就立项 |
| 同题对比 | 同一 50 条，微调版格式更好，引用仍来自 RAG | 微调版开始不检索，直接背过期 15 天规则 |
| 旧能力 | 转人工、拒答诱导承诺仍过线 | 换货话术漂亮了，却答应「已经打款」 |
| 数据 | 训练语料无完整身份证号、他人订单 | 把生产日志原样倒进训练集 |

## 和研发、算法、业务怎么对齐

| 角色 | 负责 |
| --- | --- |
| 产品 | go/no-go、成功标准、是否允许掉旧能力、灰度 |
| 算法 | 方法选型、训练、报告；不能自己宣布「可以上生产」 |
| 业务 | 金标和标注争议裁决 |
| 法务 / 安全 | 数据能否训练、能否出境 |
| 研发 | 推理部署、版本、回滚开关 |

评审会上先放 Bad Case 分类饼图。没有这张图，不讨论 LoRA。

## 面试常问

**「业务说模型不懂我们行业，你怎么判断？」**  
先看错的是事实、状态还是口径。事实补 RAG，状态补工具，口径稳定且有数据才谈微调。售后「能不能换」几乎总是前两件事。

**「提示词已经很长了，是不是该微调？」**  
长提示常常是该 RAG 或该拆工作流的信号。先称 Token、看截断、看手册是否误塞进系统提示词。

**「没有评测集为什么不能做微调决策？」**  
你分不清变好、过拟合，还是把旧能力训坏。没有对照集的提升是故事，不是决策。

**「微调能不能替代知识库？」**  
不能当主方案。权重里的制度难更新、难引用、难审计。制度走文档。
