# 大语言模型基础

大语言模型根据上下文预测后续 Token，可以完成生成、摘要、抽取、分类、问答、代码和工具调用等任务。读者需要理解它的能力边界，而不是只把它当成“更聪明的搜索框”。

## 必懂概念

| 概念 | 技术含义 |
| --- | --- |
| Token | 成本、上下文和输出长度的计量单位。 |
| 上下文窗口 | 模型一次能看到多少内容。 |
| Temperature | 控制随机性和多样性。 |
| 结构化输出 | 让结果能进入系统字段。 |
| 幻觉 | 模型编造看似合理的信息。 |

## 系统设计重点

LLM 适合处理开放语言，但不等于事实数据库。企业知识、实时数据、权限数据要通过 RAG、工具调用或业务系统提供。高风险输出要有引用、校验和人工确认。

## 常见坑

- 把所有历史对话都塞进上下文。
- 用大模型替代数据库权限。
- 不设计拒答和追问。
- 只测几个顺利 Demo，不建评测集。

## 模型选择不是排行榜选择

选模型时要看任务，而不是只看谁在榜单上更强。

| 任务 | 关注点 |
| --- | --- |
| 客服问答 | 中文理解、RAG grounded、拒答质量、延迟。 |
| 合同抽取 | 长文档、结构化输出、字段准确率。 |
| 代码助手 | 代码能力、工具调用、上下文长度。 |
| 运营文案 | 风格、可控性、品牌安全。 |
| Agent 调研 | 工具调用、规划、成本、可追踪。 |

同一个产品里也可以多模型组合：小模型做分类，大模型做复杂生成，专用模型做 Embedding 或 Rerank。

## 上线前最小评测

最小评测集可以先覆盖：

1. 高频正常问题。
2. 长输入和短输入。
3. 模糊问题。
4. 资料缺失问题。
5. 权限边界问题。
6. 安全和敏感问题。
7. 输出格式要求。

有了这组样本，模型、Prompt、RAG、工具调整才有可比较的依据。

## 工程实践要点

大模型应用的关键不是“接入模型”，而是把模型放进可控链路：用户输入、上下文、知识库、工具、权限、输出格式、人工确认和日志追踪。每个环节都可能决定功能能不能上线。

| 能力 | 适合解决 | 必须补上的约束 |
| --- | --- | --- |
| LLM | 理解、生成、总结、抽取。 | 输出格式、拒答、安全边界。 |
| RAG | 接企业知识和最新资料。 | 来源、权限、切分、召回和引用。 |
| Tool Calling | 查询或修改业务系统。 | 服务端鉴权、参数校验、二次确认。 |
| Agent | 路径不固定的多步任务。 | 步数预算、工具范围、日志和退出条件。 |

## 示例代码

下面是一个最小 LLM 调用伪代码，展示输入、上下文、模型调用和输出校验的结构：

```python
def answer(question, context):
    prompt = f"""基于资料回答问题。
资料：{context}
问题：{question}
"""
    result = call_model(prompt)
    if not result.strip():
        return {"status": "empty", "answer": None}
    return {"status": "ok", "answer": result}
```

真实系统需要把检索、权限、引用、结构化输出、日志和错误处理补齐。

## 技术细节拆解

大语言模型基础 可以拆成输入、处理、输出和指标四层。这样读的时候不会停留在概念名，而是能看到它在系统里接收什么、改变什么、产出什么。

| 层次 | 具体内容 |
| --- | --- |
| 输入 | 用户问题、系统提示词、历史对话、检索片段、工具 schema。 |
| 处理 | 上下文组装、模型调用、工具调用、输出解析、权限校验。 |
| 输出 | 自然语言、JSON、引用、工具结果、拒答信息。 |
| 指标 | 准确率、引用命中率、格式成功率、工具成功率、成本、延迟。 |

## 关键参数和边界

| 参数/边界 | 说明 |
| --- | --- |
| temperature | 越高越发散，越低越稳定。 |
| max_tokens | 限制输出长度，也影响成本和截断风险。 |
| top_p | 控制采样范围，通常和 temperature 配合。 |
| schema | 结构化输出必须有 schema 和校验。 |

## 可运行检查

```python
import json

raw = '{"answer":"可以办理", "confidence":0.82}'
data = json.loads(raw)
assert "answer" in data
assert 0 <= data["confidence"] <= 1
print(data)
```

## 怎么判断学懂了

| 判断点 | 具体标准 |
| --- | --- |
| 格式稳定性 | 结构化输出能否被程序稳定解析。 |
| 证据一致性 | 回答是否能追溯到检索片段或工具结果。 |
| 权限安全 | 不同用户只能检索和调用授权范围内的资源。 |

## 常见误区和排查

| 问题 | 为什么会发生 | 怎么排查 |
| --- | --- | --- |
| 回答没有证据 | 模型自由发挥，没绑定检索片段。 | 强制引用来源并校验引用存在。 |
| 工具参数不合法 | 模型输出 JSON 不符合接口要求。 | 用 schema 校验，失败时让模型重试或拒绝执行。 |
| 权限穿透 | 检索阶段没有按用户权限过滤。 | 把用户身份加入检索条件并记录审计日志。 |

## 这一页在链路上负责什么

售后助手整条链路是：用户原话 → 提示词 → 查制度（知识库）→ 查订单（工具）→ 生成话术 → 校验 / 转人工。

这一页只解决第一件事：**模型是生成器，不是业务系统。** 后面每一层都是在给生成器加证据、加手、加刹车。前面正文已经讲过调用链路和参数；下面补「为什么必须加这些层」，以及产品经理怎么写进需求和验收。

## 原理怎么理解

大模型给人的第一印象，往往是「什么都懂」：能聊天、能写方案、能改代码、能装成某个领域的专家。产品经理如果停在这个印象上，后面很容易把模型当成搜索引擎的升级版，或者当成不会出错的业务系统。

更准确的理解是三步：

1. **海量阅读**：训练时吃进互联网上能公开抓到的文本、代码、对话、书籍和网页片段，覆盖常识和大量专业碎片。
2. **学习搭配**：不是按百科目录记住条目，而是统计词与词、句与句、风格与风格之间的共现和上下文关系。
3. **生成回答**：接到提示词后，从这张巨大的关系网里，按概率把「接下来最像人类会写的词」一个个拼出来。

### 和搜索引擎差在哪

| | 搜索引擎 | 大模型 |
| --- | --- | --- |
| 知识怎么来 | 抓取页面，建索引，按相关度召回 | 预训练时把公开文本压进参数 |
| 用户拿到什么 | 一串链接，点进去看原文 | 当场生成一段新文本 |
| 强项 | 可跳回出处，适合核对原文 | 改写、总结、按指定格式和语气输出 |
| 弱点 | 不会替你组织答案，排序也可能偏 | 读起来通顺，不保证事实正确 |
| 产品里该当什么 | 找资料、给引用 | 理解意图、组织表达、调用后续环节 |

可以记一句：搜索是「找到已经存在的内容」；大模型是「根据看过的内容重新说一遍」。所以它能讲故事、给建议、按表格输出，也能在没有资料时编得像真的。

### 模型脑子里装的不是目录

人类学「苹果」，会建立概念：一种水果，圆的，红黄绿都有，多汁酸甜；有时也是消费电子品牌。

模型学「苹果」，学的是它常和「吃」「水果」「公司」「手机」一起出现。「天空是＿」在语料里最常接「蓝」，模型并没有看见过天空，也不理解蓝色是什么。

所以脑子里更像一张大网，节点是词和表达，边上是关系强度。这就是常说的神经网络，不必展开公式，产品只要知道：

- 网越密，搭配越像人话。
- 网上没有的关系，模型仍可能「顺着最像的路」编出来。
- 换提示词，等于换一条走网的路径，输出会差很多。

网上常见的几种连接，产品设计时都能用到：

| 连接类型 | 例子 | 产品含义 |
| --- | --- | --- |
| 词语共现 | 「苹果」常和「吃 / 水果 / 公司」一起出现 | 词义会随上下文漂，提示词要消歧 |
| 句法结构 | 主谓宾、把字句 | 要求「用表格输出」通常有效 |
| 逻辑模板 | 「因为…所以…」 | 能模仿推理，不等于真的验证过 |
| 事实关联 | 「巴黎是法国的首都」 | 高频事实较稳，长尾事实易错 |
| 文体套路 | 诗歌、新闻、代码、公文 | 指定风格往往立刻见效 |

### 生成时到底在干什么

用户问题进入模型后，并不是先「查标准答案再抄写」，而是：

1. 把问题（提示词）当成已经写下的上文。
2. 在参数里找「接下来最可能连贯」的词。
3. 写出一个词，再把它当作新的上文，继续写下一项。
4. 直到结束符、长度上限，或产品侧截断。

这能解释三个产品现象：

- **同一问题多次问，答案会漂**：概率采样本身就有随机性，加上温度参数。
- **前面写错，后面会顺着错**：它在续写，不是全局校对。
- **格式要求有用**：你规定「只输出 JSON」，等于把走网的路径收窄到「像 JSON 的文本」。

### 为什么会幻觉

模型没有「对/错」开关，只有「像不像人会这样回答」。没有检索、没有工具、没有校验时，它仍会流畅作答，而且常常很自信。

产品上必须把两件事拆开评测：

| 评测项 | 在测什么 | 售后助手上的失败 |
| --- | --- | --- |
| 像不像人话 | 通顺、礼貌、结构完整 | 用户觉得「客服挺会说话」 |
| 有没有依据 | 能否对应制度、订单数据或明确拒答 | 编造 30 天无理由、编物流、假装已经办成换货 |

幻觉不是边角 bug，是生成方式带来的默认行为。企业知识、实时状态、权限数据，都不能指望「模型自己记得」。

## 深度学习、强化学习，产品要分清什么

课件用两个生活例子，足够建立直觉。

**深度学习：这是什么。**  
给孩子看很多张球的照片，每张告诉他「这是球 / 不是球」。孩子一层层看边缘、颜色、形状，最后学会「什么样的特征组合叫球」。对应产品里的识别、分类、翻译：先有大量样本和标签，模型学习模式。

**强化学习：下一步怎么做。**  
不手把手教怎么拿球、瞄准、走动，而是把孩子放到有框有球的房间，进框给奖励，扔飞了不给或给负反馈。对应产品里的 Agent：在环境里选动作，看状态和奖励，学「什么情况下做什么能拿到长期更好的结果」。

| | 深度学习 | 强化学习 |
| --- | --- | --- |
| 核心问题 | 是什么 | 怎么做 |
| 学习方式 | 主要从带标签数据学 | 和环境交互，试错加奖励 |
| 数据 | 大量静态标注 | 交互中不断产生 |
| 反馈 | 对/错、类别，通常及时 | 常延迟、稀疏 |
| 擅长 | 感知：图像、语音、翻译 | 决策：游戏、控制、规划 |
| 类比 | 看图识字 | 学骑车、打游戏通关 |
| 在 LLM 产品里 | 预训练把语言模式学厚 | 对齐、Agent 选工具，会用到类似思路 |

两者不是互斥。大模型先靠深度学习（加自监督）成为「很会说话的底盘」，再在应用层用提示词、RAG、工具，必要时用强化学习类方法做对齐。产品讨论「要不要上 Agent」，其实是在问：路径是否固定、环境是否可观测、错误是否可回滚、奖励（业务指标）能否定义清楚。

## 预训练为什么改变了做产品的方式

传统 AI 很像作坊：每个任务自己攒数据、自己训练、换场景几乎重来。大模型的预训练相当于把「基础教育」做完了：从大量标注和未标注数据里把通用能力存进参数，具体岗位再用提示词、知识库、工具或微调去适配。

一个好用的比喻：

- 以前企业要用大学生，得从小学自己培养。
- 现在「基础教育」由模型厂商做完，企业是在招聘已经读完书的人，再做入职培训。

自监督的意义：互联网上未标注文本很多，人工标注又贵又慢。模型可以自己从文本里构造学习信号（例如根据上下文预测被遮住的词），降低「每个任务都先标十万条」的门槛。产品不需要会 Bert 的论文细节，但要知道：通用能力变便宜了，贵的是你们自己的数据、流程、权限和评测。

对产品决策的直接含义：

1. **默认从通用模型开始**，不要一上来自训。
2. **岗位适配按成本从低到高**：提示词 → RAG → 工具/工作流 → 微调 → 自训。
3. **下一阶段的产品能力**，不只是「聊得更像人」，而是接眼睛（多模态）、接手（工具和插件）、接业务系统（订单、权限、工单）。
4. **所有熟悉的产品形态都可能被重做一遍**，但重做的关键是链路可控，不是换一个聊天框。

## 贯穿案例：只把原话丢给模型会发生什么

用户说：「我上周买的蓝牙耳机左耳没声了，能换吗？订单号 202608210088。」

如果产品只做「接入大模型」，常见三种坏结果：

1. **编制度**：网上很多「7 天无理由」，模型可能答成无理由退货，和你们「质量问题才换」不一致。
2. **编状态**：它没查过订单，却说「您的包裹还在路上」或「已经给您办好了」。
3. **评测混用**：客服听起来很会说话，业务却按「能否按制度办成」打分，两边永远对不上。

正确拆法：

| 用户这句话里的信息 | 该交给谁 | 不该交给谁 |
| --- | --- | --- |
| 「左耳没声」是质量描述 | 模型：理解意图、组织话术 | 模型：自行认定已质检通过 |
| 「能不能换」是制度判断 | 知识库里的生效制度 | 模型预训练里的电商常识 |
| 「订单号 / 上周买的」是状态 | 订单接口 | 知识库或模型记忆 |
| 「帮我办了」是写操作 | 带鉴权的工具 + 二次确认 | 模型口头承诺 |

## 适用 / 不适用

**适用（让模型直接生成）**

- 把制度和订单结果改写成用户能看懂的话。
- 抽取字段：订单号、商品名、诉求类型。
- 总结对话，给人工客服做工单摘要。

**不适用（不要只靠模型）**

- 内部制度、活动规则、禁止承诺清单。
- 订单、物流、库存、余额。
- 已经办成换货、已赔付、已改地址——必须系统写成功才允许说。

## PRD 要写清什么

| 字段 | 售后助手示例 |
| --- | --- |
| 用户任务 | 判断能否换货，并给出下一步，不代替仓储质检结论 |
| 模型允许做什么 | 理解、改写、提问补全信息、生成话术 |
| 模型禁止做什么 | 编制度、编订单、口头办结、承诺赔偿金额 |
| 输入 | 用户原话、登录身份；制度与订单不由模型「想起」 |
| 输出 | 对用户的短回复 + 内部结构：`intent` / `need_order` / `need_policy` / `escalate` |
| 失败策略 | 缺订单号就追问；查不到就说查不到并转人工；禁止用通顺话术掩盖失败 |
| 评测怎么拆 | 通顺度和事实正确分开打分，不能用「像不像客服」一项糊弄 |

## 验收例子

固定用同一句用户原话。**没有知识库、没有订单接口**时：

| | 对 | 错 |
| --- | --- | --- |
| 话术 | 「我需要先核对您的订单和当前换货规则，请稍等；若查不到会转人工。」 | 「电子产品都是 30 天无理由，我已经给您换好了。」 |
| 结构 | 输出 `need_order=true`，`need_policy=true`，不给出「可以换」的最终结论 | 直接 `can_replace=true` |
| 评测 | 「像客服」可以过；「制度正确」必须判失败 | 把通顺当成上线标准 |

有制度、有订单之后的验收，写在后面 RAG 和工具两页。这里先锁死：**裸模型不得给出换货结论。**

## 和研发、算法、业务怎么对齐

| 角色 | 定什么 | 不定什么 |
| --- | --- | --- |
| 产品 | 任务边界、禁止承诺、评测拆分、失败时用户看到什么 | 选哪家模型、温度调多少 |
| 业务 / 客服 | 金标口径、哪些必须转人工 | 向量库怎么切 |
| 算法 | 在边界内把意图和格式做稳 | 私自放宽「可以先答再补证据」 |
| 研发 | 日志、截断、超时、身份传入 | 用提示词代替鉴权 |

开会时先问一句：这句话里的事实从哪来？答不出「制度文档 / 订单接口 / 明确不知道」，就还停留在 Demo。

## 面试常问

**「内部制度为什么不能只丢给模型？」**  
因为制度不在预训练里，模型会用网上的通用电商话术填空。要检索你们的生效文档。

**「Demo 很能说，上线为什么一本正经说错？」**  
评测只看像不像人话。上线要用有没有依据、有没有乱承诺来打分。

**「像搜索」和「像生成」的验收为什么不能混？」**  
搜索验收看出处对不对；生成验收看格式、语气、任务是否完成。售后助手两样都要，但必须分项，不能平均成一个「智能分」。

**「什么该查库，什么该检索文档，什么才让模型直接写？」**  
状态查库，规则检索文档，话术和摘要让模型写。用户那句「能不能换」是规则加状态，不是纯生成。
