# 应用平台与部署选择

做大模型功能时，团队很容易把「用了某个 App / 某个平台」说成架构。产品经理要把层分清，否则需求、采购和研发会各说各的。

## 这一页在链路上负责什么

售后助手的提示词、知识库、查单、是否 Agent，都可以先在云端 API 上验证。这一页决定：**模型跑在哪、编排用什么、数据能不能出你们的边界。** 平台品牌会过时，分层和决策清单不会。

## 先分四层

| 层 | 负责什么 | 典型例子（会变，重在分层） |
| --- | --- | --- |
| 模型 | 推理、生成 | 云端大模型 API、开源本地模型 |
| 编排 | 工作流、知识库、工具、发布、权限 | Coze、Dify 这类平台 |
| 使用端 | 多模型对话、本地文件、MCP 连接 | Cherry Studio 这类客户端 |
| 垂直工具 | 某一模态的专业编排 | ComfyUI 做图像生成节点 |

关系可以记：

- **模型是发动机**：换发动机，车还是车。
- **编排平台是产线**：决定工序、质检、能不能量产。
- **客户端是驾驶舱**：个人或团队日常怎么开。
- **垂直工具是专用车间**：例如图像，不必硬塞进通用对话里。

Dify 相对在线 Bot 平台，常见差异是：可本地部署、更偏可运营的应用、模型可替换。ComfyUI 把图像生成拆成可视化节点。Cherry Studio 把多模型、RAG、Agent、MCP 放在一个客户端。具体产品会迭代，选型看「它落在哪一层」，不看广告词。

## 贯穿案例：售后助手落在哪一层

| 问题 | 售后助手的答案 |
| --- | --- |
| 用户在哪用 | 电商 App 里的会话，不是员工自己的 Cherry Studio |
| 编排在哪 | 要账号、权限、发布、日志；验证期可用 Dify/同类，对客前必须能接入你们的登录与订单网关 |
| 模型在哪 | 默认云 API；订单与用户原话是否允许出域，由合规定，不是由「哪个模型更聪明」定 |
| 知识库在哪 | 制度可以在编排层；**订单数据不要只存在向量库** |
| 个人 Chat 客户端 | 适合产品经理自己做 Prompt 实验，不能当生产客服 |

业务说「我们要上 Coze/Dify」时，追问三句：要的是聊天窗口、工作流编排，还是模型本身？售后助手三样都要，但采购口不能只签一个品牌名。

## 怎么选，不把工具当项目

- 验证阶段允许多试，日常固定 1～2 个主工具，降低切换成本。
- 个人效率和企业交付不是同一套标准：本地客户端适合研究；对客功能要看权限、审计、SLA、账号体系。
- 能用云 API 跑通闭环，就先不要自建全套 GPU。工具是为了验证价值和流程，不是为了堆栈完整。

## 云上调用还是本地部署

对多数产品验证和中小流量：**客户端/编排平台 + 云端 API 更省事、更经济。** 本地部署的意义主要是：

| 本地更值得考虑 | 云更值得考虑 |
| --- | --- |
| 数据不能出境 | 要快速验证、少运维 |
| 要做训练/微调，需要控环境 | 流量不大，按 Token 付费更划算 |
| 要建立对显存、速度、并发的体感 | 需要厂商升级模型和保 SLA |
| 内网或断网场景 | 团队没有 GPU 运维能力 |

「私有化」是合规和架构决策，不是先进性象征。没有合规硬约束、又没有训练需求时，为私有化养机房，常常是成本误判。

选择时并列看：延迟、费用、合规、能否断网、谁值班、模型升级谁回归、日志落在哪。

## 决策清单

把售后助手（或任何对客 AI）上评审时，逐项填，不要只写「用某某云」：

1. **数据分级**：用户原话、订单、制度，哪一类允许发给第三方模型？  
2. **身份**：生产请求是否带登录态？编排平台能否对接 SSO？  
3. **延迟**：用户可接受几秒？查单 + 生成是否超标？超时谁转人工？  
4. **可用性**：厂商 SLA 和你们客服高峰是否匹配？降级是换模型还是关 AI 入口？  
5. **日志与留存**：对话日志存在哪、留多久、谁能搜到订单号？  
6. **供应商锁定**：提示词和工作流能否导出？换模型要改多少？  
7. **费用**：按 Token、按座、按并发，哪一种会在量上来时爆炸？  
8. **值班**：模型抽风、密钥泄漏、知识库误发，谁的 on-call？  
9. **本地的真正原因**：合规 / 训练 / 断网 / 学习体感，圈一个，不要四个都写。

圈「学习体感」就不要申请生产级 GPU 预算。圈「合规」就要法务一起签字，而不是产品自己宣布私有化。

## 练手账（数字只用来算，不是报价）

沿用微调那页的流量假设：日 5000 次，月 Token 费大约 **¥4800** 量级（单价是假的，公式要留下）。

再假想一台可用于推理的 GPU 云主机 **¥1.5 万 / 月**（含磁盘和带宽的粗数），还要加：

- 工程值班和告警  
- 模型升级回归  
- 高峰扩容（客服大促可能是平时 5～10 倍）

怎么写结论：

- 验证期和中小流量：云 API 通常更便宜，而且把 SLA 部分外包给厂商。  
- 当月 Token 费稳定接近或超过「自建推理 + 人力」且合规允许对比时，再做 POC。  
- 大促如果并发是瓶颈，问的是限流和降级，不是先买一张卡。  
- 私有化若只为「听起来更安全」，但日志仍明文堆在个人电脑或未鉴权的编排平台，账和安全都没做对。

延迟也要入账：本地小模型可能更便宜，但话术变差、转人工上升，**人工分钟成本**会吃掉 GPU 节省。产品要把「模型单价」和「一次错误办理的客服成本」放在同一张表。

## 和前面几页怎么串

用户能用上的产品，通常是这几层的组合，而不是其中一层：

提示词（怎么说）→ RAG（用哪份内部资料）→ 工作流/工具（怎么办事）→ Agent（怎么选路线）→ 微调（是否改模型本身）→ 部署（模型跑在哪）。

平台只是把这些层收纳进界面。产品文档里应写能力组合，而不是只写品牌名。

售后助手推荐的验证路径：云 API + 可替换的编排 + 自有订单网关。生产路径以合规清单为准，而不是以课件里的软件名单为准。

## 适用 / 不适用

**适用云 API**

- 要验证换货链路是否有人用。  
- 制度文档敏感度低于订单，或可做脱敏后再送模型。  
- 团队没有推理运维。

**适用私有化 / 本地**

- 法务明确：对话或订单不得出境、不得进指定厂商。  
- 内网客服、断网门店。  
- 需要真的训练，而不是「以后可能微调」。

**不适用**

- 用员工个人 Chat 客户端接生产用户。  
- 为了用 ComfyUI 而把客服做成画图工作流。  
- 采购只对品牌，不对分层。

## PRD 要写清什么

| 字段 | 售后助手示例 |
| --- | --- |
| 环境 | 实验 / 预发 / 生产；生产禁止个人 API Key |
| 数据流 | 哪些字段进模型，哪些只在自有后端 |
| SLA | 生成超时 8 秒转人工；可用性目标与客服排班对齐 |
| 降级 | 主模型失败切备用，或关闭 AI 只留表单 |
| 密钥与权限 | 平台服务账号，能轮换；操作人可审计 |
| 退出 | 编排导出、提示词版本、评测集不锁死在一家 |
| 成本告警 | 日 Token 超阈值通知产品 + 研发 |

## 验收例子

| 用例 | 通过 | 不通过 |
| --- | --- | --- |
| 分层表达 | 方案写「编排 + 云模型 + 自有查单」，可替换发动机 | 只写「我们上了某某平台」 |
| 实验 vs 生产 | 个人客户端只用于内部试提示词 | 把生产流量打到员工 Cherry Studio |
| 合规 | 订单号进自有网关；送模型字段有清单 | 整段用户画像 + 地址明文进第三方 |
| 失败 | 超时转人工，日志可查 | 超时后模型自己编物流 |
| 锁定 | 换一个同类模型，工作流仍能跑 | 提示词写死某一家专有函数且无抽象 |

## 和研发、算法、业务怎么对齐

| 角色 | 负责 |
| --- | --- |
| 产品 | 分层表述、实验/生产边界、降级体验、成本告警阈值 |
| 研发 | 网关、密钥、环境、导出与抽象 |
| 算法 | 模型候选与质量；不负责偷偷把生产 Key 写进笔记本 |
| 合规 / 法务 | 出域、留存、告知用户是否在与 AI 对话 |
| 财务 | 按量账单谁审；大促预算 |
| 业务 | 能否接受「AI 关闭后的表单路径」 |

## 面试常问

**「业务说要上 Coze/Dify，你怎么追问？」**  
问要窗口、编排还是模型。售后助手要接登录和订单，只上平台不等于上了产品。

**「什么情况下本地部署是必须，什么情况下是体感练习？」**  
必须：合规、断网、真训练。体感：了解显存和速度。体感用云厂商的体验实例或一台短期机器即可，不要用生产客服当练手。

**「为什么工具名单会过时，分层不会过时？」**  
品牌季度一变。发动机 / 产线 / 驾驶舱 / 专用车间这四层，换名字也能用来审方案。

**「私有化是不是一定更安全？」**  
不一定。没有鉴权、没有日志、模型乱写操作，本地一样出事。安全看权限和审计，不看机器在谁机房的口号。
