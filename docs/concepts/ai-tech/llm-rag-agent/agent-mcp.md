# Agent、MCP 与多智能体

Agent 是围绕目标规划步骤、调用工具、观察结果并继续推进的系统。MCP 则可以理解成 AI 连接工具和资料的标准接口层。

## Agent 基本循环

1. 接收目标。
2. 拆解步骤。
3. 调用工具或读取资料。
4. 观察结果。
5. 决定继续、修正、退出或交给人。

## 适合场景

- 多源资料调研。
- 日志和故障排查。
- 自动整理报告。
- 跨系统收集信息。
- 有明确目标但路径不固定的任务。

## 产品边界

Agent 越自由，越需要限制工具、步骤、预算、权限和退出条件。不要一开始做全自动，先做半自动助手，让关键动作由人确认。

## 工程实践要点

大模型应用的关键不是“接入模型”，而是把模型放进可控链路：用户输入、上下文、知识库、工具、权限、输出格式、人工确认和日志追踪。每个环节都可能决定功能能不能上线。

| 能力 | 适合解决 | 必须补上的约束 |
| --- | --- | --- |
| LLM | 理解、生成、总结、抽取。 | 输出格式、拒答、安全边界。 |
| RAG | 接企业知识和最新资料。 | 来源、权限、切分、召回和引用。 |
| Tool Calling | 查询或修改业务系统。 | 服务端鉴权、参数校验、二次确认。 |
| Agent | 路径不固定的多步任务。 | 步数预算、工具范围、日志和退出条件。 |

## 示例代码

下面是一个最小 LLM 调用伪代码，展示输入、上下文、模型调用和输出校验的结构：

```python
def answer(question, context):
    prompt = f"""基于资料回答问题。
资料：{context}
问题：{question}
"""
    result = call_model(prompt)
    if not result.strip():
        return {"status": "empty", "answer": None}
    return {"status": "ok", "answer": result}
```

真实系统需要把检索、权限、引用、结构化输出、日志和错误处理补齐。

## 技术细节拆解

Agent、MCP 与多智能体 可以拆成输入、处理、输出和指标四层。这样读的时候不会停留在概念名，而是能看到它在系统里接收什么、改变什么、产出什么。

| 层次 | 具体内容 |
| --- | --- |
| 输入 | 用户问题、系统提示词、历史对话、检索片段、工具 schema。 |
| 处理 | 上下文组装、模型调用、工具调用、输出解析、权限校验。 |
| 输出 | 自然语言、JSON、引用、工具结果、拒答信息。 |
| 指标 | 准确率、引用命中率、格式成功率、工具成功率、成本、延迟。 |

## 关键参数和边界

| 参数/边界 | 说明 |
| --- | --- |
| temperature | 越高越发散，越低越稳定。 |
| max_tokens | 限制输出长度，也影响成本和截断风险。 |
| top_p | 控制采样范围，通常和 temperature 配合。 |
| schema | 结构化输出必须有 schema 和校验。 |

## 可运行检查

```python
import json

raw = '{"answer":"可以办理", "confidence":0.82}'
data = json.loads(raw)
assert "answer" in data
assert 0 <= data["confidence"] <= 1
print(data)
```

## 怎么判断学懂了

| 判断点 | 具体标准 |
| --- | --- |
| 格式稳定性 | 结构化输出能否被程序稳定解析。 |
| 证据一致性 | 回答是否能追溯到检索片段或工具结果。 |
| 权限安全 | 不同用户只能检索和调用授权范围内的资源。 |

## 常见误区和排查

| 问题 | 为什么会发生 | 怎么排查 |
| --- | --- | --- |
| 回答没有证据 | 模型自由发挥，没绑定检索片段。 | 强制引用来源并校验引用存在。 |
| 工具参数不合法 | 模型输出 JSON 不符合接口要求。 | 用 schema 校验，失败时让模型重试或拒绝执行。 |
| 权限穿透 | 检索阶段没有按用户权限过滤。 | 把用户身份加入检索条件并记录审计日志。 |

## 这一页在链路上负责什么

售后助手 v1 建议是「固定工作流」。这一页回答：什么时候才需要 Agent、MCP 是什么、以及**不要把客服第一版做成全自动员工**。前面正文已有 Agent 循环和适用场景；下面用同一条换货咨询，把边界、权限和面试题写清楚。

## 最简单的智能体：先从提示词角色做起

智能体可以定义为：能感知环境、为了既定目标做决策并行动的实体。在 AI 里，特指能感知输入、做决策、完成任务的程序。完整形态通常包括：

| 能力块 | 作用 | 没有它时 |
| --- | --- | --- |
| LLM | 理解语言、生成计划与回复 | 不会对话 |
| 规划 | 把目标拆成步骤 | 只会单轮问答 |
| 记忆 | 保存任务状态和关键事实 | 每轮从零开始 |
| 外部工具 | 查系统、改数据、发通知 | 只能空谈 |
| 知识库 | 用企业资料说话 | 用通用记忆硬编 |

但入门不必四块齐活。课件里的「最简单智能体」，就是 **写好的系统提示词 + 固定专家角色**：例如「产品 AI 化专家」，能看业务特征、判断哪里能嵌 AI、给出提效思路。它还没有工具，严格说只是固化人设的 LLM 应用，但产品上已经能验证：

- 这个角色有没有人愿意反复用
- 输出结构能不能进评审
- 哪些能力下一步必须接工具或知识库

做法仍然是：定角色 → 写提示词 → 用真实业务调试 → 对比多版本 → 再考虑发布。系列产品应把这个角色当「会不断添砖加瓦的主体」：先能说，再能查资料，再能调接口，再能走工作流。

售后助手也一样：先验证「按口径说话」有没有人用，再接知识库和查单。不要第一天就挂 20 个 MCP。

## 智能体为什么被看成这一代的应用形态

一个粗糙但好记的对照：

- Web 时代，用户进网站
- 移动互联网，用户进 App / 小程序
- LLM 时代，用户越来越多进 Agent

所以要搞清三件事：逻辑（它怎么想）、运作方式（它调什么）、能力边界（它绝对不能做什么）。边界不清楚的 Agent，演示好看，事故也快。

形态可以很多：对话窗口、后台定时任务、嵌入按钮的「帮我填好这张单」、多 Agent 协作。产品先选一种主形态，不要同时承诺「全自动员工」。

## 贯穿案例：客服 v1 不要做成开放 Agent

同一句「耳机坏了能不能换」。

**v1（推荐）**：意图进「换货咨询工作流」。Agent 即使存在，也只做分流：换货 / 物流 / 投诉升级。分流错了，用户损失是进错工序，可以转人工挽回。

**过早的开放 Agent**：自行规划「先上网搜竞品保修 → 再读本地文件 → 再给财务打钱」。每多一个工具，就多一种越权。客服场景里，错误办理的成本高于「少办一件事」。

可以升级 Agent 的信号：

- 用户一句话里混了物流、换货、发票，固定树会炸。
- 工具集合仍然封闭（还是那 3～5 个），只是选择顺序不固定。
- 已经有步数上限、费用上限、退出条件和完整日志。

还不够的信号：

- 业务要求「像真人客服一样什么都能办」。
- 工具里出现打款、改价、读全部客户数据。
- 没有人看日志，也没有人工接管按钮。

## 工作流嵌进 Agent：谁调度谁

工作流更确定，Agent 更灵活。工程上常见结构是：

- Agent 负责理解用户、选路线、解释结果。
- 工作流负责把某一工序稳定做完（生成名片图、出标准报告、跑固定质检、跑换货咨询）。

例子：用户输入一种商业模式，Agent 判断「这是在要视觉化」，于是调用「多风格商业卡片生成」工作流，再把结果给人挑。另一个技能「商业模式 AI 化建议」是另一条工作流。Agent 的提示词里要写清：什么意图调 A，什么意图调 B，都不能调时问人。

个人助理也可以挂多条小工作流：「中午吃什么」「周报」「会议室」。真正难的不是挂接，而是意图识别错误时的兜底：调错工作流的成本、能否撤销、要不要先确认。

售后助手：调错「开票工作流」去处理换货，应能撤销或立即转人工，而不是把错误开票提交掉。

## MCP：统一的「手」和「资料口」

Function Call 已经能让模型和外部系统说话。MCP（Model Context Protocol，模型上下文协议）要解决的是标准化：每个模型和每个工具都两两对接，工作量按乘法爆炸；有了统一协议，应用侧按一种方式发现和调用工具/数据源。

继续用入职类比：

| 层次 | 类比 | 对应能力 |
| --- | --- | --- |
| 通用毕业生 | 通识很多，没有你们公司经验 | 预训练模型 |
| 岗位说明书 | 这岗怎么说话、办事 | 提示词 |
| 入职资料包 | 制度、案例、产品说明 | RAG |
| 系统账号 | 能查库、能退单、能写文件 | Function Call / MCP |

Function Call 和 MCP 解决的都是「给手」。MCP 的产品差异主要是：接口形态统一、生态里会出现大量可插拔服务（检索、浏览器、文件、内部系统封装）。接入变快，不代表风险变低——能读本地文件、能操作生产数据的 MCP，默认按高权限功能设计。

产品经理接入 MCP 前要问：

1. 它只读还是可写？
2. 作用域是当前用户、当前租户，还是整个环境？
3. 授权如何展示、如何撤销？
4. 每次调用是否有日志，能否审计到人？
5. 失败、超时、部分成功时用户看到什么？
6. 和已有 Function Call、内部 API 网关是什么关系，会不会两套权限？

课堂里的「GitHub / ModelScope 上有多少现成 MCP」会过时，站点只保留判断：生态在变大，选型看权限与审计，不看目录数字。

售后助手若接「订单 MCP / 知识库 MCP」，权限模型必须与现有账号体系同一套。不要因为「MCP 很新」就绕过网关。

## 能力叠加的产品顺序

建议默认顺序，和课件系列一致：

1. 提示词角色能稳定输出  
2. 工作流把可重复工序固定住  
3. RAG 让内部知识可引用  
4. Function Call / MCP 让它能办事  
5. Agent 把上述能力按意图选出来  
6. 仍不够再谈微调

每加一层，评测和安全都要加一层。不要用「已经是 Agent 了」跳过工作流和权限设计。

## 适用 / 不适用

**适用 Agent**

- 目标清楚、路径不固定：排查、调研、跨系统收集。
- 工具集封闭，写操作有确认，有步数和费用预算。

**不适用（先别上，或只做分流）**

- 售后 v1、报销 v1、对客承诺敏感的办理类。
- 无法定义奖励 / 成功标准（「让用户高兴」不能当奖励）。
- 团队看不懂日志，出了错找不到是哪一步。

**MCP**

- 适用：内部要接很多同类工具，想减少一对一适配。
- 不适用：把它当成安全方案。标准化加快接入，权限面通常变大。

## PRD 要写清什么

| 字段 | 售后助手示例 |
| --- | --- |
| 主形态 | 对话助手；不做后台全自动改订单 |
| 可调用工作流 / 工具 | 换货咨询、物流查询、转人工；名单写死 |
| 步数预算 | 单轮最多 4 次工具调用 |
| 费用预算 | 单会话 Token 上限；超限转人工 |
| 退出条件 | 用户要找人、情绪升级、工具连续失败 2 次、涉及欺诈 |
| 人机交接 | 转人工时带摘要：意图、已查订单号、已引用制度版本 |
| MCP | 若使用：只读订单 + 知识库；禁止文件系统和浏览器 MCP 进生产客服 |

## 验收例子

| 用例 | 通过 | 不通过 |
| --- | --- | --- |
| 标准换货问法 | 进入换货工作流，行为与上一页验收一致 | 自行规划成「先搜索全网保修政策」 |
| 用户同时问换货和开票 | 拆成两步或先确认先办哪件；开票未确认不提交 | 一次提交两张互不相干的单 |
| 连续工具失败 | 转人工，摘要完整 | 换一个 MCP 再试写操作 |
| 授权 | 用户能看到「将读取您的订单」并撤销 | 静默读取 |
| 只提示词的专家 Bot | 对外称为「咨询助手」，不称「已自动办理」 | 宣传成 Agent 员工 |

## 和研发、算法、业务怎么对齐

| 角色 | 负责 |
| --- | --- |
| 产品 | 形态、工具白名单、预算、退出、对外怎么称呼能力 |
| 研发 | 网关、审计、MCP 与现有鉴权合一、会话级限额 |
| 算法 | 路由准确率、循环检测（反复调同一工具） |
| 业务 / 客服 | 哪些必须人处理；交接摘要够不够用 |
| 安全 / 合规 | 高权限 MCP 能否进生产 |

产品对外文案：能查、能建议、确认后能提交。不要写「自主客服」。

## 面试常问

**「只有提示词的专家机器人，算不算 Agent？」**  
学术上通常不算完整 Agent（缺环境和行动）。产品上可以当最小验证形态，但必须把边界说清：只会建议，不会办理。

**「为什么很多业务该是 Agent 调工作流，而不是超长提示词包打天下？」**  
工作流可测、可回滚；超长提示词既贵又无法保证真的调了接口。客服换货应是路由到一条已验收的流水线。

**「MCP 降低的是接入成本还是安全成本？」**  
接入成本。安全成本通常上升，因为可插拔能力变多。面试里能列出六问（读写、范围、授权、日志、失败态、和旧网关关系）即可。

**「什么叫半自动助手？」**  
模型准备好售后单内容，人点确认。关键写操作不自动发生。这是对客 Agent 的默认形态。
