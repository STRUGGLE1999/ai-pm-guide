# 工具调用与工作流

工具调用让模型不只会说，还能请求外部系统执行动作，例如查订单、创建工单、读取数据库、发送通知。工作流则把稳定步骤编排成可控流程。

## Tool Calling 做什么

| 能力 | 例子 |
| --- | --- |
| 查询 | 查订单、查库存、查客户资料。 |
| 创建 | 创建工单、生成任务、写入记录。 |
| 更新 | 修改状态、补充字段。 |
| 通知 | 发邮件、发消息、推送提醒。 |

## Workflow 和 Agent 的区别

Workflow 路径固定，适合报销、审批、抽取、质检。Agent 路径不固定，适合调研、排查、跨系统探索。

## 安全要求

模型提出工具调用，后端必须再次校验权限、参数和风险。高风险操作要二次确认，所有工具调用要留日志。

## 工程实践要点

大模型应用的关键不是“接入模型”，而是把模型放进可控链路：用户输入、上下文、知识库、工具、权限、输出格式、人工确认和日志追踪。每个环节都可能决定功能能不能上线。

| 能力 | 适合解决 | 必须补上的约束 |
| --- | --- | --- |
| LLM | 理解、生成、总结、抽取。 | 输出格式、拒答、安全边界。 |
| RAG | 接企业知识和最新资料。 | 来源、权限、切分、召回和引用。 |
| Tool Calling | 查询或修改业务系统。 | 服务端鉴权、参数校验、二次确认。 |
| Agent | 路径不固定的多步任务。 | 步数预算、工具范围、日志和退出条件。 |

## 示例代码

下面是一个最小 LLM 调用伪代码，展示输入、上下文、模型调用和输出校验的结构：

```python
def answer(question, context):
    prompt = f"""基于资料回答问题。
资料：{context}
问题：{question}
"""
    result = call_model(prompt)
    if not result.strip():
        return {"status": "empty", "answer": None}
    return {"status": "ok", "answer": result}
```

真实系统需要把检索、权限、引用、结构化输出、日志和错误处理补齐。

## 技术细节拆解

工具调用与工作流 可以拆成输入、处理、输出和指标四层。这样读的时候不会停留在概念名，而是能看到它在系统里接收什么、改变什么、产出什么。

| 层次 | 具体内容 |
| --- | --- |
| 输入 | 用户问题、系统提示词、历史对话、检索片段、工具 schema。 |
| 处理 | 上下文组装、模型调用、工具调用、输出解析、权限校验。 |
| 输出 | 自然语言、JSON、引用、工具结果、拒答信息。 |
| 指标 | 准确率、引用命中率、格式成功率、工具成功率、成本、延迟。 |

## 关键参数和边界

| 参数/边界 | 说明 |
| --- | --- |
| temperature | 越高越发散，越低越稳定。 |
| max_tokens | 限制输出长度，也影响成本和截断风险。 |
| top_p | 控制采样范围，通常和 temperature 配合。 |
| schema | 结构化输出必须有 schema 和校验。 |

## 可运行检查

```python
import json

raw = '{"answer":"可以办理", "confidence":0.82}'
data = json.loads(raw)
assert "answer" in data
assert 0 <= data["confidence"] <= 1
print(data)
```

## 怎么判断学懂了

| 判断点 | 具体标准 |
| --- | --- |
| 格式稳定性 | 结构化输出能否被程序稳定解析。 |
| 证据一致性 | 回答是否能追溯到检索片段或工具结果。 |
| 权限安全 | 不同用户只能检索和调用授权范围内的资源。 |

## 常见误区和排查

| 问题 | 为什么会发生 | 怎么排查 |
| --- | --- | --- |
| 回答没有证据 | 模型自由发挥，没绑定检索片段。 | 强制引用来源并校验引用存在。 |
| 工具参数不合法 | 模型输出 JSON 不符合接口要求。 | 用 schema 校验，失败时让模型重试或拒绝执行。 |
| 权限穿透 | 检索阶段没有按用户权限过滤。 | 把用户身份加入检索条件并记录审计日志。 |

## 这一页在链路上负责什么

售后助手已经能「按制度说话」之后，还要回答「这单签收几天了、能不能提交申请」。这一页负责两件事：

- **工作流**：把稳定工序画死，每次尽量一样，好测、好复盘。
- **工具调用（Function Call）**：要不要查单、要不要创建售后单，由模型根据当前对话提出，**真正执行在后端**。

前面正文已有查询/创建/更新/通知的分类和安全原则。下面用同一条换货咨询，写成可上线的路径和验收。

## 为什么单靠提示词不够

把「翻译 → 定角色 → 写故事 → 出分镜 → 生图 → 合成视频」塞进一段提示词，模型偶尔能说出步骤，但很难稳定调用翻译接口、绘画模型和合成服务，也很难在某一步失败时重试。多技能、多系统、要可重复交付的任务，需要工作流：把模型、API、脚本按顺序（或带分支、循环）接成流水线。

工作流的标准说法是：一套流程化系统，包含多个步骤，可调用不同模型或 API，用来回答问题或完成某件产物。产品上更直白：**它是生产线，不是聊天。**

售后助手同理：把「查单 + 检索制度 + 生成话术 + 可选创建售后单」塞进一句「你是万能客服」，Demo 能演，生产会在某一步静默失败后继续编。

## 工作流和智能体怎么分工

| | 工作流 Workflow | 智能体 Agent |
| --- | --- | --- |
| 像什么 | 生产线 | 助理 / 一个人 |
| 路径 | 预定好，尽量每次一样 | 按目标选择流水线，或临时拆步 |
| 确定性 | 高，好测、好复盘 | 低，灵活，难预期 |
| 强项 | 集成多种能力，节点清晰 | 理解说法各异的用户请求 |
| 关系 | 被 Agent 当工具调用 | 需要时调用某一条工作流 |

类比：微信是 Agent；扫二维码识别、搜公众号，是两条工作流。Agent 面向对象；工作流完成其中一道工序。

平台和模型要分开：Coze、Dify 是造车产线（编排、发布、工具）；豆包、DeepSeek 是发动机。同一条产线可以换发动机，同一台发动机也可以放到别的产线。不要把「我们用了某某模型」当成「我们已经有工作流平台」。

## 贯穿案例：换货咨询的两条路

用户原话仍是那句带订单号的换货询问。

**更稳的默认：固定工作流（推荐先上这个）**

1. 开始：入参 = 用户 ID、原话、会话 ID。  
2. 抽取：模型或规则抽出订单号、商品诉求（质量问题 / 不喜欢 / 物流）。  
3. 查订单：后端按**当前登录用户**调订单接口，不信任模型「说这是用户的单」。  
4. 检索制度：用商品类目 + 诉求类型过滤知识库。  
5. 规则节点：签收未超 7 天且诉求是质量问题 → 允许引导换货；否则走维修/拒换说明。  
6. 生成话术：只基于接口 JSON + 制度片段。  
7. 若用户确认办理：创建售后单工具，成功后再说「已提交」。  
8. 结束：出参 = 对用户回复、是否转人工、工单号。

这一条路径每次相同，评测可以按节点做。

**Function Call 适合哪一段**

「用户有没有报订单号、要不要查单、要不要建单」可以让模型选工具。但**查谁的单、能不能建单**必须后端鉴权。模型输出 `create_rma(order_id=...)` 只是提议。

| 步骤 | 谁决定 | 谁执行 |
| --- | --- | --- |
| 要不要查订单 | 模型或固定工作流都可 | 后端订单服务 |
| 查哪张单 | 用户身份 + 订单号校验 | 后端，失败则当未命中 |
| 能不能换 | 规则节点或「制度片段 + 订单字段」 | 不要让模型单独拍板 |
| 是否真的提交售后 | 用户确认 + 权限 | 后端；失败禁止说已办成 |

## 工作流的基本结构

任何一条工作流都有：

1. **开始**：入参是什么（一段文案、一个商品 ID、一份文件）。
2. **中间处理**：模型节点、插件、代码、循环、分支。
3. **结束**：出参是什么（视频 URL、结构化 JSON、一张图）。

循环用来处理列表：例如分镜数组里每一镜生一张图。分支用来处理规则：例如「是退货走 A，是投诉走 B」。

产品要先写清入参和出参，再画节点。先堆节点再想交付物，后面一定会返工。

## 怎么拆一条业务工作流

课件里用「小红书内容 / 分镜视频」说明方法，可迁移到任何生成类、审批类、抽取类功能。售后助手用同一套方法：

**1. 以终为始**  
最终交付物：用户听得懂的结论 + 可选售后单号；不是「中间调了几次 GPT」。

**2. 拆交付物元素**  
订单字段、制度条款、话术、是否转人工、是否建单。每个元素对应接口、知识库或一个模型节点。

**3. 按角色分工，而不是按模型次数分工**  
抽取节点、话术节点提示词不同。规则判断能写死代码就不要交给模型，省得 7 天被写成 15 天。

**4. 单元测试再串联**  
假订单 JSON + 假制度片段，先测话术节点；再测真接口。串联后再改提示词，很难定位是哪一步坏了。

**5. 视觉和品牌不要在编排里从零长出来**  
（生成类功能）版式宜在设计工具做好再进流程。客服侧对应：固定话术块、按钮（「提交换货」）由产品设计，不让模型即兴发明活动。

**6. 长耗时步骤要有产品态**  
查单一般很快；若质检、人工审核是异步的，要有进度和超时文案，不能当成一次同步聊天。

## Function Call：让模型决定要不要动手

工作流的第 N 步可以写死「调用天气接口」。Function Call / Tool Calling 不同：**调不调、调哪个，由模型根据当前对话决定。**

背景：模型什么都懂一点，但默认不能发邮件、查航班、关灯。如果不把「手」接上，效率会被最后一公里的人工操作卡住。系统里最慢的那块会拖垮整体——模型再快，人去复制粘贴，整体还是慢。

OpenAI 等提出的 Function Calling，本质是一份工具说明书（名字、参数 schema）给模型，模型输出「我要调哪个、参数是什么」，真正执行仍在你们后端。

| 场景类型 | 特征 | 产品价值 | 例子 |
| --- | --- | --- | --- |
| 实时数据 | 要现在的状态 | 避免用过期记忆回答 | 天气、股价、航班、库存、订单 |
| 单次动作 | 一次调用做完 | 提效 | 发消息、开关设备 |
| 多工具编排 | 有先后和参数传递 | 跨系统办事 | 先查天气再发通知；先查单再检索制度 |
| 业务集成 | 和内部系统耦合 | 真正办成事 | 建会议、改工单、创建售后单 |

和 RAG 再次对照：制度用检索；订单用 Function Call。穿衣助手如果只调天气，建议一般；若再加「衣柜知识库 + 识图工作流」，才能基于用户真实衣物建议。产品上这是「工具 + 知识库 + 工作流」组合，不是单点功能。

## 安全：模型提议，后端做主

- 模型输出不等于已经执行。
- 权限、参数合法性、幂等、审计日志必须在服务端。
- 转账、删除、群发、改价格、创建售后单，要二次确认。
- 工具范围要最小：客服 Agent 不该拿到财务写接口。

工作流里每一步调什么是确定的，评测相对好做。Function Call 是模型动态选择，评测要覆盖：该调没调、不该调却调了、参数错、调用成功但话术错。

## 适用 / 不适用

**适用工作流**

- 换货咨询、开票、标准理赔：步骤清楚，分支能画完。
- 要给客服质检「每单走过哪些节点」。

**适用 Function Call（在鉴权之内）**

- 用户有时报订单号、有时只说「上周那单」，需要模型决定先追问还是先查列表。
- 工具很多，但每个都很窄（查单、查物流、建单）。

**不适用**

- 用工具「查完再让模型随便改库存」。
- 接口失败时用模型编一个物流结果顶上。
- 路径极度开放、还没画清退出条件——那是下一页 Agent，且通常不该作为客服 v1。

## PRD 要写清什么

| 字段 | 售后助手示例 |
| --- | --- |
| 入参 / 出参 | 入：user_id, utterance；出：reply, rma_id?, escalate |
| 工具清单 | `get_order` 只读；`create_rma` 写，需用户点确认 |
| 每个工具的身份 | 一律用登录 session，禁止模型传入任意 user_id |
| 幂等 | 同一会话重复点「提交」不得创建两张售后单 |
| 超时 / 失败 | 3 秒无响应：道歉 + 转人工；禁止假装查过 |
| 二次确认文案 | 「将为您提交质量问题换货申请，是否确认？」 |
| 评测 | 该调未调、误调、参数错、成功但话术说成已发货 |

## 验收例子

订单接口约定返回：签收 6 天、数码配件、无人为损坏。制度：7 天内质量问题可换。

| 用例 | 通过 | 不通过 |
| --- | --- | --- |
| 主路径 | 先查单，再引用 7 天条款，结论可以申请换货，并出现确认按钮 | 未调接口就说可以换；或调了接口却说「还在路上」 |
| 查单失败 | 「暂时查不到这张订单，为您转人工」 | 「系统显示您的订单已签收」 |
| 用户说「直接给我换好」 | 仍停在确认前；未调用 `create_rma` | 调用写接口或口头办结 |
| `create_rma` 失败 | 明确失败原因 + 工单/转人工 | 「已经提交成功」 |
| 他人订单号 | 后端拒绝，提示无权限 | 查出别人的地址或商品 |

## 和研发、算法、业务怎么对齐

| 角色 | 负责 |
| --- | --- |
| 产品 | 路径画死还是允许选工具、哪些写操作要确认、失败话术、评测用例 |
| 研发 | 鉴权、幂等、超时、审计、工具 schema |
| 算法 | 意图到工具的准确率；不负责「没有鉴权也能查」 |
| 业务 | 何时必须人工（高客单价、疑似欺诈、投诉升级） |

对齐会上先把工具画成表：只读 / 写入、是否要确认、失败用户看见什么。表不全，不要开始调 Prompt。

## 面试常问

**「什么需求该画死工作流，什么该让 Agent 选工具？」**  
步骤能画完、错误要可复盘：工作流。用户说法很散、工序集合却封闭：可以在工作流外包一层意图路由。客服换货咨询，v1 应画死。

**「为什么查天气可以是 Function Call，出一支标准短视频更像工作流？」**  
天气是一次实时查询，调不调取决于用户有没有问天气。标准短视频是固定工序生产线，每一步都要发生，不应让模型决定跳过配音。

**「工具失败时提示重试、转人工，还是编一个假结果？」**  
前两选一，按超时策略写进 PRD。最后一项永远不该选。

**「模型和后端谁说了算？」**  
模型提议，后端做主。面试里能举出「查单必须校验当前用户」，比背 Function Call 定义更有用。

## 常用工作流模式

能用一次模型调用解决，就不做工作流；能用确定工作流解决，就不增加 Agent。这是架构选择的默认顺序。

| 模式 | 做什么 | 售后助手 |
| --- | --- | --- |
| 串行 | 上一节点输出成为下一节点输入 | 抽字段 → 查单 → 检索 → 生成 |
| 并行 | 多个来源同时处理 | 同时查订单和查制度 |
| 路由 | 先分类，再进不同流程 | 换货 / 物流 / 投诉升级 |
| 聚合 | 汇总候选后选优 | 多条制度片段重排后再生成 |
| 循环 | 生成—检查—修正，必须有上限 | 格式校验失败则重试一次 |
| 人工关口 | 写操作前确认 | 提交换货按钮 |

每个节点定义超时、重试、幂等、降级和可观测性。写操作用唯一请求标识，避免重试导致重复建单。

低代码平台适合快速证明最关键的不确定性：用户愿不愿意用、核心结果能否达标、数据是否可得、流程是否可接入。合格 Demo 只需 3～5 个核心功能，但必须跑通完整旅程。从 Demo 到生产要补权限、隔离、监控、版本、容量、成本、审计和 SLA。平台缩短验证时间，不会自动消除工程责任。平台分层见 [应用平台与部署选择](/concepts/ai-tech/llm-rag-agent/app-stack-and-deployment)。
