# RAG 与知识库

RAG 是 Retrieval-Augmented Generation，检索增强生成。它先从知识库找资料，再让模型基于资料回答，适合企业知识问答、制度查询、客服助手和文档分析。

## RAG 链路

1. 文档解析。
2. 清洗和切分。
3. Embedding 向量化。
4. 向量库和元数据存储。
5. 用户问题检索。
6. Rerank 重排。
7. 组装上下文。
8. 模型生成答案和引用。
9. 记录反馈和 Bad Case。

## 技术链路要点

- 文档是否有权限和版本。
- 切分是否保留语义完整。
- 是否支持关键词 + 向量混合检索。
- 答案是否给出引用。
- 找不到资料时是否拒答。
- 用户反馈能否回流。

RAG 的难点不是“接一个向量库”，而是让资料可信、可更新、可追溯。

## RAG 错了怎么排查

| 现象 | 可能原因 | 优先排查 |
| --- | --- | --- |
| 完全答不上来 | 知识库没有资料，或问题没有召回。 | 文档覆盖、切分、Embedding、Top K。 |
| 答案引用错资料 | 检索相似但不适用。 | 元数据、权限、时间、Rerank。 |
| 引用了资料但答偏 | 上下文太乱或 Prompt 不清。 | 上下文组装、格式约束。 |
| 编造不存在内容 | 没有强制基于证据回答。 | 引用校验、拒答策略。 |
| 用户看不到依据 | 展示层没做引用。 | 前端引用展示、来源链接。 |

不要把所有 RAG 问题都归因于模型。很多时候是资料治理和检索链路的问题。

## 工程实践要点

大模型应用的关键不是“接入模型”，而是把模型放进可控链路：用户输入、上下文、知识库、工具、权限、输出格式、人工确认和日志追踪。每个环节都可能决定功能能不能上线。

| 能力 | 适合解决 | 必须补上的约束 |
| --- | --- | --- |
| LLM | 理解、生成、总结、抽取。 | 输出格式、拒答、安全边界。 |
| RAG | 接企业知识和最新资料。 | 来源、权限、切分、召回和引用。 |
| Tool Calling | 查询或修改业务系统。 | 服务端鉴权、参数校验、二次确认。 |
| Agent | 路径不固定的多步任务。 | 步数预算、工具范围、日志和退出条件。 |

## 示例代码

下面是一个最小 LLM 调用伪代码，展示输入、上下文、模型调用和输出校验的结构：

```python
def answer(question, context):
    prompt = f"""基于资料回答问题。
资料：{context}
问题：{question}
"""
    result = call_model(prompt)
    if not result.strip():
        return {"status": "empty", "answer": None}
    return {"status": "ok", "answer": result}
```

真实系统需要把检索、权限、引用、结构化输出、日志和错误处理补齐。

## 技术细节拆解

RAG 与知识库 可以拆成输入、处理、输出和指标四层。这样读的时候不会停留在概念名，而是能看到它在系统里接收什么、改变什么、产出什么。

| 层次 | 具体内容 |
| --- | --- |
| 输入 | 用户问题、系统提示词、历史对话、检索片段、工具 schema。 |
| 处理 | 上下文组装、模型调用、工具调用、输出解析、权限校验。 |
| 输出 | 自然语言、JSON、引用、工具结果、拒答信息。 |
| 指标 | 准确率、引用命中率、格式成功率、工具成功率、成本、延迟。 |

## 关键参数和边界

| 参数/边界 | 说明 |
| --- | --- |
| temperature | 越高越发散，越低越稳定。 |
| max_tokens | 限制输出长度，也影响成本和截断风险。 |
| top_p | 控制采样范围，通常和 temperature 配合。 |
| schema | 结构化输出必须有 schema 和校验。 |

## 可运行检查

```python
import json

raw = '{"answer":"可以办理", "confidence":0.82}'
data = json.loads(raw)
assert "answer" in data
assert 0 <= data["confidence"] <= 1
print(data)
```

## 怎么判断学懂了

| 判断点 | 具体标准 |
| --- | --- |
| 格式稳定性 | 结构化输出能否被程序稳定解析。 |
| 证据一致性 | 回答是否能追溯到检索片段或工具结果。 |
| 权限安全 | 不同用户只能检索和调用授权范围内的资源。 |

## 常见误区和排查

| 问题 | 为什么会发生 | 怎么排查 |
| --- | --- | --- |
| 回答没有证据 | 模型自由发挥，没绑定检索片段。 | 强制引用来源并校验引用存在。 |
| 工具参数不合法 | 模型输出 JSON 不符合接口要求。 | 用 schema 校验，失败时让模型重试或拒绝执行。 |
| 权限穿透 | 检索阶段没有按用户权限过滤。 | 把用户身份加入检索条件并记录审计日志。 |

## 这一页在链路上负责什么

售后助手问「能不能换」，制度不在模型参数里。这一页负责：**先从你们的生效文档里找出相关片段，再让模型基于片段说话。** 订单状态仍不是知识库的事。前面正文已经有链路步骤和排查表；下面用同一条售后案例，把「什么进库、怎么验收、谁维护」写成产品规格。

## 什么时候必须上 RAG

提示词只能调动模型在预训练里已经见过的模式和公开知识。下面这些东西默认不在里面：

- 公司退换货规则、对内 SOP
- 商品详情、价格策略、活动规则
- 内部案例、项目复盘、制度 PDF
- 你们自己的口径、禁止承诺清单

只靠提示词问这些问题，模型仍会答，而且常常很自信。这就是幻觉在企业场景里最常见的来源：不是模型「坏了」，是你让它回答它没读过的材料。

RAG（Retrieval-Augmented Generation，检索增强生成）的产品定义是：**先从你们的资料里找出相关片段，再让模型基于片段回答。** 目的不是「接一个向量数据库」，而是让答案有据、可更新、可追溯。

## 三类信息，三种接法

做客服机器人时，不要把所有问题都丢进知识库。

| 信息类型 | 例子 | 更合适的做法 | 原因 |
| --- | --- | --- | --- |
| 通用表达 | 礼貌话术、总结、改写 | 模型本身 | 预训练已覆盖 |
| 相对稳定的内部知识 | 退换货制度、产品说明、操作手册 | RAG | 模型没见过，但文档可以索引 |
| 实时状态 | 订单物流、库存、余额、工单状态 | Function Call / 查库 | 知识库更新追不上交易 |

常见误区：把「查我的订单」做成 RAG。订单每分钟都在变，向量库不是交易系统。知识库回答「规则是什么」，工具回答「你这笔单现在怎样」。

## 贯穿案例：制度进库，订单不进库

用户问能不能换那只耳机。知识库里应有一份当前生效的《售后政策》，例如：

> 电子产品签收 7 天内因质量问题可换货；超过 7 天走维修；人为损坏不换。

正确检索结果：命中「电子产品 / 换货时限 / 质量问题」这几段，并带文档版本号和生效日期。

模型应基于片段说：「按当前售后政策，电子产品在签收 7 天内、且属于质量问题，可以申请换货。是否满足时限，需要核对您这笔订单的签收时间。」  
还不能说「可以换」——签收几天是订单接口的事。

错误做法：

- 把历史工单、物流轨迹、每个用户的聊天记录一股脑向量化，当成「知识」。
- 制度改了只发群公告，知识库仍是去年的 15 天时限。
- 检索到「服装 7 天无理由」却用在耳机上，没有类目过滤。

## RAG 适合什么业务

相对适合：

- 制度、手册、FAQ、合同条款查询
- 客服里「政策怎么规定」而不是「我的单到哪了」
- 运维手册、故障复盘经验沉淀后再检索
- 有病例库、案例库、研报库，需要「先找相似再生成解释」
- 希望答案带来源，方便人和法务核对

不一定以 RAG 为主：

- 强创意写作（有时纯生成更好）
- 毫秒级行情、实时库存（应查系统）
- 没有任何可维护文档、只有口口相传（先治理资料）

## 链路要能点名负责人

完整链路可以记成：

1. **加载**：PDF、网页、表格、工单知识如何进来，谁有权限上传。
2. **切分**：文档往往长过模型窗口，要切成块。切太大检索不准，切太碎没有上下文。
3. **向量化与存储**：块变成 Embedding，写入向量库，并带上权限、部门、生效日期、文档版本等元数据。
4. **检索**：用户问题同样向量化，找最相近的块；更好的系统会加关键词、元数据过滤、重排。
5. **拼进提示词**：把命中片段和角色、任务、格式要求拼在一起。
6. **生成**：模型只基于这些材料写。
7. **引用与拒答**：展示来源；找不到就说找不到，不要空编。
8. **回流**：Bad Case 回到切分、权限、文档更新，而不是只骂模型。

产品验收时按层问，避免所有问题都归到「换个更强的模型」：

| 现象 | 先查哪一层 | 售后助手例子 |
| --- | --- | --- |
| 完全答不上 | 有没有文档、切分、Embedding、召回条数 | 《售后政策》根本没入库 |
| 引用了不相关资料 | 权限、时间过滤、重排、类目元数据 | 召回了服装无理由退货 |
| 资料对但答案歪 | 提示词拼装、格式约束 | 片段写 7 天，回复写成 15 天 |
| 编造不存在的条款 | 是否强制 grounded、拒答策略 | 编「首单包运费」 |
| 用户看不见依据 | 前端有没有展示引用 | 客服质检无法核对 |

## RAG 如何进 Agent：增强提示词

不要只把知识库挂成「对话框旁边的附件」。更稳的用法是固定四步：

1. 用户原话进入。
2. 检索器返回若干片段及相关度。
3. **提示词增强**：角色 + 检索到的材料 + 明确任务 + 数字/口吻/引用要求。
4. 模型生成，并标来源。

课堂里的研报结构（数字仅说明拼装方式，上线必须以你们真实资料和评测为准）：

- 用户问：分析某公司某季度某业务，要关键数据和对比。
- 检索可能返回：财报摘要、行业报告、第三方研究，各有相关度。
- 增强后的提示词应写成：你是分析师；下面是检索到的数据（分条列出）；任务是对比、解释差异、给下一季方向；数字精度和口径要求；没有的数据不要编。

售后助手同样：把「检索到的制度原文」整段贴进提示词，并写「数字和时限必须与片段一致，片段没有的句子不要写」。模板属于提示词规格，检索质量属于数据与算法规格。

## 和提示词、微调的边界

| 手段 | 解决什么 | 不解决什么 |
| --- | --- | --- |
| 提示词 | 角色、格式、拒答、任务拆解 | 模型没见过的内部事实 |
| RAG | 可更新的内部知识、可引用 | 实时交易状态、模型文风彻底改变 |
| 微调 | 稳定口吻、领域格式、反复出现的模式 | 天天改的制度（改一次就要重新训不划算） |

经验数字（如「幻觉下降百分之几十」）只能当课堂直觉，不能写进对外承诺。上线用你们自己的评测集：检索命中、引用真实、过期文档、权限隔离。

## 适用 / 不适用

**适用**

- 规则以文档形式存在，且有人维护版本。
- 答案需要可引用，质检和法务要能点开原文。
- 同一套制度服务很多重复问法（「能换吗 / 换货几天 / 耳机坏了怎么办」）。

**不适用**

- 「我的订单到哪了」、库存、余额。
- 只有老客服脑子里的口径，从未写成文档——先治理，再上 RAG。
- 希望入库一次、永远不用更新——制度一改，助手就会用旧法害人。

## PRD 要写清什么

| 字段 | 售后助手示例 |
| --- | --- |
| 知识范围 | 现行售后政策、类目说明、禁止承诺清单；不含订单、物流轨迹、用户隐私聊天 |
| 语料来源与权限 | 客服运营上传；法务审核后发布；过期文档下线而不是留着「也许有用」 |
| 元数据 | 类目、生效日期、文档版本、是否对用户可见 |
| 找不到时 | 对用户：「我这边没有查到适用规则，为您转人工」；禁止用通用电商常识顶上 |
| 引用展示 | 对内必显来源；对用户是否显示「根据售后政策」由品牌决定，但质检后台必须有 |
| 更新 SLA | 制度变更后多久必须入库，例如工作日 4 小时 |
| 评测集 | 至少覆盖：正确类目、错误类目干扰、过期文档、无文档拒答、同义问法 |

评测集规模：冷启动 30～50 条真实问法即可开始；不要等「完美语料」再上线，但也不能零金标。

## 验收例子

约定：库里只有现行《售后政策》（7 天质量问题可换），没有订单数据。

| 用例 | 通过 | 不通过 |
| --- | --- | --- |
| 用户问能不能换（有订单号） | 引用 7 天质量问题条款，并声明还要核对签收时间 | 直接宣布可以换；或引用服装无理由 |
| 运营故意留了一份去年「15 天」旧文档且未下线 | 检索被版本/生效日期过滤，或评测判知识治理失败 | 助手按 15 天答复 |
| 问「我的包裹到哪了」 | 不检索制度硬答物流；应走工具或说明查不到轨迹 | 从某篇 FAQ 里编一个物流状态 |
| 库里没有该品类规则 | 拒答 + 转人工 | 用手机类规则套在家电上 |

## 和研发、算法、业务怎么对齐

| 角色 | 负责 |
| --- | --- |
| 产品 | 范围、找不到怎么办、对用户是否展示来源、更新时限、评测用例 |
| 业务 / 法务 | 哪份是唯一生效制度、禁忌承诺、金标答案 |
| 算法 | 切分、混合检索、重排、相关度阈值；向产品解释「为什么召回这条」 |
| 研发 | 权限过滤、审计、发布流程；上传者身份 |
| 运营 | 日常增删改；Bad Case 回流工单 |

产品不要把「召回率」单独丢给算法交差。没有类目元数据和过期下线，算法再强也会召回错制度。

## 面试常问

**「客服里规则和订单为什么不能共用一个知识库？」**  
规则是文档，订单是交易状态。混在一起会用过期文本回答正在变的事实，也会把个人订单泄漏进检索。

**「RAG 错了，怎么判断是文档、切分、检索还是提示词？」**  
完全没答到：先看有没有入库。答了无关类目：元数据和重排。片段对但话术改了数字：提示词和 grounded 校验。编出库里没有的句：拒答策略没生效。

**「为什么先检索再生成要写进产品流程？」**  
因为这是用户承诺：「我们按现行制度回答」。把它当成纯实现细节，业务会以为接了聊天框就等于接了知识。

**「制度经常改，该微调还是 RAG？」**  
改文档、重新索引。为改一则时限去微调，成本和回滚都划不来。
