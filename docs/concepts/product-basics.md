# 产品经理基本功

AI 产品仍然先是产品，需要需求、用户、流程、指标和协作能力。

## 知识点清单

| 知识点 | PM 要掌握的重点 | 面试可能怎么问 |
| --- | --- | --- |
| 需求分析 | 从用户任务出发，而不是从“接入大模型”出发。 | 需求分析 对 AI 产品设计有什么影响？ |
| 用户研究 | 围绕最近一次真实任务追问输入、输出、判断标准和错误成本。 | 用户研究 对 AI 产品设计有什么影响？ |
| 竞品分析 | 用任务链路比较产品，不只做功能表。 | 竞品分析 对 AI 产品设计有什么影响？ |
| PRD | 额外写清模型行为、输入输出、评估标准和异常兜底。 | PRD 对 AI 产品设计有什么影响？ |
| 指标体系 | 覆盖使用、质量、效率、成本和风险五层指标。 | 指标体系 对 AI 产品设计有什么影响？ |
| 数据分析 | 通过触发率、采纳率、重试率、编辑率定位问题。 | 数据分析 对 AI 产品设计有什么影响？ |
| B 端流程 | 关注权限、安全、集成、审计、交付和运营责任。 | B 端流程 对 AI 产品设计有什么影响？ |
| ROI 测算 | 把 AI 能力转化为降本、提效、增收或风险降低。 | ROI 测算 对 AI 产品设计有什么影响？ |
| 灰度发布 | 降低模型不稳定和流程误操作带来的上线风险。 | 灰度发布 对 AI 产品设计有什么影响？ |
| 需求优先级 | 优先选高频、耗时、数据可得、错误成本可控的场景。 | 需求优先级 对 AI 产品设计有什么影响？ |
| 验收标准 | 用样例集和可观察指标替代“生成得不错”。 | 验收标准 对 AI 产品设计有什么影响？ |
| 跨团队协作 | 连接业务、研发、算法、法务、安全和运营。 | 跨团队协作 对 AI 产品设计有什么影响？ |

## 学习方法

1. 先用一句话解释概念，避免陷入纯技术细节。
2. 找一个真实产品场景，说明它如何改变用户流程。
3. 写出风险、指标和验收标准。

## 练习任务

选择 3 个知识点，各写一个「用户场景 + 产品方案 + 指标」的小卡片。

---

AI 产品经理不是「会写 Prompt 的传统产品经理」，也不是「懂几个模型名词的项目经理」。这个岗位要把模糊的业务期待，翻译成可验证的用户任务、可实现的智能能力、可控的系统行为和可持续的商业结果。下面按工作顺序把基本功写清楚。贯穿例子仍用电商售后助手：用户说「耳机坏了，能换吗？订单号 202608210088」。

## AI 产品经理到底在解决什么

传统软件把需求写成规则：用户点按钮，系统执行预先定义的逻辑。大模型产品更像概率性的能力系统：同一输入可能得到不同结果；表现受上下文、知识、工具状态和模型版本影响；它能处理规则难以穷举的问题，也可能一本正经说错。

因此必须同时管理四种不确定性：

| 不确定性 | 售后助手上的样子 | 产品要管什么 |
| --- | --- | --- |
| 需求 | 业务说「做个智能客服」，真实任务可能是少转人工、少承诺错误、或少查单时间 | 写成可观察任务，而不是聊天框 |
| 能力 | Demo 上 10 句都答对，真实长尾（人为损坏、过保、情绪投诉）不稳 | 评测集覆盖长尾，不拿 Demo 当验收 |
| 系统 | 答错可能是制度没入库、订单接口超时、提示词乱承诺 | 按层复盘，不默认换模型 |
| 价值 | 回复更会说话，客服仍不愿用，或严重错答导致资损 | 看一次解决、严重错误、是否愿意继续把入口交给它 |

正确交付物不是对话框，而是责任系统：哪些任务由 AI 完成，哪些由规则约束，哪些要人确认，失败时怎样解释、重试、撤销和转人工。

用四个问题判断自己是不是在做 AI 产品工作：

| 维度 | 核心问题 | 典型产出 |
| --- | --- | --- |
| 用户与业务 | 谁在什么场景中遇到什么阻碍？ | 用户任务、流程图、机会判断 |
| 智能能力 | 模型为什么能解决，边界在哪里？ | 能力拆解、技术路线、失败分类 |
| 产品与工程 | 怎样让能力稳定、可用、可控？ | PRD、工作流、权限、降级与评测 |
| 商业与组织 | 价值如何量化，谁为它付费？ | ROI、定价、增长与实施方案 |

行业能力在涨，可靠交付并不同步。机会不是「接入更强模型」，而是把能力变成可验证、可治理的产品。技术细节见 [大模型应用](/concepts/ai-tech/llm-rag-agent/)。

## 五类基本功，按能闭环到哪一层衡量

**产品基本功**回答做什么：用户研究、需求判断、信息架构、交互和数据分析。  
**AI 基本功**回答智能怎样形成：模型边界、Prompt、RAG、工具、Agent、记忆与评测。  
**业务基本功**回答怎样嵌入真实流程：角色、规则、成本、数据和责任。  
**商业基本功**回答为什么值得持续投入：价值量化、增长、定价和单位经济。  
**协作基本功**把业务、算法、研发、数据、运营、销售和行业专家对齐。

不要用「知道多少术语」衡量自己，用能独立闭环到哪一层：

| 层级 | 能独立做到 | 售后助手例子 |
| --- | --- | --- |
| L1 | 用 AI 提高个人效率 | 自己用模型改客服话术 |
| L2 | 设计单点功能，写清输入输出和体验 | 给定制度片段，生成对用户的短回复 |
| L3 | 完成 RAG / 工作流 / Agent 的端到端方案 | 查制度 + 查订单 + 确认后建单 |
| L4 | 建立数据、评测、成本和业务反馈闭环 | 黄金集、严重错误率、Token 与转人工一起看 |
| L5 | 定义行业 AI 战略，推动组织与商业模式变化 | 售后组织、质检口径、供应商和 SLA 一起改 |

### PAIR：四方对齐，才叫可验收

一个可落地的 AI 需求至少完成四方对齐：

- **P（Product）**：用户问题、场景、流程、范围、体验和指标。
- **A（AI）**：模型能做什么、不能做什么，评测集和质量门槛是什么。
- **I（Implementation）**：系统、数据、权限、延迟、稳定性和运维怎样实现。
- **R（Result）**：业务结果如何衡量，收益归谁，风险由谁承担。

产品经理的价值不是替算法选模型，而是把「效果不错」翻成可验收标准。「回答准确」应拆成：检索命中率、事实忠实度、任务完成率、关键错误率、拒答正确率、人工接管率。售后助手里，「准确」若只等于「像客服」，就会把乱承诺也算通过。

## 从功能设计转向行为设计

传统 PRD 列举页面和规则；AI PRD 还要定义系统在模糊输入、知识缺失、工具失败和高风险请求下如何行为。设计重点从「页面是否存在」变成「系统是否在正确条件下采取正确行动」。

AI 产品常见三种嵌入方式：

1. **AI 包裹流程**：原流程不变，AI 只生成文案、摘要。落地快，壁垒弱。例如把客服工单自动写成摘要，办理仍走旧系统。
2. **AI 嵌入流程**：AI 进入检索、分析、审核或决策节点，直接改善关键指标。售后助手查制度、查订单，属于这一层。
3. **AI 重构流程**：围绕目标重新划分人、系统和 AI 的责任，可能创造新体验与商业模式。例如用户不再填售后表，对话确认后直接建单并回写 OMS。

判断成熟度，不看聊天框漂不漂亮，而看这些机制在不在：证据引用、结果可编辑、关键动作确认、失败解释、撤销回滚、权限隔离、过程追踪、人工升级。

### 交互不应只有对话框

对话适合表达意图和处理开放问题，不适合精确配置、批量比较和高风险确认。成熟产品通常混合交互：对话理解意图，表单约束参数，画布展示过程和产物，卡片支持比较与操作，传统页面完成权限、账单和管理。

原则：**表达越开放，越适合自然语言；责任越重大，越需要结构化界面与明确确认。** 售后里「能不能换」可以对话；「确认提交质量问题换货」必须是按钮，并展示将写入系统的字段。

## 从用户任务出发挖场景

不要从「我们能不能做一个 Agent」开始，而要从「谁想完成什么任务，今天为什么做不好」开始。完整场景至少包含：用户、触发条件、目标、输入、处理过程、输出、使用环境、约束、异常和责任人。

高潜 AI 场景通常有一个或多个特征：信息量大、规则无法穷举、需要理解非结构化内容、重复认知劳动多、个性化程度高、跨系统协调复杂。相反，任务规则稳定、输入结构化、错误成本极高且没有人工复核时，传统软件或规则引擎往往更合适。

To C 需求可归为：提高效率、消除未知、情感与关系、娱乐与创作、交易与决策。To B 围绕增收、降本、提效、控险和组织协同。分类只是入口，必须落到具体任务。例如「提高销售效率」要继续拆成客户研究、线索排序、沟通准备、会议纪要、跟进建议和 CRM 回写。

### 场景机会画布

访谈时少问「你想要什么功能」，多追问最近一次真实事件：当时想完成什么、拿到哪些信息、在哪一步停住、如何绕过、错误造成什么后果。真实行为比愿望清单更接近需求。

| 问题 | 必填内容 | 售后助手填写示例 |
| --- | --- | --- |
| 谁 | 具体角色、能力差异、使用权限 | 已登录买家；未登录不查单 |
| 何时 | 触发条件、频率、时间压力 | 签收后发现质量问题，常在下班后 |
| 要完成什么 | 可观察的任务结果 | 得到能否换货的结论，或提交申请 |
| 今天怎么做 | 工具、人工步骤、等待与返工 | 翻物流、找客服、等排队、口头承诺对不上系统 |
| 最大阻碍 | 时间、信息、判断、协作或操作 | 制度口语化、订单状态分散、客服口径不一致 |
| AI 做什么 | 理解、生成、检索、判断或执行 | 理解诉求、检索制度、查订单、生成话术 |
| 人做什么 | 授权、审核、例外处理与担责 | 疑似欺诈、高客单、情绪升级转人工 |
| 成功如何判断 | 业务、产品、质量和风险指标 | 一次解决率、乱承诺次数、转人工准确性 |

### 五维评估再进开发

一个场景进入开发前，应同时过五道门：

1. **需求真实性**：是否高频、强痛或高价值，用户是否已经付出成本解决。
2. **技术可行性**：任务能否分解、输入是否足够、质量是否可测。
3. **数据可得性**：知识、历史样本和反馈能否合法获取、持续更新。
4. **风险可控性**：错误能否发现、撤销、由人工接管。
5. **商业持续性**：价值是否覆盖模型、实施、运维、审核与获客成本。

可用相对排序（不是精确财务公式，作用是迫使团队公开假设）：

`机会得分 = 价值强度 × 发生频率 × 覆盖规模 × AI 增益 × 可落地性 ÷ 风险成本`

### 容错率决定自动化等级

同样的模型准确率，在不同场景意义不同。生成活动创意可以容忍多个候选；自动付款、医疗诊断和合同承诺则不能只靠「多数时候正确」。

| 风险 | 自主性 | 售后助手 |
| --- | --- | --- |
| 低风险、可逆 | 可自动执行，提供历史和撤销 | 生成话术、工单摘要 |
| 中风险、可校验 | AI 建议，人确认后执行 | 创建换货申请 |
| 高风险、难逆 | AI 只检索整理，专业人员决策 | 高客单赔偿、疑似欺诈 |
| 不可接受 | 禁止，或改用确定性系统 | 口头说「已经打款」 |

PoC 验证技术假设，MVP 验证用户价值，生产版本验证规模化的稳定、成本、安全与组织采纳。不要拿 PoC 演示成功率替代生产验收。

## 从业务流程定位切入点

先还原 As-Is：角色做什么、信息从哪里来、在哪做判断、操作写回哪个系统、责任由谁承担。再设计 To-Be，并把节点分成四类：AI 节点、规则节点、人工节点、系统节点。

常见错误是把整条流程一次性交给模型。更可靠的方式是按可验证中间产物拆分，例如：文档解析 → 信息抽取 → 知识检索 → 方案生成 → 规则校验 → 人工确认 → 系统执行。每个节点都有输入输出、失败条件、重试方式和负责人。

售后助手可以拆成：抽取订单号与诉求（AI）→ 查订单（系统）→ 检索制度（AI+检索）→ 时限规则（规则：签收是否 ≤7 天）→ 生成话术（AI）→ 用户确认（人）→ 创建售后单（系统）。

优先选择「价值高、边界清晰、结果可评估」的节点试点。单点跑通后，再向上游扩展数据、向下游连接执行。端到端并不等于端到端都由 AI 自主完成。

## AI 产品 PRD 要多写的部分

在传统业务背景、用户、范围和流程之外，还必须写清：

- 输入来源、上下文、模型、知识库、工具和记忆；
- 理想输出、最低可接受输出和明确禁止输出；
- 质量指标、评测样本、验收阈值和版本基线；
- 不确定、缺证据、冲突、超时、工具失败时的行为；
- 权限、敏感数据、日志、内容标识和人工接管；
- 延迟与成本预算、监控告警、灰度与回滚。

AI 可以帮助整理访谈、生成初稿和发现遗漏，但不能替产品经理决定业务目标、责任边界和风险接受度。任何由 AI 生成的需求都要回到证据：用户研究、数据、业务规则、技术验证或监管要求。

### 最小目录（可直接当大纲）

1. 背景、问题证据与目标  
2. 用户、场景、范围与非目标  
3. As-Is / To-Be 流程和用户旅程  
4. AI 能力、知识、工具、记忆与系统架构  
5. 输入输出、状态、交互与人工接管  
6. 数据、权限、隐私、安全与内容标识  
7. 评测集、指标、阈值与验收  
8. 延迟、成本、容量和稳定性  
9. 灰度、监控、反馈、回滚与迭代  

## AI 交互：让用户知道三件事

系统正在做什么、结果依据什么、下一步由谁决定。长任务要显示阶段和进度；知识型答案要提供证据；可编辑产物要保留修改权；高风险操作要展示影响并确认。

关键状态都要设计：空状态、加载、流式输出、信息不足、无权限、无可靠答案、工具失败、部分成功、等待确认、完成和撤销。不要把所有错误都包装成「请稍后重试」，否则用户无法判断是自己输入问题还是系统能力边界。

信任不等于堆砌免责声明。真正的信任来自可验证证据、稳定行为、用户控制和诚实表达不确定性。置信度若没有校准依据，显示一个百分比反而会制造虚假精确。售后助手不要写「我有 92% 把握可以换」——写「按现行制度，签收 6 天且为质量问题，可以申请换货，需您确认提交」。

## 用生成式编码做 Demo，不要直接当生产

用自然语言更快生成页面、组件和接口，速度不等于质量。正确流程是：写清任务与验收 → 生成最小版本 → 运行和截图 → 逐项反馈 → 检查状态与边界 → 让真实用户完成任务。

Demo 前先定义信息架构、页面、核心流程、数据结构和假接口；生成后检查组件状态、数据持久化、错误处理、移动适配和可访问性。每次只改一个明确问题，并保留可回退版本。低代码工作流（如编排平台）同样：合格 Demo 通常只需 3～5 个核心功能，但必须跑通完整旅程——用户进入 → 提供必要信息 → 系统处理 → 看到结果与证据 → 纠正或确认 → 完成任务。评审时记录成功样本、失败样本、等待时间、人工干预和用户原话。

从 Demo 走向生产还要补齐：身份与权限、数据隔离、异常处理、监控、版本管理、容量、成本、审计、安全测试和服务承诺。生成代码和低代码都不会自动消除这些工程责任。

## 场景机会评分表

每项 1～5 分，风险项反向计分。总分只用于项目间比较，不是财务模型。

| 维度 | 评分问题 |
| --- | --- |
| 问题强度 | 用户是否频繁付出时间、金钱或承担风险？ |
| AI 增益 | 相比人工、规则和搜索是否有明显提升？ |
| 数据条件 | 输入、知识和反馈是否可合法持续获得？ |
| 可评测性 | 是否能定义成功、错误和最低门槛？ |
| 流程接入 | 能否进入现有入口和系统闭环？ |
| 商业价值 | 收益是否覆盖全部建设与运行成本？ |
| 风险可控 | 错误是否可发现、可逆、可接管？ |
